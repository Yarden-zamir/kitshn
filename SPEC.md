# KitSHn 2 spec

KitSHn 2 runs your apps, sites, pages, files and machines on Cloudflare, and decides who may open each one. It puts everything on one map. Circles on the map say who. A card inside a circle is shared with that circle.

The repo is named "KitSHn 2". "kit" is the short name of the project. Code, packages and the MCP tools use `kitshn`. The CLI is `kitshn`, with `kit` as a short alias. The admin and the map live at `kit.yarden-zamir.com` until the pending move of K-1209 to `kitshn.yarden-zamir.com` (K-1208).

Requirements have stable numbers with the prefix `K-`. Do not renumber them. Mark a removed requirement "Removed" and keep its number. `VERIFY:` marks a Cloudflare fact that the docs do not confirm; the first milestone that needs it tests it.

The architecture, the request paths and the budget are in [docs/architecture.md](docs/architecture.md). The order of work is in [docs/migration.md](docs/migration.md).

## Core rules

- **K-001** The app and what it needs to deploy live in its repo. The places (machines, the Cloudflare account, domains, who may open what) live in kitshn, never in the repo.
- **K-002** "Create a repo, push, and it deploys" stays true. A new app repo needs a recipe and a workflow file, and nothing else: no per-repo secret, no setup step in kitshn. The one exception is the first deploy of a repo, which waits for one click by the owner or by an agent key that may add apps (K-819).
- **K-003** kitshn runs on Cloudflare only. Its logic and state run in one Worker with one Durable Object. Machines do only machine work: tunnels, local sites, Compose deploys, commands and builds.
- **K-004** kitshn fits the Cloudflare free plan for the setup of K-1301. A paid plan only raises limits; no feature needs it.
- **K-005** kitshn knows nothing about T3 Code. T3 Code and other programs add their own resource kinds through the local interface of section 7.
- **K-006** Every unexpected state fails closed: a request that kitshn cannot decide gets no access, and the error says why.

## Terms

- **Owner:** the person who installed kitshn. The owner is the first member of the "Owner" circle.
- **Circle:** a named group of who: people (emails), email domains, devices, networks (IP ranges), machines, and the flag "needs passkey". A circle has a default level.
- **Resource:** something that kitshn can share: a machine, a site, a page, a file, an app, a thread. Each resource kind names its levels.
- **Card:** a resource on the map.
- **Share:** a card inside a circle. It gives the members of the circle the circle's default level on that resource, or the level of an override.
- **Level:** what a share allows. Each resource kind names its own ordered levels, for example `view`, `use`, `control`.
- **Daemon:** the `kitshn` program on a machine.
- **Provider:** a program on a machine that adds resource kinds through the daemon, for example T3 Code.
- **Recipe:** `kitshn.config.ts` in an app repo.
- **Environment:** one deployed copy of an app, for example `prod` or `pr-12`.
- **Job:** one piece of machine work, for example a Compose deploy.

## 1. Identity and login

- **K-101** Cloudflare Access does every login. kitshn has no login code and no password store.
- **K-102** People log in with the Access One-time PIN (an email code). GitHub is a second login method next to the email code. The passkey check of K-103 applies after either login method.
- **K-103** A circle with "needs passkey" asks for a passkey or a security key after the login, through Access independent MFA. [Independent MFA](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/independent-mfa/) supports biometrics (Touch ID, Face ID, Windows Hello) and security keys, per application and per policy.
- **K-104** kitshn administration is a resource of kind `kitshn.admin` with the level `control`. Its card sits in the "Owner" circle. The Owner circle has "needs passkey" on.
- **K-105** kitshn refuses every change that leaves the admin resource without a share to a circle that has at least one person and "needs passkey". This guard runs on every write: a drag, a circle edit, an undo, an agent tool and the pause (K-1504). It also refuses a share of the admin resource with a circle that has "everyone", because that circle compiles to an Access Bypass policy.
- **K-106** A device proves itself with an Access service token: one token per device, for example "Mac desktop app" or "Yarden's phone". A device is a circle member like a person.
- **K-107** A machine proves itself to Access with its own service token (K-602), and to kitshn also with its own key pair (K-1704). A machine is a circle member too, so a share can give one machine access to another resource.
- **K-108** Browser approvals of the machine map (browser keys, the Clients approval flow) do not exist in kitshn. A passkey or a device token replaces them.
- **K-109** Access sessions of the admin resource last 24 hours. Sessions of other resources last 30 days unless a circle sets a shorter time.
- **K-110** "Sign out everywhere" ends every Access session of every application that kitshn made, through the Cloudflare API. It does not end sessions of other applications (K-408). The Worker also refuses page and file logins from before the sign-out (K-1004). It runs at once, without a confirm; its label and tooltip say that every session ends. History records the start, before any Cloudflare call, and then the outcome: how many applications ended their sessions, and which failed. While an application is left (a failed call, the call limit of one request, or a failed list of applications), the Access warnings name it with "Retry sign-out", which is also in the command palette. A retry revokes only the applications left that kitshn still has, or starts over after a failed list; an application that Cloudflare no longer has counts as ended. History records each retry's outcome, and the warning goes when every session ended. One sign-out or retry runs at a time.
- **K-111** Zero Trust Free counts one seat per person who logs in, up to 50. kitshn turns on seat expiration in Zero Trust admin controls, set to 1 month, so guests who stop coming free their seat. [Seat management](https://developers.cloudflare.com/cloudflare-one/team-and-resources/users/seat-management/) runs the expiry once a day.
- **K-112** The admin view shows the seats in use, with a warning at 40. The view can also remove a seat. Checked on 2026-10-27: `GET /accounts/{id}/access/users` lists each user with `seat_uid` and `access_seat`. VERIFY: the [seat API](https://developers.cloudflare.com/api/resources/zero_trust/subresources/seats/methods/edit/) `PATCH /accounts/{id}/access/seats` turns a seat off. Milestone 2 tests it with the Seats view.
- **K-113** Every person in a circle with "needs passkey" can open the App Launcher, because Access enrolls a passkey there (`https://<team>/AddMfaDevice`). kitshn keeps one reusable policy "kitshn passkey enrollment" on the App Launcher application, made from the emails and domains of the passkey circles with "any" match that have not ended; during a pause (K-1504), only of the Owner circle. A circle with "all must match" is left out, because its rules joined with "or" would let in more people than the circle does. A failed write of the App Launcher waits for the daily retry. It adds that policy next to the existing policies of the App Launcher and never changes or removes another policy there. The daily compare (K-408) repairs it. The circle editor shows the enrollment address while "needs passkey" is on.

## 2. Circles and shares

- **K-201** A circle has a name, a colour, a default level, members, a match mode (K-203), an optional end date, and the flag "needs passkey".
- **K-202** Member kinds: an email, an email domain, an IP range, a device token, a machine, and "everyone". "Everyone" means anyone who can reach the address, with no login.
- **K-203** A circle has one of two match modes:
  - "Any" (the default): the visitor matches at least one member. In Access, the members are include rules.
  - "All must match": the visitor matches every member, for example the domain `qlik.com` and the IP range of the Qlik network. In Access, the members are require rules. This replaces the "required IP ranges" of the machine map Guests view.

  With "needs passkey", the visitor must also pass a passkey check in both modes.

- **K-204** A card is shared with every circle that it sits inside. Circles overlap freely, and there is no limit on their number.
- **K-205** A share uses the default level of its circle. One card can override the level for one circle. The override shows as a chip on the card.
- **K-206** A level that the resource kind does not have becomes the highest level of that kind that is lower. A circle with the default `control` thus gives a file `view`.
- **K-207** When several circles match a visitor, the visitor gets the highest level of those shares.
- **K-208** A card outside every circle is private. Only the admin (K-104) can see it in the map.
- **K-209** A share can have an end date. At the end date, kitshn moves the card out of that circle as a new revision, and the history names the expiry. An Undo of the expiry puts the card back, and an end date that has passed does not come back with it, so the share stays until someone changes it. Any other Undo that brings back an end date that has passed, such as the Undo of a later end date, keeps it, so the share ends at once.
- **K-212** A card can have an end time, as a timed card: for example a preview of a local server for one hour. The share ends of K-209 and the card end share one expiry step. At the end time every share of the card ends at once, also before the alarm runs. The alarm then moves the card to the tray, out of every circle and its stack, in one revision: "Time of <card> ended", with the shares that it lost. That revision runs as the actor who set the time, which is the actor of the revision that set it, also an Undo, so that actor's Undo (K-1506) brings the card and its shares back, without the passed end time. Any other Undo keeps a passed end time, such as the Undo of an extension after the first end, so the card ends at once. Setting, moving and removing an end time and "End now" are one service: the map, `POST kit.<zone>/api/cards/<card>/time` and `POST kit.<zone>/agent/cards/<card>/time` with `{"endsAt": <ms> | null}` or `{"now": true}`, and `kitshn time <card> <30m|1h|4h|1d|stop|now>` on a machine (K-1714). An agent sets the time only of a card that it manages (K-718), and `kitshn agent state` shows each `endsAt`. The admin card cannot have an end time (K-105). During a pause, an end time cannot move later or go (K-1504), unless the card leaves the map with it, as at its end and with End now.
- **K-210** A circle with "everyone" asks for confirmation the first time that a card enters it: "This makes <name> public."
- **K-211** The Owner circle and the Everyone circle exist from the start. The owner can rename them, and cannot delete the Owner circle. A delete of another circle runs at once, without a confirm; the toast and History undo it (K-1502).

## 3. Resources

- **K-301** Built-in resource kinds and their levels:

  | Kind           | Levels             | What it is                                                  |
  | -------------- | ------------------ | ----------------------------------------------------------- |
  | `kitshn.admin` | control            | kitshn administration (K-104)                               |
  | `machine`      | view, use, control | a machine with a daemon (section 6)                         |
  | `site.static`  | view               | a static site on Workers static assets                      |
  | `site.worker`  | view               | a Worker app                                                |
  | `site.compose` | view               | a Compose app on a machine                                  |
  | `site.live`    | view               | a local site of a machine, through its tunnel (K-1104)      |
  | `page`         | view               | an HTML page in the library (section 10)                    |
  | `file`         | view               | a file in R2                                                |
  | `repo`         | view               | a repo that has a recipe; its environments are its children |

- **K-302** A provider adds kinds through the daemon (K-704). Each kind has an id with the provider prefix (for example `t3.thread`), its levels, and how it is enforced (K-405).
- **K-303** An environment of an app is its own resource and its own card, for example "riffle" and "riffle pr-41". A preview card (a deploy of a `pr-<n>` environment, K-821) shows a "PR #<n>" sticker with the number of that environment, and its panel links the pull request on GitHub. New environments start in the circle that the recipe names (K-807).
- **K-304** Each resource has an id, a kind, a name, an owner machine when it has one, its addresses, and its status. The status is one of: running, stopped, deploying, failed, offline, unknown.

## 4. Enforcement

- **K-401** kitshn compiles shares into Cloudflare Access wherever Access can check them, so a check costs no Worker request.
- **K-402** Each circle becomes reusable Access policies: one for its people (Allow, with the passkey check), and one for its devices and networks (Service Auth), because Access lets service tokens and logins without a person in only through Service Auth. A resource with an address becomes one self-hosted Access application whose policies are the circles that hold it. Checked on 2026-10-27: the API attaches one reusable policy to two applications, and the policy reports `app_count` 2. The account limits are 500 applications and 500 reusable policies ([account limits](https://developers.cloudflare.com/cloudflare-one/account-limits/)).
- **K-403** A resource inside "Everyone" gets a Bypass policy, or no Access application.
- **K-404** The Worker checks shares itself for what it serves: pages and files (section 10 and 11). It reads the Access JWT and the visitor IP; its only cookies of its own hold the Access tokens of the login steps and the return mark of a login step (K-1004).
- **K-405** A provider enforces levels inside its own program. kitshn gives it a grant table for each of its resources (K-706). Access still guards the address: it lets in every circle with a level above none.
- **K-406** kitshn writes Access changes in a Durable Object alarm queue. One alarm run makes at most 40 Cloudflare API calls and sets the next alarm when work remains. kitshn counts each call before it starts, also calls that run together. The free plan allows 50 subrequests per request ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)).
- **K-407** The map shows a change at once. Each card shows "applying" until Cloudflare has the change, and "failed" with the reason if Cloudflare refuses it. A refusal is any error that is not an unclear answer, also an error without a status, such as a fault of kitshn itself. A refusal waits for the daily compare of K-408. When Cloudflare gives no clear answer (no answer, a 5xx or a 429), the write may or may not have landed. kitshn then forgets the body of that object, and the card shows "retrying" with the reason and the time of the next try. kitshn tries again after 5 minutes, then after 15, then every 60 minutes, and the daily compare also tries. Each try first reads the object back and compares it with the wanted body. If Cloudflare serves the wanted body, kitshn keeps it and writes nothing. On any difference, kitshn writes the wanted body and never adopts what Cloudflare serves. If the body that Cloudflare serves has a policy that the wanted body does not have, kitshn ends the sessions of that application (K-409). A create that landed is found by name on the next run (K-408). A write that lowers access (it takes a policy off an application, takes a person or a rule out of a policy, adds a check to a policy, deletes one, or replaces a body that kitshn does not know) never waits for the daily compare. It tries again on the same backoff, also after a refusal. Until it lands, the card shows "Access not lowered yet" with the reason, in red, because the old access can stay open. Each change on the map clears every failed write and its backoff, so the next alarm writes the wanted bodies at once.
- **K-408** A daily alarm compares Access with the shares and repairs differences that kitshn made. It never changes an Access application or policy that kitshn did not make, and it names such an application when it covers a kitshn address. The one exception is the login applications of pages and files: kitshn removes every policy there except its own and the machines policy (K-1004).
- **K-409** A lower level takes effect at once: kitshn revokes the Access sessions of the affected application, and providers end the sessions of members that lost a level. A policy write that takes access away (K-407), such as a person out of a circle, revokes the sessions of each application that uses that policy. Each revoke comes after the write that took the access away. The revokes of one write run together, and the deletes of the same run do not wait for them. When more applications use the policy than one run can reach, the next runs end the sessions that are left.
- **K-410** Removal order: kitshn never deletes an Access application while a route can still reach its address: tunnel ingress, a DNS record, a Worker route or a custom domain. It takes the route off and confirms it, then the DNS record, and deletes the Access application last. A failed step stops the sequence and retries after five minutes. A card with several addresses (K-817) goes through these steps for each address.

## 5. Map UX

The map is the main view. These requirements improve the demo of 2026-10-26.

- **K-501** The map shows every card and every circle. The "Show" menu of the toolbar has a toggle for each kind, which hides that kind. Hidden kinds still count for their circles.
- **K-502** A drag of a card, or of a selection, into or out of a circle shows a preview before the drop: each circle edge lights up, and a label says what changes, for example "+ Qlik · view" or "− Her". The drop applies it.
- **K-503** After each drop that changes a share, a toast names the change and has Undo for 10 seconds. Undo is also in the history (K-1502). The toast shows in the half of the open map away from the card that the change names (under the toolbar, or at the bottom above the hint line, or on a phone above an open card sheet), so it never covers that card; a change that names no card uses the last press or drop instead. A toast button ignores a press in its first 500 ms, so a double press of the button that made the toast never runs Undo.
- **K-504** A drag of a circle by its head moves its cards with it. ⌘ and a drag on macOS and iOS, or Ctrl and a drag on other systems, moves the circle alone. The tooltip of the head and the hint line name the key. The preview of K-502 then names every card that gains or loses the circle.
- **K-505** A resize of a circle shows the same preview as K-504 before the release.
- **K-506** A circle shows its members as chips on its edge, at most 4. A "+N" chip opens the full list. The circle head sits on the top of the edge. When a card covers that spot, the head slides along the edge to the first free spot, at most 55° to each side; when no spot is free, the head stays at the top. Heads draw above cards, so a card never hides a head or its level sticker. Known limit: two heads can still overlap each other. Revisit this when circles often touch at their tops.
- **K-507** A card shows a dot for each circle that holds it, and a chip for each override (K-205). A hover on a dot names the circle and the level.
- **K-508** Cards stack by group: the environments of one app, the pages of one thread, the files of one upload. A stack shows the top card and a count. A click opens it as a column under the top card, where each card steps down by its drawn height when that is taller than a plain card (a card with a preview frame, also one opened from its kind sticker), so no card covers the one below it; a click on a card of an open stack selects that card and the stack stays open, and the count on the top card closes it. A drag of a stack moves all its cards.
- **K-509** New cards arrive in a tray at the edge of the map, outside every circle, so they start private (K-208). Cards that a recipe places (K-807) and files dropped on the map (K-1101) skip the tray. The tray lists every such card, newest first, with a filter, and scrolls on its own. A click on its count folds it to that count and opens it again; each device keeps that choice in local storage, and a folded tray leaves its width to the map. Unset, it is open on a wide screen and folded on a phone (K-528). A card dragged from the tray, or several picked with Shift, lands where it is dropped, in exactly the circles there (K-204, K-210).
- **K-510** Multiselect: a box drag on empty space, Shift and a click, and "Select all of this kind" in the context menu. A selection moves as one.
- **K-511** The command palette (Cmd+K or Ctrl+K) finds every card, circle and action. "Share <card> with <circle>" works without a drag, also on a phone.
- **K-512** The card panel shows who can open the card: each circle, its members, the level, and the address. It has "Copy address" and "Open".
- **K-513** Zoomed out under 40%, cards become dots and each circle shows its counts by kind. On touch, a tap on a dot zooms to 100% around the finger and opens its group or stack; the next tap selects the card. The map never animates continuously, and a change plays at most one short transition.
- **K-514** Pan, zoom, fit and auto layout work as in the machine map (MM-1111, MM-1114 to MM-1121). Each device keeps its own view in local storage. The map fits on load when the device has no saved view, and when the panel (K-519) opens or closes while the owner has not panned or zoomed since the load. A fit shows every circle with its heads and every card whole in the free area, left of an open panel, right of the tray, below the toolbar and above the hint line, and zooms out as far as that needs, down to 0.15. On a wide screen a saved view zooms out no further than 0.85, so card names stay readable; the wheel zooms out further. Fit, and the pan of "Show details" and of a History row (K-1508), keep circle heads and cards clear of the toolbar, the tray and an open panel (K-519).
- **K-515** A card of an offline machine, or of an app on it, shows the "offline" sticker and the time since it was last seen. A machine card also shows its live state from data that the client already has (K-605), with no new traffic: a row with the daemon version and system, and online CPU and memory bars from the newest sample; offline, the row says "seen <time> ago" and shows no bars, because an old load is wrong. These rows have a fixed height, with two lines for stickers, and the bar row stays empty while offline. The presence sticker of a machine card says only "offline", without the time. So a status change never resizes the card or moves a saved card. Its stickers are, in this order, "<n> needs you" while asks of the machine wait for the viewer, the number of its queued jobs from the job table (a link to the Machines view), and NEWEST or BEHIND (K-1616). Only a member of the approver circle sees "needs you" (K-1902), and it opens the Inbox with the asks of that machine only and a link back to every ask. The maps get an update when kitshn hands queued jobs to the machine.
- **K-516** The map works on a phone: one finger pans the map, a long press opens the context menu (K-523) and starts a drag of the card, and a move after it closes the menu. Two fingers pinch to zoom, inside the zoom range of the wheel, and pan together; a second finger ends a drag or a hold that the first one started, and moves no card. The panel (K-519) is a bottom sheet over at most 45% of the screen, and its full view takes the whole screen.
- **K-517** The map uses the tick3d look in light and dark mode (the `neo-brutalism` skill): lilac dotted canvas, ink borders, hard shadows, tilted stickers, Bricolage Grotesque. It uses the standard components of the skill and no native browser UI: every icon button, control, option, sticker and short label has a tooltip. Needed information is never only in a tooltip.
- **K-518** Map state (places, circles, members, shares, stacks) lives in the kitshn database, never in Git (K-001).
- **K-519** Views next to the map: History (with presets, K-716), Queue, Inbox (K-1607), Seats, Usage (K-1303), Machines (a table of status), Health (alerts and charts, K-1604, K-1605), Settings (K-1613), Tasks (K-1614), Clients (K-1602), Library (section 10). Each view and each selected item has its own link; `#map/<card id>` selects the card. Known limit: a selection on the map does not change the link. Revisit this when links to selections get shared often. History, Library, Machines, Usage and the details (the selected card, stack or circle, or the map with its circles and repos) open in one panel that floats over the right side of the map, from the toolbar tabs; a selection on the map shows its details there. The panel has a header with its title, "Enlarge", and Close. "Enlarge" opens the full view of the same content: the tab view of History, Library and Machines, or the details over the whole map; "To the map" goes back. A panel that opens puts the focus on its heading, and its header stays at the top while it scrolls. Escape outside a text field and a dialog first clears a selection, then closes the panel, and the focus goes back to the control that opened it; in the History search, Escape first clears the search. After Close, the Map tab shows as not pressed, and a click on it opens the panel again. The map keeps its full width under the panel. Beside the panel, the toolbar and the hint line end at the panel edge, and the hint wraps.
- **K-520** "Previews" shows a live view of up to four site and page cards near the centre of the map, from zoom 80%. Each is a sandboxed frame that exists only while it shows, a thumbnail of the top of the page at the width of the card, that takes no clicks until "Interact". Until the page loads, the frame shows a still "Loading preview" in the look of the card; a page that does not load within 20 seconds shows "Preview not available" with Open, because a browser reports no error for a frame. Known limit: a page that refuses to be framed fires `load` with the browser's error page, so it shows that page, not "Preview not available"; revisit if refused frames become common. On the map, a dragged card draws above every other card, then the card with keyboard focus (also focus inside its frame, until focus leaves), then selected cards, then cards with a frame, which reach over the cards below; circle heads stay above all of them (K-506); a sideways trackpad pan of the map never becomes the browser's back swipe. A site behind Access shows only when the browser has its Access session already, because the Access login refuses to load in a frame; the frame of a card that is not public always says so, next to "Open in new tab". A selected card with an address also offers its preview on its kind sticker: a small "▾" button at the sticker's end, with a target of at least 1.75rem (2.5rem on a touch screen) that never covers the sticker's text, opens and closes one such frame by click or keyboard, on the card on the map and in the card sheet on a phone, and the rest of the sticker still selects and drags the card. The frame loads only then, with "Enlarge" for a large view over the map, which Escape closes and which leaves the selection as it is; it starts closed for every card, and the frame goes when the card loses the selection. A card without a preview shows the plain sticker. A file gets the ▾ only for a type that a browser shows (images, PDF, text, audio, video), because a frame downloads any other. A site frame gets `allow-scripts allow-same-origin allow-forms`, which is safe only because each app has its own origin; kitshn never frames the admin host, and a page or a file frame gets only `allow-scripts`, as the Worker sandboxes them anyway (K-1003).
- **K-521** The owner can stack cards: drop a card on another card, or select several cards and choose "Stack these", in the selection panel, the menu of a selected card or the palette (one shared action, K-523); the other cards stack onto the first selected card on the map, and the action is left out when the cards already are one stack. A stack holds two or more cards and may have a name: a new stack has none, and a stack without a name shows only its cards, and History and menus name it by its cards. kitshn refuses a name with spaces around it. A card is in one stack at most. Its cards sit on one point, so the stack moves as one and every card of it gets the same circles; moving one card moves its stack. A level override (K-205) and an end date (K-209) stay per card; when a stacked card's share ends, the card leaves its stack. Closed, a stack is one card that lists its cards from top to bottom; a click, or "Open as a column" in its menu and the palette, opens it as a column of cards ("Close the column" closes it), and as in K-508 a click on one of its cards selects that card and the stack stays open. Stacks by group (K-508), such as the previews of an app, stay as they are.
- **K-522** The stack panel renames the stack or clears its name, pulls one card out (it lands next to the stack, in the same circles, so no share changes), and "Unstack" spreads all cards in the same circles. Each of these, and a drop that makes or grows a stack, is one revision with Undo (K-1502); a stack that enters a public circle asks first (K-210). A drop from the tray never stacks, and a stack by group dropped on a card joins that card's stack. While a drag is over a card, the card is outlined and the label says "Stack with" it.
- **K-523** Cards, stacks, circles and the empty map have a context menu. A right-click opens it, and so do a long press on touch (K-516), Ctrl and a click on macOS, the menu key, and a "⋯" button on each card, stack and circle head and on each card in the tray, which the keyboard reaches. Zoomed out (K-513), a card is a dot without "⋯"; a right-click and the menu key on the focused dot open its menu. The menu holds the same actions as the toolbar, the panel and the command palette, from one list per item, so the palette (K-511) has every menu action. - **K-525** The owner drags the left edge of the side panel and the right edge of the shelf (the tray of K-509) to change their widths. - **K-529** "New circle for these" makes one new circle around two or more selected cards: in the selection panel, the menu of a selected card and the palette. "Share with" of one card, in its menu, the palette and its panel, ends with "New circle…", which does the same for that card alone. A selected card takes its stack along (K-521). - **K-532** "Organize" puts the cards in order: the toolbar has it next to Fit, with a tooltip, and so do the "☰" menu (K-528), the menu of the empty map and the palette (K-523). ## 6. Machines and the daemon

- **K-601** Each machine runs one `kitshn` daemon as a service of the user who joined it: a systemd user service on Linux (it starts without a login when the user has lingering on), a launchd agent on macOS, a Task Scheduler task at the user's logon on Windows (K-622). The tunnel runs as a second user service of the same user, `kitshn-tunnel.service` on Linux, `com.kitshn.tunnel` on macOS and the task `\kitshn\tunnel` on Windows, which the daemon installs and starts (K-603). The daemon is one binary per platform, so a machine needs no Node.js. A Windows machine stays on the machine map portal until it joins kitshn ([docs/migration.md](docs/migration.md)).
- **K-602** "Add machine" creates a service token and a remotely managed tunnel, and shows a one-time join command with a code that expires after 10 minutes: `curl -fsSL <address>/join | sh -s -- <code> <address>`. The command downloads the daemon, runs `kitshn join`, and starts the service. `kitshn join` saves the token and the tunnel token in a file that only the daemon user can read, makes the machine key pair and sends its public half with the code (K-1703). kitshn stores the two tokens only encrypted with a key from the code, and deletes them when the code is used. The code has 20 random characters (about 99 bits), so kitshn sets no attempt limit; revisit if codes get shorter.
- **K-603** The daemon runs `cloudflared` for the tunnel of its machine as its own user service (K-601), with the tunnel token in a file that only the user can read (`--token-file`), not on the command line. A restart or an update of the daemon never stops the tunnel, so apps and sites keep serving. The daemon restarts the tunnel service only when `cloudflared`, its token or its service file changes, and reads the state of the service for its status (K-605). Known limit: "running" means that the service runs, not that `cloudflared` has a connection to Cloudflare. Revisit with the readiness endpoint of `cloudflared` when a false "running" misleads. kitshn owns the tunnel ingress through the API; the daemon never edits it. Each ingress rule whose address has a kitshn Access application sets `originRequest.access` with `required: true`, the team name (the first label of `ACCESS_TEAM_DOMAIN`) and the audience tag of that application, so `cloudflared` drops a request without a valid Access JWT ([origin parameters](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/origin-parameters/#access)). This guards the address when a DNS record or a removal step goes wrong. A rule whose application has a Bypass policy (K-403) gets no check, because Access issues no JWT for Bypass. kitshn takes this decision from the application that Cloudflare last accepted, not from the shares, so the check never comes on before Access stops the Bypass. When kitshn does not know the accepted body of the application or of one of its policies, the rule goes without the check. kitshn stores the audience tag of each application. Before it writes ingress, it reads missing tags from the list of applications, and tries again after five minutes. When the list does not have the application, kitshn forgets its id and makes it again. A site never leaves the tunnel for a missing tag: while kitshn does not know the tag, the rule goes without the check, and kitshn logs the address. An empty `ACCESS_TEAM_DOMAIN` has the same effect. The check comes on at the next tunnel write after kitshn stores the tag. Checked on 2026-10-27: a Service Auth policy whose only include is an IP range let a request from that IP in with no login, and Access set `CF_Authorization` on the response. So Access issues a JWT for a network member, and the check stays on. An Allow policy with only an IP range sends the visitor to the login instead; kitshn does not compile networks to Allow (K-402). A service token gets a JWT (K-1004).
- **K-604** The daemon keeps one WebSocket to the Durable Object at `/connect`, with backoff after a failure. Each connection starts with the challenge of K-1704. Liveness uses `ping` and `pong` with the Durable Object auto response, so a ping wakes nothing.
- **K-605** The daemon sends its status on connection and on each change, at most once every 5 seconds. It sends a resource sample (CPU, memory, disk) once a minute. The local request `samples` (K-702) gives a sample taken now and the samples of the last hour from the daemon's disk (K-606), with no message to kitshn.
- **K-606** The Durable Object keeps only the latest sample of each machine, in memory. The daemon keeps 30 days of history on its disk and answers a history request. This keeps the daily writes low (K-1302).
- **K-607** Local sites use Unix sockets. A Compose service listens on `<deployment>/sockets/<name>.sock`, and the tunnel ingress sends its address to `unix:<path>`. Services publish no host ports. Caddy is not needed. The [ingress docs](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/configure-tunnels/local-management/configuration-file/) show `service: unix:/path` for local configuration files. Checked on 2026-10-27: the API accepts `service: unix:/path` in a remotely managed tunnel configuration, and `cloudflared` 2026.10.3, run with the tunnel token, served a request from a Unix socket.
- **K-608** For an app that cannot listen on a socket, the recipe names a port inside its Compose network, and the daemon adds a small socket proxy service. The machine still publishes no host port.
- **K-609** Each machine has labels, for example `docker`, `server`, `arm`, `laptop`. The owner sets one order of all machines.
- **K-610** A job names the labels that it needs. kitshn gives it to the first online machine in the order that has all of them. Without such a machine, the job waits in the queue until its expiry (K-613). A deploy runs only on a machine that has the label `deploy`, so the apps of repos never land on a machine that the owner did not offer for them.
- **K-611** A running app stays on its machine. kitshn never moves it by itself. "Move to <machine>" in the card panel deploys it on the other machine and then removes the old copy.
- **K-612** Commands are jobs too. Built-in commands: restart the daemon, update the daemon, collect diagnostics, run a shell command. A provider adds its own commands (K-707).
- **K-613** A job for an offline machine waits. It has a delivery rule ("when online" or "when online and idle", `whenIdle` in the jobs API, K-1608) and an expiry, by default 24 hours.
- **K-614** "Run a shell command" needs `control` on the machine. The member that sends it is in the history. A job that kitshn makes itself, such as a deploy (K-812), needs no member; the `deploy` label is the owner's consent (K-610).
- **K-615** "Remove machine: deletes its token and tunnel" runs at once, without a confirm, and History records it. It deletes its service token, its public key (K-1707), its tunnel, its DNS records and its queue, and closes its connection. Its apps show as stopped with "Deploy elsewhere". A connected daemon then stops and removes its tunnel service and the tunnel token file (K-603). For a machine that is offline at that moment, the tunnel service stays until `kitshn service uninstall` on it.
- **K-616** A whole machine can belong to another person. Example: a second VPS whose card sits in the circle "Her" with `use`, and in the Owner circle with `control`. Its provider shows everything on it to every member with `use`, including the owner's threads there. The owner accepted this.
- **K-617** kitshn names one release: the version of its Worker. The join command, "Update daemon" (K-612) and the deploy workflow download the daemon and the CLI only from that release, `edge-<version>`, and check each file against its `SHA256SUMS`. "Update daemon" in the machine panel and the jobs API take no version from the sender. The rolling `edge` release only serves the bootstrap of a new account. The daemons are gzipped in the release (`kitshn-<os>-<cpu>.gz`), and `SHA256SUMS` names the `.gz` files. The release workflow never deletes an `edge-<version>` release: on a public repository they cost nothing, an old one is the way back, and a machine pinned to it keeps working. Every `edge` release is a pre-release, so none shows as "Latest".
- **K-618** The daemon carries the kitshn skill for coding agents of its release (`packages/kitshn/skill/SKILL.md`), with one line under the front matter that names the release and the update command. `kitshn skill install` writes it to `~/.local/share/kitshn/skills/kitshn` and links `~/.claude/skills/kitshn` to it, relative to the real skills folder, so the link matches the one that stowed dotfiles track. It replaces that path only when it is free, or a link that resolves to kitshn's folder or whose text ends with `.local/share/kitshn/skills/kitshn`; a folder or another link of the user stays, the command refuses with one line, and a refusal writes nothing. Each write goes through a temporary file or link and a rename. `kitshn skill install --repo` writes `.claude/skills/kitshn/SKILL.md` in the git repo around the working folder, and refuses a linked folder, such as the kitshn repo's link to the source. `kitshn skill check` exits 1 when the global copy or its link is missing, or when the global or the repo copy is from another release, and names the update command. A copy from another release counts as out of date. The join script installs the global copy once, and the daemon writes it again at its start when it is from another release, as after an update (K-612); a link of the user stops that too, and the daemon logs it once per release. The deploy workflow warns, and deploys anyway, when the repo copy is missing or from another release than the server. The KitSHn 1 skill (`kitshn-deploy-service`) has no link in the kitshn repo, so kitshn 2 agents do not read it. The App CLI carries the skill of its release too, and `kitshn repo` (K-1127) writes the repo copy into a new repo.
- **K-619** Each daemon reports the TCP ports that listen on its machine, for the site wizard (K-1131): the port, the process name, and the status and `<title>` of one `GET /` on `127.0.0.1`, or on `[::1]` when that refuses, with a 2-second deadline and at most 64 KB read. It reads them with `lsof` on macOS and `ss` on Linux every 30 seconds, sends the list on connect and only when it changes, and checks only new servers, except every 10th scan, which checks all of them again. It reports only the listeners of the daemon's own user (`lsof -u` on macOS, the `uid` of `ss -e` on Linux, where a root daemon takes the lines without a `uid`, because `ss` prints none for root) and leaves out a listener without a known owner, so it never probes a server of another user. It leaves out cloudflared and kitshn itself, and sends at most 32 entries, by port. kitshn keeps the list on the machine's socket, so it costs no row writes and goes with the connection. Workerd keeps at most 16,384 bytes there, so every write of a machine socket's data (status, sample, volumes, servers) goes through one budget of 15,000 bytes of estimated structured clone, where a string with a character above U+00FF counts two bytes for each character; over the budget, the last servers go first, then the last volumes. A machine agent gets its own list in `kitshn agent state`, and `kitshn servers` prints it on the machine.
- **K-620** Windows: one console binary, `kitshn-windows-x64.exe`, in each release beside the other daemons (K-617); no Windows arm64 build in the first version. Windows cannot replace a running program but can rename it, so an update renames the running `.exe` to `kitshn.old-<time>.exe`, a name of its own, then puts the new one in place, with retries while a virus scan holds it; when that still fails, the old one goes back, so the task always finds a binary. Each start deletes the old copies that no process runs, and tries the others again every hour.
- **K-621** On Windows the local socket of K-701 is the named pipe `\\.\pipe\kitshn-<user>`. A pipe without a security descriptor gives read and write only to its owner, SYSTEM and Administrators, and read only to everyone else, so no other user and no low integrity process sends it a request (tested on Windows 11). Every caller counts as the daemon user. The name is first come: a program of another account can take it before the daemon starts. The daemon start then fails, and each client checks the account SID of the pipe's server process (`GetNamedPipeServerProcessId`, then its token) before it sends anything, so it refuses such a pipe and sends nothing. Known limit: the check opens the pipe once, and the client then connects again, so a program of another account that takes the name between the two gets the request; with one account on the PC nothing can, and the next step is one connection for both, when a Windows machine has more accounts. The daemon keeps at most 64 pipe connections, and it closes a connection that sends no line within 30 seconds. Bun's pipe server does not refuse remote clients (no `PIPE_REJECT_REMOTE_CLIENTS`): over SMB from the same PC, `CreateFileW` opened the pipe for write as the owner, as it opened a control pipe without that flag, and a control pipe with the flag refused it (tested on Windows 11). So only the access list above guards the pipe from the network: a client over SMB writes only as the owner, SYSTEM or an Administrator. The Windows firewall blocks SMB from other machines by default ("File and Printer Sharing (SMB-In)" is off on that PC). Known limit: with SMB open, a remote session of the owner or an Administrator reaches the pipe; an Administrator over SMB can already run programs on the PC. Revisit when a machine has a user other than the owner.
- **K-622** On Windows `kitshn service install` registers two tasks of the user in the Task Scheduler folder `\kitshn\`: `daemon` and `tunnel`. Each starts at logon, runs with no time limit, starts again within 5 minutes after it ends, and runs through `conhost --headless`, so no window opens. The daemon runs only while the user is logged on; a service that runs without a logon needs a service account and admin rights, a later step. The tunnel task runs the daemon's own copy of cloudflared, `kitshn-cloudflared.exe`, with `--token-file`, its own `--config` file and a free metrics port (`127.0.0.1:0`), so it shares no name, config or port with another cloudflared on the machine, such as a system "Cloudflared" service; the daemon reads the tunnel state from that process name, because the task state of `schtasks` is in the language of Windows. "Restart" and an update start the daemon task again before the daemon exits. `schtasks /End` does not stop the program inside `conhost`, so a stop also ends the daemon or the tunnel process, found by its full path in the user's folders, never by its name alone.
- **K-623** On Windows the config, the key, the tokens and cloudflared live in `%LOCALAPPDATA%\kitshn`. The join turns off inherited access on that folder and gives full access only to the user and SYSTEM, because Windows ignores the file modes of K-602.
- **K-624** What Windows does not have in the first version: Compose apps, their logs and backups (no Docker setup; the daemon does not report those capabilities, so the map and the deploy refuse them with a reason), the running servers list of K-619 (its scan sends an empty list), the KitSHn 1 takeover and local users other than the user who joined. Shell jobs (K-612) run in Windows PowerShell. Exposed local servers and agent calls work as on the other platforms.
- **K-625** "Add machine" also prints the join for Windows PowerShell: `& ([scriptblock]::Create((irm https://<KITSHN_HOST>/join/windows.ps1))) <code> https://<KITSHN_HOST>`. The script sits below the public Access path `/join`, so the bootstrap needs no new application. It downloads the daemon of the release that kitshn names, checks it against `SHA256SUMS`, puts it in `%LOCALAPPDATA%\Programs\kitshn`, joins, installs the tasks and the skill, and adds the folder to the user's `Path`.

## 7. Local interface for providers (T3 Code)

- **K-701** The daemon listens on a local Unix socket: `$XDG_RUNTIME_DIR/kitshn/kitshn.sock` on Linux, `~/Library/Application Support/kitshn/kitshn.sock` on macOS. On start, the daemon removes an old socket file and makes a new one, with mode 0600 in a folder with mode 0700. A second daemon refuses to start while another daemon answers on the socket. On stop, also on SIGTERM and SIGINT, the daemon removes the file and ends its running shell jobs. For each connection, the daemon reads the user id of the peer: `SO_PEERCRED` on Linux, `getpeereid` on macOS. Bun has no call for this, so the daemon uses `bun:ffi`. The daemon closes the connection unless the peer is the daemon user or is in `localUsers` of `machine.json`, a list of user ids. The list is empty by default, so only the daemon user connects. The daemon reads the list at each connection. A peer whose user id it cannot read, or a list that it cannot read, never passes (K-006). The daemon user changes the list with `kitshn local-users list`, `add <user or uid>` and `remove <user or uid>`. Only the daemon user and root reach this socket: its folder is 0700, and the folder above it (`$XDG_RUNTIME_DIR` on Linux, `~/Library` on macOS) is 0700 too. So the daemon also listens on a shared socket, `/tmp/kitshn-<uid>/kitshn.sock`, with mode 0666 in a folder with mode 0711, and the peer check is its only guard. Another user can make that folder in `/tmp` first, so the daemon uses it only when `/tmp` belongs to root and has the sticky bit, and the folder is a real folder of the daemon user, not a link; otherwise the daemon logs why and runs without the shared socket. A client that finds such a folder of another user says so, instead of saying that no daemon runs. `add` accepts any user id. A client finds the socket by itself: `KITSHN_LOCAL_SOCKET` when set, else its own socket, else the one shared socket in /tmp. It trusts a shared socket only when the system user `kitshn` owns its folder, the folder name holds that user id, the folder has mode 0711, and the socket belongs to that user too. Another local user can make a folder in /tmp under its own user id, so only the user name anchors this trust. Otherwise, and with two shared sockets, the client refuses with one line. Known limit: a daemon whose user is not named `kitshn` needs `KITSHN_LOCAL_SOCKET` for the other users; revisit when such a machine joins. Before a client sends anything, it reads the peer user id of the socket in the same way and stops unless it is the daemon user: `KITSHN_DAEMON_UID` (digits only), else the id in the name of the shared folder, else the id in `/run/user/<uid>/` of a private socket, else its own. A user in `localUsers` may send only `status`, `ask`, `forget-token` (K-1762) and `forward` (K-1714); `rotate-key`, `reconnect`, `attester-set` (K-1751) and every other machine-admin request answer "not allowed" unless the caller is the daemon user or root. A new request kind must name who may send it. So a user who made the folder first cannot pose as the daemon. A client service with systemd `PrivateTmp=yes` does not see the shared socket. The daemon logs each request with the user id of the caller, and a refused connection at most once a minute for each user id. Planned for `pass` (K-1713): a request that the daemon forwards to kitshn carries that user id, so History can name it. An agent pass goes only to an allowed local user (K-1713). Known limit: Bun gives the descriptor of a connection only in its `fd` property, which Bun does not document. Without it, the daemon refuses every peer. So CI compiles `packages/daemon/src/peer.selftest.ts` for linux-x64 and linux-arm64 and runs it, and a Bun upgrade that drops `fd` fails CI, not a machine. `.bun-version` names the one Bun of CI and of the release build. Checked on 2026-10-28: the daemon reads the user id of a client of the same user on macOS, from source and in a compiled `darwin-arm64` binary. CI runs the same test on Linux x64 from source, and the self-test compiled for linux-x64 and linux-arm64. Checked on 2026-10-28: the full compiled `linux-arm64` daemon answers `kitshn status` on the Oracle VPS, and on the VPS root (uid 0), with `KITSHN_LOCAL_SOCKET` set to the private socket of the daemon user, is refused until `kitshn local-users add root`, then answered. Since the client check, root needs no other setting there: the client reads the daemon user from `/run/user/<uid>/`.
- **K-702** The socket speaks JSON lines: requests with an id, answers with the same id, and events with no id. An error answer to a line without a valid id has the id `null`. The schema is TypeScript types with Effect Schema, in the workspace package `@kitshn/local` (`packages/local`). It is not on npm yet. Revisit when a provider outside this repo imports it (K-704). Providers import the types; the daemon checks each message against them. It answers a bad message with an error that names the problem. A line longer than 65,536 characters ends the connection. The requests are `status` (the machine id, the key fingerprint, the connection to kitshn, the tunnel service and the version), `rotate-key` (K-1705), `reconnect` (K-1706), `ask` (K-1710), `forward` (K-1714), `attester-set` (K-1751), `forget-token` (K-1762), and the provider requests `register`, `upsert`, `remove` and `command-result` (K-704 to K-707). `kitshn status` shows the answer of `status`. When the daemon does not run, each command says so.
- **K-703** The interface pushes events. A provider subscribes once with `register` (K-704), then gets each change of its grant tables (`grants`) and each command (`command`) as an event on that connection. Nothing polls.
- **K-704** `register` names the provider, its resource kinds (K-302), its commands and all its resources. It replaces what an earlier registration named, so a provider restart needs no cleanup. The answer to `register` names the machine (`machineName`, from kitshn on each signed connection; null before the first). The provider belongs to the connection that registered it, and only that connection sends `upsert`, `remove` and `command-result`. When the connection closes, the provider is offline, and its cards stay with the status "offline". Only the daemon user and root send these requests (K-701). A provider name has `a-z`, `0-9` and `-`, at most 32 characters, and is not `kitshn`, `site`, `repo`, `machine`, `page` or `file`. A kind id starts with the provider name and a dot. One machine has at most 8 providers and 500 provider cards, and one provider at most 20 kinds and 40 commands. The daemon and kitshn check these rules with the same code (`reportProblem` in `@kitshn/local`). The daemon keeps the last registration of each provider in `providers.json`, and reports all of them to kitshn on each connection and after each change, at most once a second. kitshn takes the report only on a signed connection (K-1704). A report that does not name a provider keeps that provider's cards. `kitshn provider` joins its stdin and stdout to the socket, line by line, with the socket search and the peer check of K-701, so a provider needs no socket code. The daemon and the bridge keep what the socket buffer cannot take and write it when the socket drains, so a long line arrives whole. "Forget provider" in the menu of an offline provider card removes every card of that provider on the machine, with its places and shares, as one revision with Undo (K-1502); it needs `control` on the machine, and kitshn refuses it while the daemon last reported the provider as running. `kitshn provider forget <name>`, as the daemon user or root, drops a provider that no connection holds, so the daemon no longer reports it. An undo brings the cards back offline; the provider's next registration brings its commands back. "Forget provider" also reaches the daemon: kitshn sends it now, or on the next signed connection, and the daemon drops the provider from `providers.json` unless a connection holds it. Until then, kitshn ignores the offline reports of that provider, so they bring no card back. A provider that registers again as running is back, with new cards. "Forget this card" needs no message: the daemon reports only the last registration, which no longer has the card.
- **K-705** `upsert` adds or replaces resources of the provider, and `remove` removes them by id. A resource has the provider's id, a kind, a name and a status, and can have a parent and a site. A card stacks with the card of its parent (K-508). A site is a name and a local port: it makes the card the live site `<name>.<zone>` of its machine (K-1104), so Access and the tunnel guard it as any card. The card gets that address only after the check of K-1111 found it free: until then, and while the check refuses it, the card has no address, so kitshn makes no Access application, DNS record or ingress rule for it, and a refused card shows the sticker "address in use" as soon as the check refuses it. The daemon reports a provider's sites before its cards, so a site can wait under an id of its own; it moves to the card that names it, and a card that kitshn made for it meanwhile goes. The owner can take such an address over (K-1623). The daemon and kitshn refuse a site name of kitshn itself (`pages`, `files`, `kit`, `www`, K-817), and the daemon refuses one that `sites.json` or another provider holds. kitshn keeps an address off the card when another card or a live site holds it, a folder site plan holds it (K-1123), or it sends visitors on to another card (K-1124), with the same checks as a deploy. A new card waits in the tray (K-509). When a provider's report no longer has a card, the card stays offline with its place and shares and no grants, and the card panel says since when. A report that has it again brings it back whole, so a provider that registers before its list is complete loses nothing. kitshn never forgets such a card by itself: the owner removes it with "Forget this card" in its menu, also while the provider runs, or with "Forget provider" (K-704), both with Undo. A card of an offline machine shows "offline", whatever its provider reported last (K-304). A change of a status, a fact or a sticker is no revision. A kind without levels has no cards; it holds desired state (K-709).
- **K-706** For each resource of a provider, the daemon pushes a grant table: each circle with its match mode (K-203), its rules (an email, a domain, an IP range, a device with its Access client id, a machine with its id and its Access client id, or everyone) and its passkey flag, with the provider's name of its level (K-713) and the earlier end date of the circle and the share (K-209), so the provider ends the sessions of a member at an end date by itself, also while kitshn is out of reach. The provider decides a level with no call, from the JWT that Access put on the request. The Access JWT carries the client id of a device or a machine in `common_name`, so the provider matches them without a call. A rule type that a reader does not know decodes as `{ unknown: <type> }` and never matches; in a circle with "all must match" it fails that grant. So a new rule type never breaks a table or widens access in an older provider. A pause closes every grant (K-1504, K-1618). A circle with "all must match" that names a machine that kitshn does not know gives no grant, because a dropped rule would widen it (K-006). kitshn sends the tables of each provider on each signed connection and after each change. The daemon saves the last tables and gives them to the provider in the answer to `register`, also while kitshn is out of reach. The provider saves the revocations that a lower level or an end date needs, runs them again until they work, and runs them after a restart (MM-1306).
- **K-707** A provider command is a job of the kind `provider` (K-612), so an offline machine gets it from its queue (K-613). A command names the kinds of the cards that it applies to; a command without kinds belongs to the machine card. The menu of a card and the palette list its commands (K-523), and a command with `confirm` asks first (K-1615). It needs `control` on the machine (K-614, K-1612). kitshn refuses a command that no provider of the machine has for that card. The daemon passes it to the provider as a `command` event with the provider's id of the card, and the row of a list for a row command (K-1625), and the provider answers with `command-result`. The daemon sends that result to kitshn as the job result. A job that arrives before its provider registers, as after a daemon restart, waits at most 60 seconds for it. Without the provider then, or without a result in 5 minutes, the job fails.
- **K-708** A provider publishes a page or a file (sections 10 and 11) with one `forward` request to `/agent/library` (K-1714), with the rights and the attested labels of that path. The forwarded body is at most 12 MiB each way (K-1714); a bigger file needs an agent key. A live site of a provider is the site of its card (K-705).
- **K-709** A resource kind can carry a desired state: a JSON value that kitshn stores and pushes to every machine with that provider. kitshn does not read the value. T3 Code uses it for shared settings and themes. Each value is at most 64 KB. A value can hold a shared part and one part per machine; kitshn pushes each machine only the shared part and its own part. A provider may send a JSON Schema of the value with `register` (K-704), so the map edits it with generic controls without knowing the provider. A kind with `state` holds desired state and has no cards. kitshn pushes each machine a `desired` event per kind, and the daemon gives the saved state in the answer to `register`. A provider sets the part of its machine, or the shared part, with `desired-set`; the map sets them with `PUT /api/desired/<kind>`, the shared part as the admin and a machine part with `control` on that machine. `GET /api/desired/<kind>` reads every part and the schema. The daemon and kitshn check a part with the same code (`desiredProblem`): the kind is one that the provider registered with `state`, and the part holds at most 64 KB. The provider gets kitshn's own answer to `desired-set`, also a refusal or a failed write, within 60 seconds; after that the daemon answers that kitshn did not answer. kitshn does not check a value against the kind's schema: the provider validates what it applies. History records each change without Undo. Removing a machine removes its part. Planned with settings sync (K-1613): the editor of the map.
- **K-710** A local round trip (request to answer) takes under 5 ms, and a change on the map reaches a provider in under 1 second when its machine is online.
- **K-711** The provider holds no Cloudflare credential. Only the daemon holds the machine token and the machine key (K-1702).
- **K-712** T3 Code side: the fork adds the interface in its own files, with one-line hooks in upstream files. It never breaks upstream code paths when the daemon is missing: then T3 Code runs as upstream.

- **K-717** Each `t3.app` card has the setting "Update channel": `nightly` (a build for each commit) or `daily` (one release a day). Every machine starts on `nightly`. The setting belongs to one card, not to the kind (K-709 holds values for all machines of a kind): kitshn stores it with the card and pushes it only to the provider on that machine. The card panel shows one control per setting, and `POST /api/cards/<id>/settings` changes it. - **K-718** An agent key is a device member (K-106) without the admin card. A key keeps its address `kit.<zone>/agent/<path>` (K-1714). Put it in a circle such as "Agents" and drag in the cards it may manage. It manages a card that one of its circles holds at the circle level `control` (or a `control` override), before the kind cuts the level down (K-206). With its service token on `kit.<zone>/agent` it sees only those cards, without their machine or group but with the newest deploy, the newest backup and the uptime of each, and its agent circles, with no members, and Everyone when it may publish; it moves those cards, but only between its agent circles at the level `control`, or out of every circle; and it runs jobs on a machine only when it manages the machine card, every card that runs on it and every card that the machine's own token opens (K-107, K-614), never by labels, checked again when a job goes out; a redeploy that it asked for goes out only while the key manages the card, the machine has the label `deploy` and runs the card; it reads the state and output of its own jobs, and the history names it by its member name. A dispatch deploys as a push of that branch. Both ways follow the repo gate (K-819). It never edits circles, members, stacks, levels, the pause or any admin setting. It removes no app and deletes no volume (K-909). Planned: after machine identity lands, it removes only the apps that it added. The owner gives a key two rights on its device member in an agent circle, and both are off by default: "may add apps" lets it allow a waiting repo (K-819) and publish a folder site (K-1123) and hand a card over to a new repo (K-1127), and "may publish" lets it publish a card of a repo that it allowed. The map shows them as "adds apps" and "publishes" stickers on the device in an agent circle. A public move takes a static site, Worker site, Compose app, page or file that the key added (K-1116) into the overlap of an agent circle of the key at `control` and the Everyone circle, with `POST kit.<zone>/agent/apply`, so the key keeps managing the card: it still redeploys it, takes it back and runs jobs on its machine. Everyone counts only while it is public, has no other member and matches "any". kitshn refuses a publish that leaves every agent circle of the key at `control`; when no such circle overlaps Everyone, the owner moves the Agents circle alone (K-504) so it overlaps Everyone, and its cards stay in place. A live site is never published. A move out of Everyone into the same other circles needs no "may publish", because it lowers access, but only for a card that the key added. `/agent/apply` checks every move by these rules; the older `POST kit.<zone>/agent/publish` is gone. This is the one exception to K-715: the owner chose the cards, the circles and the rights, so a move between them raises no access that the owner did not give. The map marks a device that has an agent circle and no admin card with an "agent" sticker.

## 8. Recipes and deploys

- **K-801** A recipe is `kitshn.config.ts` with `export default defineApp({...})`, or `export default defineApps({ <key>: {...}, ... })` for a repo with several apps (K-804). The value is one object literal. The `kitshn` npm package exports `defineApp`, `defineApps` and their types as a `.d.ts` with no imports, so an editor shows recipe mistakes: in `defineApps`, `needs.apps` takes only the keys of the same file, and `defineApp` takes none (K-820); it has no runtime dependencies, because its CLI is one bundled file. Until it is on the npm registry, an app does not need it: Actions runs `kitshn check` from the release. For editor types, install the `kitshn.tgz` asset of an `edge-<version>` release without saving it (`npm i --no-save <address>`). A later `npm i` removes it again, so an app keeps `kitshn.config.ts` out of its own `tsc` run.
- **K-802** Recipes do not compute. A lint rule in `kitshn check` refuses loops, conditions, function calls other than `defineApp` and `defineApps`, and imports other than `kitshn`. The lint rule is enough, because kitshn never runs repo code (K-803).
- **K-803** GitHub Actions reads the recipe without running it: `kitshn check` turns the literal object into JSON. kitshn checks the JSON with the same schema. kitshn never runs repo code. The reusable workflow is `.github/workflows/kitshn2-deploy.yml` in this repo. The deploy job takes the GitHub Environment `prod` only for the default branch, and `pr-<n>` for a pull request. Any other push or dispatch runs with no GitHub Environment, so per-branch Environment secrets are not supported; revisit that when an app needs them. kitshn skips a branch that the recipe does not deploy (K-807).
- **K-804** Kinds: a Compose app (`compose`), a static site (`static`), a Worker app (`worker`). A recipe has exactly one kind. A repo can have up to 10 apps, each with its own recipe, under a key: a lowercase letter, then up to 19 lowercase letters or digits. `defineApp` is the app with the key `app`. The app `app` keeps the card ids `app-<repo>-<repo id>-<environment>` and the default addresses of a repo with one app. Every other app has its key after the repo id (`app-<repo>-<repo id>-<key>-<environment>`) and in its default address (`<repo>-<key>[-<environment>].<zone>`). A card id over 56 characters ends in a hash of the key and environment instead, and kitshn refuses a deploy onto a card of another app of the repo. One workflow run deploys every app, each as its own deploy with its own result, in the order of K-820. Known limit: all apps of one run get the same `KITSHN_<NAME>` values (K-808). Revisit when two apps of one repo need different values under one name.

  ```ts
  import { defineApp } from "kitshn";

  export default defineApp({
    compose: { runsOn: ["docker", "server"] },
    deploy: [
      { on: "push", branch: "main", name: "prod", address: "riffle.example.com" },
      { on: "pull_request", name: "pr-{pr}", ephemeral: true, startsIn: "Owner" },
    ],
  });
  ```

- **K-805** A static site names a build command and an output folder. Actions builds it and uploads the files. Each upload of a bucket of files that Cloudflare refuses tries again after 5 s and 15 s, because the files are keyed by their hash; a last failure names the HTTP status and the start of the answer. kitshn deploys them as Workers static assets, with no Worker code, so their requests are free ([static assets billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)). A `_headers` file in the output folder sets response headers, such as content types and cache rules ([headers](https://developers.cloudflare.com/workers/static-assets/headers/)), and a `_redirects` file sets redirects ([redirects](https://developers.cloudflare.com/workers/static-assets/redirects/)): the CLI sends the text of each with the deploy instead of uploading it as a file, warns when it passes Cloudflare's limits, and kitshn passes it to Cloudflare, at most 100 KB each. A site whose build needs more than the deploy job offers (another runner, other tools, the full git history) builds in its own job of the same workflow run and uploads its output as an artifact; that job is also the place for a build that runs untrusted code, because it has no `id-token: write`, while the build command of the recipe runs in the deploy job, which can ask for the deploy token; the deploy workflow takes `artifact` and `artifact-path` for the app `app`, or `artifacts` as JSON by app key (`{"<key>": {"name": "<artifact>", "path": "<folder>"}}`, K-804), and puts each into the output folder of its app, and the recipe names no build. `artifact-path` must be the output folder of the recipe, inside the repo; the CLI refuses another folder. A closed pull request builds nothing and still removes its preview, so the build job skips the close and the deploy job runs after it unless it failed (the pattern is in the workflow's header).
- **K-806** A Worker app is described in the recipe only: the entry module, the compatibility date and flags, an optional build command and assets folder, KV binding names, Durable Object bindings to class names, crons and plain vars. The recipe has no field that names a place, so kitshn sets the script name, the addresses and the storage of each environment. Actions runs the build, then bundles the entry module into one ES module with a pinned esbuild that `npx` downloads in the deploy; the CLI fails when the bundle is larger than the Free plan limit of 3 MB after gzip, or does not export a class of the recipe. Known limit: each deploy downloads esbuild from npm. Revisit when that download fails a deploy, or when the kitshn release can ship esbuild. The assets folder follows K-805, with `_headers`, `_redirects` and the icon (K-1112), and the Worker reaches it through the binding `ASSETS`. Each environment gets its own KV namespace per binding, which stays with the card across deploys. A deploy makes a namespace again when Cloudflare no longer has it. kitshn declares the Durable Object classes of the recipe in the declarative `exports` of the upload, each with SQLite storage, and Cloudflare reconciles them with the classes that the script has, so kitshn keeps no migration state. A class that leaves the recipe fails the deploy at Cloudflare, because kitshn never declares a deletion, which deletes its data. Renames and transfers of classes are not supported. Only push environments run the crons; a preview runs none. The Free plan allows 5 crons per account, so in the storage step, before the upload, kitshn counts the crons of every other Worker of the account with a scheduled handler and refuses a deploy that passes 5. The schedules change after the upload, before the addresses and before the card shows the deploy as live; a failed change fails the deploy there. An existing Worker serves its new code from the upload on, because Cloudflare keeps schedules per script, not per version. D1, R2, queues, service bindings, Workflows and AI bindings are not supported yet. Nothing replaces `wrangler dev` yet: a pull request preview is a full environment with its own storage.
- **K-807** `deploy` maps triggers to environments as in KitSHn 1: the first matching entry wins. `startsIn` names the circle of a new environment, except for a repo that an agent key allowed (K-819). After that, the map decides (K-518). A `pull_request` entry is named `pr-{pr}`, and the number comes from the signed GitHub token, so a pull request reaches only its own preview. The token of a closed (merged) pull request names no number; then kitshn takes the request's number only to close a preview that the token's own head branch deployed. A push environment deploys only from the branch that first deployed it. A push environment of a branch other than the default one gets no GitHub Environment, so only repo secrets reach it (K-803). Each app of a repo has its own environments (K-804). An environment keeps its kind: kitshn refuses a deploy whose recipe kind differs from the kind of its card, and says to remove the app on the map first, because the removal and the teardown of a card follow its kind.
- **K-808** `needs.vars` and `needs.secrets` list names, next to `needs.apps` of K-820. Until they exist, the recipe schema refuses them. Values come from the kitshn store, per app and environment. A `KITSHN_<NAME>` GitHub variable or secret forwards into the store as `<NAME>` on each deploy and wins over the store. A deploy fails before any work when a needed name has no value, and it names each missing name. Every app of one workflow run gets the same values (K-804). A Worker app gets each `KITSHN_<NAME>` value of the run as the secret binding `<NAME>`; kitshn passes it to Cloudflare and stores none (K-806). A repo secret also reaches the previews of pull requests, as their code runs with it; a secret for production only goes in the GitHub Environment "prod".
- **K-809** The kitshn store encrypts secret values with AES-GCM under a Worker secret. The map shows names and "set" or "missing", never a value.
- **K-810** The workflow file is the same few lines for every app. It needs `permissions: id-token: write` and calls the kitshn action.
- **K-811** Deploy auth: Actions sends its GitHub OIDC token (issuer `https://token.actions.githubusercontent.com`). kitshn accepts a token whose `repository_owner_id` is on its list of owners. It refuses any other token. The list holds user accounts only; GitHub organizations are not on it for now.
- **K-812** A Compose deploy is a job (K-610). Actions sends the checkout, with `.git` and without a stored token, and the `KITSHN_*` params to R2 through the Worker, with its OIDC token. The daemon downloads both with its machine token, only while it runs that job. After the app comes up, the daemon keeps that build and its params on the machine as the last good build (K-718), and replaces it only with the next build that comes up. For a push environment it also keeps the build before it, and tags the image of each service of both builds as `kitshn-keep/<card>/<service>:<deploy id>`, for a rollback (K-821); it removes the tags of older builds and then only images that no tag holds. A preview keeps one build. It builds with Compose at the lowest CPU priority and starts the app with the variables of KitSHn 1 (`KITSHN_SOCKET_DIR`, `KITSHN_DEFAULT_SOCKET`, `KITSHN_ENVIRONMENT`, `KITSHN_DATA_DIR`, `KITSHN_LOG_DIR`, `KITSHN_PARAMS_FILE`, with the params quoted as KitSHn 1 quotes them, so Compose still reads a `$` in a value as a variable), so a KitSHn 1 `compose.yml` works unchanged, within the limits of K-818. The daemon takes the Compose files that Compose finds on its own (`compose.yml` and `compose.override.yml`), or the recipe's `file`, and passes them to Compose by name. KitSHn 1 deploy credentials (`KITSHN_SSH_KEY`, `KITSHN_VPS_HOST`) never reach the app. A machine runs one Compose job per app at a time. When the socket answers, the daemon exposes it under the address name (K-1104), so the tunnel, DNS and Access follow the live site path. The files are deleted from R2 when the job ends, and an R2 rule removes any that remain after a day.
- **K-813** The Actions step asks kitshn for the state of the deploy every few seconds until it ends, and prints the job output and the final address. It fails when the deploy fails. The daemon sends the output at the end of the job, not line by line; revisit when builds get long enough to need live logs.
- **K-814** The deploy ends with a route check: kitshn requests the address and records status and content type, as KitSHn 1 does.
- **K-815** `kitshn try` builds and runs a recipe on the machine of the developer with a temporary socket, as KitSHn 1 `try`. It touches no environment.
- **K-816** kitshn creates a GitHub deployment and its status for each environment of each app, with the address.
- **K-817** A `push` entry may list several addresses, at most 5 (each costs Cloudflare API calls in one deploy request, under the limit of K-406); a `pull_request` entry keeps one (K-901). Each address is the apex or one level below a zone of K-1111, so Universal SSL covers it. The first address under `KITSHN_ZONE` is the main one: it keeps the card address, the expose name (K-1104), the route check (K-814) and the deployment (K-816); a list without one is an error. Every other address serves the app: a Compose app gets its own ingress rule to the same socket and a DNS record on the zone of that address (each address of a Compose deploy gets its record at plan time, before the build, so no lookup during the build caches another answer such as an old wildcard; a deploy that came up keeps it until it expires, by when the live site holds it; a deploy that fails loses it again unless its site is live, and the record of a running deploy that the CLI gave up on stays until the machine reports or the deploy expires after an hour), a static site its own custom domain on that zone, and each address its own Access application and, for a live site, its own offline route. K-402, K-403 and K-410 hold per address: its Access application comes before its route, and removal runs in reverse. An address that leaves the list loses its route before its Access application. No address, also not the main one, is an admin host (`KITSHN_HOST`, and `KITSHN_OLD_HOST` during the move of K-1209) or a name that kitshn uses on its zone (`kit`, `pages`, `files`, `www`). An extra address is never the apex of `KITSHN_ZONE`; the apex of a further zone (K-1111), such as onion-climbers.com, may serve an app. kitshn takes over no record that it did not make (K-1404): a deploy with an address that already has an A, AAAA or CNAME record fails and names it. The MX and TXT records of a zone apex, for email, stay, because Cloudflare serves a CNAME at the apex next to them. kitshn keeps the card that made each of its records: a record of the same card does not count, so an address that comes back on its card before the old record went deploys again; a record of another card, also one that waits for removal, blocks until it is gone, and the error says so. A record from before kitshn kept the card counts as another card's. The data of a moved app: on the same machine the takeover of K-1404 copies the KitSHn 1 data; on another machine the owner stops the old app, copies the data folder, checks the copy, then deploys and moves the DNS record. An address that leaves the list, also the main one of a static site or a Worker app, sends its visitors on (K-1124). A Compose app keeps its main address, because its machine serves it under that name (K-1104).
- **K-818** A Compose app gets no more than its own folders, project and network. Each deploy or redeploy unpacks the source into a new folder that no running container mounts. There the daemon first parses each raw Compose file as YAML for `include` and `extends`, before Compose reads them; a file that is not one YAML mapping fails the deploy. `extends` needs an allowance also within one file. Then it reads `docker compose config --format json --no-interpolate`, which names the env and label files without reading them, checks those files, and only then reads the config once more with the params. Every Compose command of a deploy that reads Compose files gets them and the params file by name, so the params and the repo's `.env` add no Compose file; the clean-up after a failed takeover runs by project name in the app's folder, which holds no Compose file. The whole check runs before the KitSHn 1 takeover (K-1404), so a refused deploy leaves KitSHn 1 as it is. The recipe's `file` is a path inside the repo, also after symlinks; a missing file fails the deploy. Only a short list of Compose keys passes on its own (image, build, command, environment, env files, volumes, networks, healthcheck, restart, limits, `scale`, `profiles`, `extra_hosts` and a few more), and only with safe values: build contexts, additional build contexts, the Dockerfile, env and label files stay inside the new source folder after symlinks; bind mounts, secret and config files stay inside the app's source, data, log and sockets folders after symlinks, are no link inside those folders (setting `link:<path>`), and a link whose target is missing fails the deploy; and are not under another writable bind source of the app (setting `nested:<path>`), because Docker follows links at each container start; a built image and its tags are `<project>-<service>` with an optional `:<tag>`, and a container name is `<project>-<service>`; logging is `json-file` or `local`; a service joins networks without aliases or addresses; top-level volumes and networks are plain ones of the app's own project, and a network can be `internal`; no label starts with `com.docker.compose.`; `cache_from` names registry images only. Every other key or value, for example `privileged`, `cap_add`, `pid`, `network_mode`, `ports`, `volumes_from`, `provider`, `post_start`, `security_opt`, `include`, `network:kitshn-edge` or `bind:/var/run/docker.sock`, runs only when the owner names that repo and setting on the allow list of the machine in its panel, for example `owner/repo bind:/var/run/docker.sock`; an entry holds for every environment of the repo, previews too. The daemon builds and starts from the checked config itself, not from the repo's files. It builds while the old app still runs. Then it stops every container of the app (by its Compose label, orphans too), checks the bind and file paths once more and runs `up`, so no container of the app can swap a path between that check and `up`. A deploy that fails before `up` starts the old containers again and removes its new folder, so the old app runs on. A failure in `up` or later leaves the app down until a deploy or redeploy comes up. When the app answers, the daemon removes the source folders of earlier deploys. The deploy output names each refused setting. The configs hold the params, so they stay in folders that only the daemon user reads; the daemon keeps only the checked config and params of the last `up`, also of a failed one. A preview teardown (K-904) runs `down` with them, and also removes every volume with the app's project label. A removal (K-909) runs `down` with them and keeps the volumes. kitshn sends Compose jobs only to daemons that report the capability `compose-guard`. Known limits, to revisit when a second person deploys apps on a machine: apps on one machine share the BuildKit cache; a root container can leave setuid files or device nodes in its own folders on the host; kitshn sets no default CPU or memory limits; Compose gives each service its name as an alias on every network that it joins, so an app with `network:kitshn-edge` can take the traffic of a service of the same name in another app on that network; an image or container name `<project>-<service>` can match the same name of another project when the names have dashes (the project `app-foo-1-prod` with the service `2-prod-web` gives `app-foo-1-prod-2-prod-web`, also the name of the service `web` of the project `app-foo-1-prod-2-prod`), so one app can replace the image that the other built, or one of the two fails to start; the check of nested binds holds only for the app's own config, so a process outside the app that changes links in the app's folders, or a link inside the `subpath` of a named volume, is not checked; the link check reads the path as the Compose file writes it, so an outside path that the owner made a link into the app's folders is checked only at its real target and needs no allowance. Rootless Docker for the kitshn user is the next step against these limits. Since 2026-10-28 the VPS runs it: the CLI context of the `kitshn` user is `rootless`, so every `docker` call of the daemon goes there; the daemon has no code for it, and other machines keep system Docker. Root of a container is the daemon user on the host there, so a moved app gets its data folder owned by the daemon user. Since 2026-10-29 the `kitshn` user is no longer in the `docker` group, so the daemon cannot reach system Docker; dozzle, the last app there, is gone, and the Logs view (K-1801) replaces it.
- **K-819** A repo that kitshn has never deployed waits. The gate is per repo: one Allow or Block covers every app of the repo (K-804). Its first deploy step records it by its GitHub `repository_id`, and the step fails with "waits on the kitshn map". The toolbar shows the count of waiting repos that the owner can allow; a repo of a removed key or a repo that GitHub deleted does not count. The map panel lists each repo with "Allow" and "Block", and every repo also with "Forget". The panel of each card that the repo deployed shows "Deploys" with the same switch; the card matches by the repo id that kitshn stores with each deploy. "Allow" on a repo that waits after a push starts the workflow of that run again on the first pushed branch through the GitHub App (K-908) (K-1121), and the panel names that branch. Allow is a deploy permission, not an access share, so it works during the pause (K-1504) but starts nothing until Resume. Until a start succeeds, the panel keeps the branch with a "Start" button. After a pull request run, the next run deploys. "Block" cuts a repo off at once, also after a rename or a transfer, because the gate keys on the id: every deploy step checks it, the jobs and Compose deploys of the repo that have not finished fail, kitshn deletes their files in R2, the daemon gets no source of the repo, and agent keys cannot redeploy or build it (K-718). A build whose daemon already downloaded the source can still finish on the machine, and a static upload that already started can finish too; the card stays as it was. A blocked repo still tears down its previews and environments. A repo that finished a deploy before the gate existed counts as allowed; a teardown alone does not count. The gate covers deploys, not jobs: an agent key that manages a machine can still run jobs there (K-718). Only a member with control on the admin card (K-104) blocks or forgets. "Forget" stops what the repo has under way as Block does, deletes the gate row and writes a History revision, so the next deploy of the repo waits again. kitshn refuses Forget while the repo has cards on the map, so each card keeps its "Deploys" switch; the owner removes them with "Remove app" (K-909) first. kitshn also refuses Forget of a blocked repo, and of a repo that a removed agent key allowed, until GitHub reports it deleted (below), because a forgotten repo waits again and an agent key with "may add apps" could then allow it; the refusal says to unblock, take over or block it first, and the repo list hides Forget on such a row. With the GitHub App (K-908), the repo list asks GitHub whether each repo id still exists (`GET /repositories/<id>` with each installation) when it opens, at most once per repo per day and with at most 40 GitHub calls per check. The daily run does not ask, because its alarm already spends 40 of the 50 calls of a Free plan request (K-406). A repo is "deleted on GitHub" when every installation answers 404 for its id and one of them holds all repos of the repo's owner. Any other answer, a fault or no App leaves the mark as it is, and every answer counts as the check of that day, so one unknown repo never starves the others; a stored id that is not a GitHub id counts as unknown. Such a repo shows "deleted on GitHub" with "Forget" and "Block", in the repo list and on its cards, so a wrong mark stays recoverable; `GET kit.<zone>/agent/state` leaves it out, and an agent key cannot allow it. A deploy step or a build of the repo clears the mark. Known limit: a private repo that moved to an account without the App also reads as deleted, and an App with selected repos only never marks a repo as deleted. Revisit this when kitshn stores the owner id of each repo. It allows too, and so does an agent key with "may add apps" (K-718): it sends `{"state": "allowed"}` to `POST kit.<zone>/agent/repos/<repoId>`. A key allows only a waiting repo and not during the pause (K-1504); it never unblocks a blocked repo or changes an allowed one. Its Allow starts the waiting branch as the owner's Allow does, writes a History revision that names the key, and the repo stores the key, which the repo list shows. The owner can still Block. While the key that allowed a repo has no agent circle, for example after the owner removed the key, the repo counts as waiting for every deploy, static, Worker and Compose: the gate refuses, and the repo list shows it as waiting with "allowed by <name>, key removed". This lasts until the owner takes it over, blocks it, or gives the key an agent circle again. A teardown of such a repo always runs. "Take over" on such a repo is the owner's Allow: it clears the key, and the repo then follows the rules of an owner Allow. Block clears the key too. `GET kit.<zone>/agent/state` lists the waiting repos with their ids for a key with "may add apps". A key never writes allow entries: they are the owner's (K-818), and a new repo has none, so the daemon refuses every risky Compose setting of a repo that a key allowed. Known limit: the allow list keys on the repo name, so a new repo under a freed name, also one that an agent created, gets the entries of the old repo. Revisit this when the allow list keys on the repo id. Known limit: a Compose job that waits in the queue is not checked again when kitshn sends it to the machine. Known limit: after Take over, the recipe's `startsIn` places the new cards of the repo again (K-807). A Compose app of such a repo goes only to a machine where the key may run jobs (K-718). kitshn checks this at the plan and again at the start of the job; without such a machine, the step fails and says why. Static and Worker sites need no machine. A new card of such a repo starts in the first agent circle of the key at the level `control`, not in `startsIn` (K-807); without one, or during the pause, it waits in the tray. Planned (K-1730): a machine with the right "adds apps" allows a repo as a key does, and the repo then stores the machine in place of the key. This bends K-002: a new repo needs one click by the owner before its first deploy, because with OIDC (K-811) any repo of a trusted owner, also one that an agent created, could otherwise deploy code onto a machine.
- **K-820** An app names the keys of the other apps of its repo that it needs in `needs.apps` (K-804), next to `needs.vars` and `needs.secrets` of K-808, so one word says what an app needs. In one workflow run, `needs.apps` means: deploy after those apps, and do not deploy when one of them did not deploy. - **K-821** "Roll back…" on a deployed app card, in the card panel, its menu and the command palette, lists the last finished deploys of the card, newest first; the newest serves now. ## 9. Previews

- **K-901** A pull request environment gets one address, one level deep, so the free Universal SSL certificate covers it: `<repo>-pr-<n>.<zone>`, or `<repo>-<key>-pr-<n>.<zone>` for an app other than `app` (K-804). The free plan allows 100 Worker scripts per account; kitshn refuses a new preview at 90 and names the open previews. - **K-907** A preview starts in its `startsIn` circle, by default "Owner".
- **K-908** The kitshn GitHub App adds: preview teardown on close (K-904), deployment statuses (K-816) without a workflow token, builds that agent keys start (K-718, with the permission "Actions: write"), "Allow" that starts the refused push again (K-819), repo cards before the first deploy, and "New app" from the map, which creates a repo from a template. - **K-909** "Remove app" takes down an app environment that a deploy made: a card of the kind `site.static`, `site.worker` or `site.compose` with a deploy that names its repo id (K-819), or with a finished deploy from before the repo id. Only a member with control on the admin card (K-104) removes an app. The card panel and the command palette show "Remove app" only on such a card, with no confirm. Both call `DELETE kit.<zone>/api/apps/<card>`, which runs one service with the same check, so agent keys can reach it later. A removal lowers access, so it also works during the pause (K-1504). It reuses the teardown of K-904. For a static site, kitshn takes off the custom domain, confirms it, and deletes the Worker script; then the card goes. For a Worker app and a folder site (K-1123) that no repo took over (K-1127), kitshn takes off its custom domains and confirms it, turns off its crons, and keeps the script with its Durable Objects and its KV namespaces, as a Compose app keeps its volumes; `workers.dev` stays off, so nothing reaches the script. The label of "Remove app" says what goes and what stays for each kind (K-523). The admin card lists the kept scripts and KV namespaces of removed apps as "Orphaned Worker storage", each removed card with one "Delete" that names what goes. A delete is a separate step. kitshn refuses it while a deploy of the card runs, and refuses a deploy or an Undo of the card while the delete runs. History records what went, also when a part failed; undo never brings deleted data back. For a Compose app, the card goes, and a `compose-down` job with `removeData: false` stops the containers. That job never expires: it waits for the machine. When the machine drops or renews its connection while it has the job, or kitshn restarts, the job goes out again, because its result may never come and a stop can run twice without harm. A newer deploy or redeploy of the app replaces a stop that waits, or one that would go out again, so a stop never stops a newer deploy. Until the job ends, the address still answers; its Access application then lets in only the people of the Owner circle, with no Bypass and no other circle, also during the pause. When the machine stops the app, the tunnel route, the DNS record and the Access application go in the order of K-410. A removal never deletes volumes or the last good build (K-812). It writes one History revision, "Removed the app <name>". Undo of that revision (K-1502) restores the card in the same place on the map, with its share settings and its stack; the card lands in the circles that cover that place now. The undo follows K-1506: it works only while the removal is the newest revision of the caller and no later revision touched the card or its circles. During the pause, kitshn refuses an undo that gives the card a share again, because the pause refuses every change that raises access; an undo of a card that waited in the tray restores the card and starts nothing until Resume. The undo starts the app again. While the machine runs the `compose-down` of a Compose app, kitshn refuses the undo: "The machine is stopping <app> now; undo after it finishes". Otherwise the undo cancels a `compose-down` that still waits, and the Compose app starts its last good build with `compose-redeploy` on its machine; the daemon runs one job per app at a time, so a stop under way ends first. The undo always starts the app again, also when its stop never ran, so the app then restarts for a short time. The restored card drops the old live site row of the app, and the next report of the machine makes it again, to be checked (K-1104); a new card of a deploy does the same. During the pause, the undo starts nothing and its note says that kitshn did not start the app, although the app can still run when its stop never ran; it then stays without its route until the machine reports its sites again. The undo of a preview whose pull request closed leaves the preview teardown of K-904 alone. A static site builds again on the branch of its environment through the GitHub App (K-908), as an agent build does (K-718); that run deploys every app of the repo again (K-804). A Worker app gets its custom domains back on its kept script once the Access applications of its addresses exist again, with its data as it was, and the crons of its last deploy. A static preview (`pr-<n>`) comes back on the next push to its pull request. A preview whose pull request closed does not come back. The Access application, the tunnel route and the DNS record come back through the normal sync of the restored card. The undo result names each app that it did not start, and why: the pause, the repo gate (K-819), a closed pull request, a machine without the label `deploy` or without a daemon that redeploys, no GitHub App, or no finished deploy. The repo stays in the repo list with the same gate state, also when it has no app left. A later deploy of the repo makes the card again through the normal deploy path (K-807); the undo of the removal then no longer fits, and kitshn refuses it. The daemon reports the volumes of kitshn apps (a Compose project with an app folder of the daemon) that no running container uses. The machine card lists the ones whose app has no card as "Orphaned volumes", each with its own "Delete". A delete is a separate step. History records it when the daemon reports that the delete succeeded, and undo never brings a deleted volume back. kitshn takes the project of the volume from the daemon's report and checks again, before the job goes out, that the app still has no card. The daemon deletes a volume only while it still reports it as idle for that project. An agent key never deletes a volume (K-718). Known limit: a removal leaves the app's data folder and its folder under `apps/` (with the last good build) on the machine, and "Delete" of a volume does not remove them; only a preview teardown (K-904) does. Revisit this when the disk of a machine fills with removed apps.

## 10. Artifacts library

- **K-1001** Every HTML page from T3 threads on every machine goes into one library in R2. The provider sends each new `html_render` page with `publishPage` (K-708), with its thread title, machine and time.
- **K-1002** A new page is private: it sits in the tray (K-509), unless the owner drops it on the map (K-1101).
- **K-1003** The Worker serves a page at `pages.<zone>/<name>` (K-1120), or at `pages.<zone>/<id>` for a page from before names, with the sandbox of the T3 render route (no same-origin scripts). Only the kitshn admin host may frame a page or a file (`frame-ancestors`), for the previews of K-520. The id is random, 16 characters or more, and the id address of a page with a name sends its visitors to the name.
- **K-1004** The Worker checks shares for each page request (K-404). A page in "Everyone" opens with no login. Other pages need a login through an Access application on `pages.<zone>/login`, which sends the visitor back. A second application on `pages.<zone>/login/passkey` adds the passkey check, for circles with "needs passkey" (K-103). Files use the same two paths on `files.<zone>`. Checked on 2026-10-27: a service token on `/login` gets the `CF_Authorization` cookie with `Path=/`, and a plain login cookie does not pass `/login/passkey`. Both applications write that one cookie, and Cloudflare advises against relying on it. So each login path checks the token that Access sends with it (`Cf-Access-Jwt-Assertion`) against its own application, and the Worker keeps it in its own cookie on `/` (`__Host-kitshn-login-token`, `__Host-kitshn-passkey-token`) for as long as the token lives. A cookie name never sets the level: the audience of the token does. A logout at the Access logout URL does not end these cookies; "Sign out everywhere" (K-110) and the loop guard do. A login path whose token does not prove that step answers with the reason at once. Each login path marks its return in a 60-second cookie on the item's path; when the item still cannot use the login after that step, the Worker answers with the reason and what it saw in each token instead of a second round, so a login never loops. Only people who can open an item may log in, so a stranger cannot take a Zero Trust seat (K-111). The login applications get their own copies of the people rules of every circle with an active page, file or admin share; Access applications of cards keep the people policy. `/login` gets a copy without the passkey check for each such circle, because that step comes first. `/login/passkey` gets a copy with the passkey check for each such circle with "needs passkey". A circle with "everyone" adds nothing, because its items open without a login. An "all must match" circle adds its people rules as they are, because its require rules let in only the circle. Ended shares and circles add nothing, and during a pause (K-1504) only the Owner circle stays. The `/login` applications also always get the machines policy of the bootstrap; the Worker removes every other policy. It then deletes the policies "kitshn any login" and "kitshn any login (passkey)" of older bootstraps when no application uses them. A policy goes on a login application only after Cloudflare holds its current body, so a new passkey check is never skipped. While the login applications hold a copy, the Access sync neither changes nor deletes it until the login step lets go of it; after a login step that failed part way, both the earlier and the new copies count as held. So a failing login step never holds back a policy of a card (K-409). The first run after a deploy fails closed: until the next alarm adds the circle policies, no person can log in to pages and files. When someone deletes a login policy in the dashboard, its old id stays until the daily compare, so login updates can fail until then. A failed write shows as an Access warning on the map and waits for the daily retry; the daily compare (K-408) repairs the applications. Milestone 3 tests it.
- **K-1005** The Library view lists all pages with a search by title, thread and machine, and a preview. It reads the index in the Durable Object, not R2.
- **K-1006** Deleting a thread does not delete its library page. "Delete page for good" (or file) in the library removes it from R2 and the map at once, without a confirm. Undo cannot bring it back, so the label says so; History records it.
- **K-1007** An MCP App page is not shared, because its buttons need its live MCP server. The library keeps it private and says why.
- **K-1008** An import adds all past pages of each machine once. Each imported page is private, as a new page (K-1002). Work pages (QCDI, Upsolver, SDE) are no exception. On 2026-10-27 there are 46 pages, about 14 MB: 41 on the Mac, 5 on the VPS, 0 on the Oracle VPS. Pages on Windows are not counted, and wait for the Windows daemon (K-601). New pages arrive at about 20 per week.

## 11. Files and sites

- **K-1101** "Upload" on the map, and `kitshn publish` for agent keys (K-1116), put a file into R2 and a card into the tray. A file is at most 100 MB. A file dropped from the computer onto the map lands where it was dropped instead, in one revision, so it gets the shares of the circles there at once; an `.html` file becomes a page. A drop into a public circle asks first (K-210), and one Undo takes back the whole drop (K-503). A dropped folder becomes a folder site (K-1129).
- **K-1102** The Worker serves files at `files.<zone>/<name>/<file name>` (K-1120), or at `files.<zone>/<id>/<file name>` for a file from before names, with the checks of K-1004.
- **K-1103** Public sites (for example tick3d and the resume) are static sites (K-805) in the Everyone circle.
- **K-1104** A live site is a local server of a machine, shared through the tunnel of the machine. `kitshn expose <socket or port> --name <name>` or `kitshn_expose` adds it, and `kitshn unexpose <name>` removes it. kitshn makes its card, its DNS record and its ingress only when nothing else uses the address, and its DNS record and ingress only after its Access application exists. The one exception is the record of a planned Compose deploy (K-817): it points at a tunnel without ingress for the address, so it exposes nothing until the site is live. `kitshn_expose` is the agent tool of milestone 5 (K-714). Its address is `<name>.<zone>`. It is live only: when the machine is off, the site is off. kitshn keeps no copy. `kitshn expose` also takes `localhost:5173`, `http://127.0.0.1:5173/` and the other forms of K-1131, `--time 30m|1h|4h|1d` gives the new card that end time (K-212), and the end runs as the machine; `--new` refuses a name that the machine shares already. `--ends-at <ms>` sets the end as a time, as the site wizard sends it (K-1131).
- **K-1105** A live site of a dev server gets the `Host` header `localhost` toward its origin, because Vite and similar servers refuse other hosts.
- **K-1106** When the origin of a live site or of a Compose app is down, visitors who pass Access get the kitshn offline page:
  - It uses the kitshn look (K-517), a short playful message, the site name, the machine name, the time the site was last seen, and "It comes back when <machine> is on."
  - It has one button, "Knock again", which loads the address again. It has no continuous animation and no automatic reload.
  - The response is status 503 with `Retry-After: 60` and `Cache-Control: no-store`.
  - The Worker serves it from its own static assets, with no call to the machine.
- **K-1107** kitshn detects a down origin in two ways, and acts on either:
  - The machine is off: its daemon socket closes, or misses pings for 30 seconds. kitshn checks the pings on each daemon sample and at least every 2 minutes, so a silent machine counts as offline after 30 seconds to 2.5 minutes (K-1302).
  - The machine is on, but the local server is off: the daemon tries the socket or port of each exposed site every 10 seconds, on the machine only, and reports a change.
- **K-1108** While an origin is down, kitshn adds a Worker route for the site address to the kitshn Worker. When the origin is back, it removes the route. So visits to a healthy site never run the Worker and cost no Worker request. Custom error rules would do this with no Worker, but the free plan has none ([Custom Errors](https://developers.cloudflare.com/rules/custom-errors/)).
- **K-1109** While the route exists, the Worker first passes the request to the origin. It shows the offline page only when the answer is status 502 or 530, or a Cloudflare 1033 error. So a site that comes back before kitshn removes the route works at once. Checked on 2026-10-27: the offline route was still on the hostname, and the restarted origin answered 200 through the Worker. So the fetch did not run the Worker again.
- **K-1110** The Worker reads the site name and the last seen time from the Durable Object, and keeps them for 60 seconds in the Cache API.
- **K-1111** Domains: kitshn publishes only on zones that the owner adds to it. Each address must be in one of them. The zone of `KITSHN_HOST` is the kitshn zone; the bootstrap adds further zones with `KITSHN_ZONES` (a comma-separated list), checks that the API token reads DNS on each, and keeps the list on a later run without it. Only the extra addresses of K-817 use the further zones. kitshn finds the zone of an address by its name, the longest zone first, and refuses an address outside every zone. A broken `KITSHN_ZONES` leaves only the kitshn zone: its addresses keep working, and the others fail (K-006).
- **K-1112** A static site deploy, and a Worker app deploy with an assets folder, takes the site icon from the built files, in this order: each `<link rel="icon">` of `/index.html`, then `/favicon.ico`, then each icon of the web manifest that `/index.html` links. The first file that exists, is an image and fits the limit of K-1113 wins. The `kitshn deploy` step picks it, because only Actions has the bytes; the Worker gets only the hashes of the files (K-805). The deploy log names the icon and says why each earlier file did not win. A link to another host does not count. Known limit: kitshn ignores `<base href>`. Revisit this when such a site shows the wrong icon.
- **K-1113** kitshn keeps one icon for each static site, Worker app, Compose app, live site, page and file card in the Durable Object, and writes it only when its bytes change (K-1302). An icon is at most 100 KB and one of PNG, ICO, GIF, JPEG, WebP or SVG, by its first bytes, not by its name. The Worker checks this again and refuses the deploy step otherwise. A deploy without an icon removes the stored icon; a deploy step from an older CLI, which sends no icon field, keeps it. The Worker serves the icon at `kit.<zone>/api/icons/<card id>` only to a visitor who opens the map, by the same check as the map (K-104, K-208); every other visitor gets 403, also for a card that does not exist. The answer has a sandbox content security policy, so an SVG runs no script on the admin host. The icon of a removed card goes at the next daily run (K-1503), so a quick Undo keeps it.
- **K-1114** The daemon reads the icon of each Compose app and live site through the target of that site only: its Unix socket or its port on localhost. A socket target must be the socket file itself; a link counts as no socket, for the site check of K-1107 too. It uses the order of K-1112 with `/` as the entry page and the limits of K-1113. Each read is one GET with a 2-second timeout and at most 256 KB; a redirect or an answer other than 200 counts as no file, and one site gets at most 8 reads. The daemon reads a site that is up when the connection starts, when it comes up again (at most once a minute) and once an hour, at most 3 sites in each site check of 10 seconds, so a machine with many apps does not stall. It sends the icon, or null for none, in an `icon` message when it changed, and again after an hour. The Durable Object takes the icon only for a site that this machine reports, checks it again, and changes the stored icon of a site at most once an hour, so a daemon cannot use up the rows written of K-1302. A site that comes up within a minute of its last read gets its read after that minute. kitshn takes no icon from a connection on the token alone: the daemon sends it, and the Durable Object drops it (K-1708). A site that is down keeps its icon.
- **K-1115** An upload of a page or a file (K-1101) gives its card an icon. For a page, the Worker reads the first 256 KB of the upload and looks at its first 64 `<link>` tags, outside `<!-- -->` comments; a `>` inside a quoted value does not end a tag. The first `<link rel="icon">` whose href is a `data:` URL counts, as base64 or as text, after the references `&quot;`, `&#39;`, `&lt;`, `&gt;` and `&amp;`; when it does not decode, the page has no icon. A page is one file, so a link to a path counts as no icon. A file of at most 100 KB that is an image of K-1113 is its own icon. The Worker reads only these bytes, so a large file costs no extra CPU. It finds the icon before it writes to R2, and it deletes the object again when the card cannot be written, so no object stays without a card. Other pages and files show their kind icon. Known limit: other character references in an href stay as they are.
- **K-1116** An agent key publishes a page or a file with `kitshn publish <file> [--name <name>] [--address <name>] [--circle <circle>] [--public]`, which sends it with the key's service token to `POST kit.<zone>/agent/library`. It runs the same upload as "Upload" and a drop (K-1101), with its limits: one file of at most 100 MB, and a file whose name ends in `.html` becomes a page, and any other file, also `.htm`, stays a file. Its title is the file name without `.html`, or `X-Kitshn-Title`. The CLI sends the content type by the extension, so an image, a PDF, a text, an audio or a video file opens in the browser. Without `--circle`, the card waits in the tray, private. With `--circle`, it lands inside exactly that circle, which must be an agent circle of the key at `control` (K-718), by id or name, clear of the cards there. With `--public`, it lands in the overlap of that circle, or the first agent circle of the key, and Everyone, which needs "may publish" (K-718). kitshn refuses anything else before it writes to R2. It decides the spot again after the write, in the same transaction that makes the card, with the pause (K-1504) and K-105, because the rights and the circles can change while R2 takes the bytes; a refusal then deletes the bytes. History names the key. A folder becomes a static site (K-1123). Known limit: kitshn has no MCP tool for this; the T3 Code provider tool of K-708 comes from the T3 Code side. With `--json`, `kitshn publish` and `kitshn address` print exactly one JSON object on stdout, `{address, card, kind, updated, revision?}` with `kind` one of `page`, `file` and `folder`, or `{"error": <reason>}` with exit code 1, and send every other line to stderr; the routes answer `card` (and the address routes `kind`) for that.
- **K-1117** A second `kitshn publish` of the same file name by the same key updates its card instead of making a new one: the card keeps its id, address, place, circles and stack, and gets the new bytes and their icon (K-1115). Only that key updates it by name, and only while it controls the card (K-718), as for a move, or while the card has waited in the tray since this key published it. The first move or share of the card by anyone, or a restore by the owner, ends that tray right for good, so a card that the owner puts back in the tray is out of the key's reach. kitshn checks the right again in the transaction that makes the new bytes current; a refusal then drops the written bytes and the previous version, because the slot of the previous version held them. An update refuses `--circle`, `--public` and `--address`, because those apply only to a first publish; a move goes through `/agent/apply`. R2 keeps two slots of each item, and the database names the one that serves. An update writes the other slot, which held the previous version, and one transaction then makes it current, so a failed upload leaves the served bytes as they were. "Restore previous version" in the card panel, the card menu and the palette switches the slot and copies nothing, so a second restore switches back; the owner restores any page or file, an agent key what it may update (`POST kit.<zone>/agent/library/<id>/previous`). kitshn runs one update, restore or delete of an item at a time, and refuses a second one with 409 until the first ends. History records each update and restore. An update and a restore change no share, so they have no Undo of their own; "Delete page for good" (K-1006) removes both versions.
- **K-1118** `GET kit.<zone>/public/cards.json` lists the app cards that anyone may open now and that are up: the kinds `site.static`, `site.worker` and `site.compose`, with a finished deploy of a push environment (no `pr-<n>`), a status other than offline, stopped or failed, and a share in a circle with "everyone" and the match "any" that gives access now. A circle or a share that has ended gives none, and during a lockdown (K-1504) the list is empty. Each entry has the card name, its main address (K-817), its kind, and its icon (K-1113) as a `data:` URL or null. Only this path has a Bypass Access application. It answers any origin (`Access-Control-Allow-Origin: *`), because the data is public and the request carries no credentials. The Worker keeps the answer in the Cache API for 5 minutes, and a fault for 30 seconds, so a change shows within 5 minutes. Browsers get `Cache-Control: no-store`, because the Browser Cache TTL of the zone raises every lower `max-age` to its own value; it leaves `no-store` as it is. The path also answers `HEAD`. The kitshn site reads it for its list of live apps. Planned: a public circle can be "unlisted", and its cards then stay out of this list; until then, every public app card is listed. Known limit: icons are inline, so the answer grows with each card; revisit when it passes 500 KB.
- **K-1120** A page or a file has an address name: `pages.<zone>/<name>` and `files.<zone>/<name>/<file name>`. A name has 3 to 63 characters from a to z, 0 to 9 and inner hyphens; `login` and names in the shape of an id are kitshn's own. An upload takes the name that `kitshn publish --address` or `X-Kitshn-Address` gives, and refuses a taken one. With no name, kitshn picks a random readable one, such as `calm-otter-42`; it comes from no part of the file, its name or its content, so the address tells nothing about the item. Pages and files from before names keep their id address until someone sets a name. "Set address…" in the card menu and the palette, the "Name" field of the card panel, `kitshn address <card> <name>` (the card by its id or a name of its address) and `POST kit.<zone>/api/cards/<id>/address` with `{"address": <name>}` give a page or a file a new name; an agent key calls `POST kit.<zone>/agent/cards/<id>/address` for a card that it may update (K-1117), and a later MCP tool calls the same route. An old name stays with the item (K-1122): it answers with a 302 to the current address, after the checks of K-1004, so a visitor without access learns no new name, and no other item can take it. A new name that is the current one changes nothing and writes no revision. An agent key gets one answer for a card that does not exist and for a card that it may not change, so it learns no names. The change is a revision of its own, so Undo and the per-item undo move the card back (K-1506, K-1507). The address of a card that a repo deploys comes from its `kitshn.config.ts`; its panel says so, and the route refuses it. Known limit: a readable name lets a stranger guess that a private page exists, because the Worker answers an unknown visitor of an existing page with the login, not a 404; the login must stay reachable for a member who is not logged in yet, and the Worker cannot tell that member from a stranger before the login. The page stays closed. Revisit this when a name itself is a secret.
- **K-1122** An item keeps its 5 newest old names. A new name past that frees the oldest one, which then answers 404 and which any item may take. The delete of the item frees all its names. An Undo to a freed name that another item took since then fails with "taken". The limit keeps an agent key that renames in a loop from holding many names.
- **K-1123** An agent key publishes a folder as a static site with no repo: `kitshn publish <folder> [--name <name>] [--address <name>] [--zone <zone>] [--circle <circle>] [--public]`. The CLI runs the steps of a repo deploy (K-805) against `kit.<zone>/agent/sites/plan`, `…/assets` and `…/finish`: it uploads the files straight to Cloudflare, with `_headers` and `_redirects` and the icon of K-1112. The site lives at `<name>.<zone>`, on any zone of K-1111 (the kitshn zone without `--zone`), with the checks of K-817 and the name rules of K-1120; without `--address`, kitshn picks a random readable name. The first publish needs "may add apps" (K-718), because it makes a Worker script, a hostname and an Access application, and it lands as K-1116 says: the tray, an agent circle of the key, or with "may publish" the overlap with Everyone. kitshn decides the spot again when the files arrive, with the pause (K-1504) and K-105. The same folder name from the same key deploys the same card again, under the rule of K-1117 for updates; `--circle`, `--public`, `--address` and `--zone` apply only to a first publish. Its previous versions are the versions of its script, as for a repo deploy (K-820). "Remove app" keeps its script, as for a Worker app, because no repo can build the site again; Undo puts its address back (K-909). A folder site counts while its card exists or a plan of it waits for its files; a plan expires after the deploy time (K-805). A plan holds its address and its folder name from the start: another plan or a repo deploy cannot take that address, a second plan of the same new folder answers 409, and the files' step checks "may add apps" and the address again before it makes the card. "Remove app" ends the plans that wait, so a removed site counts for nothing, and a later publish of the folder is a first publish, with "may add apps" and the landing rules of K-1116; Undo of the removal brings the site back as long as no new publish of the folder replaced it and no other card took its address; otherwise it fails with "taken" or names the new publish (K-909). The delete of its kept script frees the folder name for good. A folder site has no workflow run, so it offers "Roll back…" but not "Roll back this run…" (K-821). Named limits: a key has at most 10 folder sites (`FOLDER_SITES_PER_KEY`), and kitshn makes no new one when the account has 90 Worker scripts (`SCRIPT_LIMIT`, K-903), because the Free plan stops at 100. Revisit them when one agent needs more sites or the account moves to the paid plan. `kitshn address <folder> <name>`, the "Name" field of its card panel and the address routes of K-1120 move a folder site to `<name>.<zone>` on the zone of its address, and its old address sends visitors on (K-1124). A move back to one of its old addresses takes that address off the redirect Worker first. History records the move only when Cloudflare took it; a failed move puts the card and its old addresses back. Known limit: the move has no Undo; a move back does the same. Revisit when a site needs the Undo of K-1506. The owner uploads a folder from the map as a folder site too (K-1129).
- **K-1124** An old address of a site card, of any kind, sends its visitors on with a 302 to the card's main address, with the path and the query. One Worker, `kitshn-redirects`, serves every old address; kitshn uploads it again with a map of old to main address when the map changes. An old address keeps an Access application with the policies of its card (K-401), so only who may open the card learns where it went, and a public card gets a Bypass. Its custom domain comes after that application (K-402); the old address of a Compose app first loses its route and its DNS record (K-410). An address that a static site or a Worker app serves again leaves the redirect Worker first; one of a Compose app leaves it in the next alarm, and its route and DNS record follow. A card keeps its 5 newest old addresses (K-1122), and another card cannot take one of them until it goes free. "Remove app" takes the card's old addresses off with it: each custom domain leaves the redirect Worker before its Access application goes, which keeps only the Owner circle in between (K-410, K-909). Undo brings them back, and fails with "taken" when another card took one of them meanwhile. The old addresses of a card that cannot come back (its kept script deleted, or the card forgotten) go free. A step that waits (an Access application, a DNS record, the budget, a failed upload) tries again after five minutes, as K-410 does, and a new map runs at once. The alarm does this work, not the deploy, so a deploy stays inside its subrequests (K-406). Known limit: Cloudflare caps the custom domains of an account and a zone; with 5 old addresses per card that is far off. Revisit when a zone nears the cap.
- **K-1127** "Make it a repo": `kitshn repo <card> [<folder|file>] --repo <owner/name>` makes a new private GitHub repo of a page or a folder site with the user's own `gh` login, so the kitshn App needs no right to make repos, and the first deploy comes from the user's push, never from the App (section 17). The CLI runs with an agent key that may change the card (K-1117, K-1123) and has "may add apps" (K-718). It makes the empty repo first, reads its GitHub ids, and asks `POST kit.<zone>/agent/cards/<card>/handover` with `{"repo", "repoId", "ownerId"}`; then it writes the files under `site/`, a `kitshn.config.ts` with the card's address, the deploy workflow of "Add a site", a README with the deploy badge of K-1119 and the repo copy of the kitshn skill (K-618), and pushes. A page gets its bytes from `GET kit.<zone>/agent/library/<id>/content` when no file is named; a folder site needs its folder, because kitshn cannot read its files back. A file is no site and cannot become a repo. The CLI refuses a repo that exists. A handover lasts an hour and holds the address. - **K-1505** A move joins the revision of the move or drop that started it. A move is a card that goes from one point to another, or a circle whose place alone changes. A drop is a card that comes onto the map, from the tray or by an upload, or a new circle. A move joins the newest revision when that revision is a drop or a move of the same cards or circles (or more), by the same actor, and its last move or drop is at most 2 minutes old. The revision then keeps the first `before` and takes the last `after` of each item, and History shows one entry with the time of the last move. When a move changes a share, the summary is the net summary of the whole revision, because History is the record of who gave access. A move that changes no share keeps the first summary and adds "and moved it" once. The Undo of the toast of a later move (K-503) then takes back the whole revision. The commit on the server does this, so the map, `/api/apply` and agent tools behave the same. Two minutes covers the nudges after a drop; a later rearrangement gets its own entry. An Organize (K-532) is a revision of its own: it joins no revision, and no move joins it. Known limit: any other revision in between, also one by another actor or by kitshn, starts a new entry. Revisit this when drops and their moves split on a busy map.
- **K-1506** Undo reverses the caller's own newest revision that changes something, as a whole, and nothing else. An undo and the revision that it undid no longer count, so the next Undo reverses the change before them. The rule is per actor because other actors write often: in a day of the live map, about half of the revisions came from devices, deploys and live site reports, so "the newest revision of anyone" would turn Undo off at random. kitshn refuses an Undo of an older revision, of a revision of someone else, of a whole undo, and of a revision that is undone already. A per-item undo (K-1507) is a normal revision, so Undo can reverse it. kitshn also refuses the undo, and names the later revision, when a later revision by anyone depends on the same things: both touch the same card, or one of them changes a circle that a card of the other is or was inside, also inside a shape of the circle that no longer exists. A revision touches a card when it changes the card's place, stack, share settings or address (K-1120), or makes, removes or forgets the card. kitshn forgets a card when a live site stops, a preview closes, a machine goes or a page or file is deleted; the revision of that deletion marks the card, also one that waited in the tray, so an older undo never touches a new card with the same id. Such a revision records an action and has nothing to undo. A revision changes a circle when it changes the circle in any field or a share setting of it. This rule keeps an undo from giving access that a later change made possible, such as a card that entered a circle after a member left it. Undo applies the plain inverse of the revision. The History view shows Undo only on the caller's own newest revision (K-1508). Known limit: a later revocation of the same member through another circle does not block the undo, so the undo can give that member access again through the circle that the revision changed. Revisit this when a circle shares members with another circle often. Known limit: revisions from before the forget marks do not mark the cards that they deleted, so an older undo can still meet a new card of the same id. This ends when those revisions age out (K-1503).
- **K-1507** "Undo the last change" of one card or circle undoes only that item's part of the caller's own newest revision that changed the item: `POST kit.<zone>/api/undo-item` with `{"item": {"kind": "card" | "circle", "id": <id>}}`, or the WebSocket message `undoItem`. A card's part is its place, its share settings, its app, its address (K-1120) and its stack membership. A circle's part is the circle and its share settings, and for a drag by its head (K-504) the cards that sat inside it before the drag and moved with it. The rules of K-1506 hold, with the item's part in place of the revision. kitshn refuses the per-item undo when the rest of the revision depends on the item's part, for example a circle that became public while the card left it: "undo the whole change instead". The undo is a revision of its own, "Undo #<n> for <item>: …", so a second call reverses the first. Only a member with control on the admin card (K-104) calls it, as Undo. Agent keys have no undo (K-718). The context menu of a card and of a circle and the command palette call it as "Undo last change to this card" or "… circle" (K-523). Before it offers the entry, the client asks `GET kit.<zone>/api/undo-item?kind=card|circle&id=<id>`, which answers `{"allowed": true}` or `{"allowed": false, "reason": …}` by the same rule over the whole History and every check that the undo itself runs, so the menu and the undo agree. The one exception is the stop of a removed Compose app that a machine runs now (K-909): it depends on live jobs, so the menu can offer the undo and the undo then refuses, with the reason in its toast. The menu asks once when it opens for a card or a circle, and again when a new revision arrives while it is open. Until the answer comes, the entry is disabled with the tooltip "Checking whether this can be undone", and after 150 ms its label says "checking…"; a quicker answer shows at once. A refused undo then shows disabled with the reason, and an answer for a closed menu or another item is dropped. The palette asks once when it opens, only for the selected card or circle, and offers no per-item undo for other items.
- **K-1508** History groups the revisions by day (today, yesterday, older) and then by runs of one actor, newest first. The actor heads each group once, and each row starts with the verb, from the summary alone, for example "shared tick3d with Everyone at view" or "changed the level of riffle in Her from view to use". A row of kitshn names its reason, such as an expiry, next to its time. A summary of a shape that the rules do not know stays as it is, so a row never adds a fact. Filters: the kind of change (cards, shares, circles, stacks, apps, pause, actions; a share setting that changes or ends counts as a share, also when it takes its card out of a stack), the actor ("Anyone" shows every actor, so the chip is not read as the Everyone circle; every kitshn reason is the one actor "kitshn"), and words in the name of a changed card or circle or in the summary. Only the row of the caller's own newest revision (K-1506) shows Undo. For that row the client asks `GET kit.<zone>/api/undo?revision=<id>`, which answers as `GET /api/undo-item` does (K-1507), when History opens and again when the caller's own newest revision changes or a move joins it (K-1505); the undo itself checks again. Until the answer comes, Undo is disabled with the tooltip "Checking whether this can be undone"; a refused undo shows disabled with the reason. A click on a row pans the map so that the cards and circles of the row show clear of the panel (K-514), and outlines them once; the outline fades and does not repeat (K-513). When none of them shows on the map (gone, in the tray, or of a hidden kind), a toast says so. For this, each revision in the snapshot carries its kind and at most 30 changed cards and circles, from the tag and id of each change and the members of each stack change. Known limit: revisions from before this rule name a new level of a share as a share ("shared … at use"). This ends when those revisions age out (K-1503).
- **K-1509** Each whole-revision Undo records where it came from: the toast of a change, History, or the HTTP API. The map names the button that sent it ("toast" or "history"); an Undo over HTTP that names none counts as the API, such as an agent or a script. The History row of the undo says it after its number and time ("from the toast", "from History", "from the API"), so an Undo that the owner did not mean shows how it came. An undo of one card or circle (K-1507) and revisions before this record none. Known limit: the map trusts its own buttons; a person can still press either one by mistake, so the source says which button, not why.

"Give the address back" works only while the portal still holds the exact host: it points the record at what it served before, and kitshn forgets the record and never deletes it. Once the record moved and the portal no longer holds the host, the address stays with kitshn. The portal's path applications on a host are more specific, so Access lets them answer their paths, and they stay with the portal for now. Their paths get tunnel rules ahead of the host's rule: a Bypass path gets no Access check, and any other path the check of its own application, while the host keeps kitshn's check. kitshn reads them again every 10 minutes. The provider checks Access tokens against kitshn's applications too: kitshn pushes each provider the Access audiences of its site hosts on the machine (K-1608), with the team domain and the AUD tags of kitshn's applications that cover them (`<host>/*` after a handover), and none while no application exists. An application stays in the list until kitshn deletes it, also after a give-back, because it answers until then. The same push names `served`: the provider's site hosts whose DNS record points at kitshn's tunnel, after the record of a handover moved and for sites that kitshn served from the start. The audiences come before the record moves, so only `served` tells the provider when to stop its own route, such as the portal's cloudflared. A give-back drops its host from `served` and sends that push before it moves the record back. Known limit: the record call follows at once, so the provider's own route can lag it by the time it takes to start; revisit if give-backs happen in use, then the record waits for `applied`. The answer to `register` carries them as `access` (null before kitshn sent them), and an `access` event follows each change: a take, a give-back, or an application made again. The provider accepts a token whose `aud` is in that list or is the portal's audience, until the portal goes. A daemon names `access` among its capabilities; one from before leaves that push out of its queue count.
- **K-1624** The machine map's "Later" ideas (waking a machine, scheduled presets, push on failed commands, groups, the mobile Machines panel) stay later in kitshn too.
- **K-1625** Provider facts. With `upsert` (K-705), a provider may attach facts (a label and a value), stickers (a text, a tone and an optional link) and lists (rows with named columns and row commands) to its resources. kitshn stores and shows them without knowing what they mean (K-005). Two fact roles are generic: `version`, which kitshn compares within one kind to mark the newest machines, and `busy`, which "when online and idle" waits on (K-1608). T3 status (K-1616), tasks (K-1614) and sessions (K-1602) use it. Built: facts, stickers and lists, which the card panel shows, and the `busy` hold. A sticker tone is `info`, `good`, `warn` or `bad`. A card has at most 4 lists of 100 rows and 8 columns, and each cell of a row is one of its list's columns. A resource holds at most 64 KB as JSON, checked by the daemon and kitshn with the same code. A row names commands of its card's kind; the panel shows them as buttons, a command with `confirm` asks first (K-1615), and the command event carries the row id (K-707). ## 17. Machine identity and agent rights

An agent on a joined machine acts in kitshn as its machine (K-1612). kitshn is the authority, not the tool layer: it decides who may do what, with which approval, and records it. Agents keep their own tools (`git`, `gh`, `wrangler`, cloud CLIs, MCP servers). kitshn gives them identity and short credentials, and never wraps those tools.

kitshn reaches a service in one of four ways, in this order of preference:

1. Federation: the service trusts kitshn passes (17.7). kitshn has no code for that service.
2. Token minting: kitshn makes a short, narrow token of the service (17.6).
3. Action relay: kitshn makes the call with a credential that stays in kitshn. Only for a short, named list of actions, each with its own design check. None is in this section yet.
4. Not kitshn: the machine uses its own credentials.

The machine proves itself with its own key pair (17.1). The agent asks its daemon, and the daemon sends the ask over its signed connection (17.2). Each right of a machine is off, automatic, or asks a circle (17.3). Agent rights belong to machines (17.4). Labels and the thread attestation say which thread asked (17.5).

Planned for milestone 5 ([docs/migration.md](docs/migration.md)) as one pull request. Its commits keep kitshn working after each one, in this order: the host move code (K-1209), asks and modes (17.2, 17.3), GitHub tokens (17.6), labels and attestation (17.5), passes (17.7), and rights on machines with repo groups (17.4). Every new right starts off for every existing machine and agent key, so the merge alone gives no new right.

### 17.1 Machine key pairs

Built.

- **K-1701** A machine proves itself to kitshn with its own Ed25519 key pair. Checked on 2026-10-27: Workers `crypto.subtle` supports `Ed25519` for sign, verify, generate, import and export ([Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/)), so kitshn does not need P-256 here. The daemon makes the pair with `crypto.subtle`. Checked on 2026-10-28: a compiled `darwin-arm64` Bun binary signs and verifies, and Bun gives the exact signature of RFC 8032 test 1 (`packages/daemon/src/key.test.ts`). Not yet tested: the compiled `linux-arm64` daemon; the hand install and `kitshn rekey` on the Oracle VPS test it (K-1708), and the panel then shows its fingerprint.
- **K-1702** The daemon keeps the private half in `machine.key` next to `machine.json` (K-602), with mode 0600 in a folder with mode 0700. kitshn stores only the public half, its fingerprint and the time that it became valid, with the machine. The machine panel shows the fingerprint and that time. Known limit: root and every process of the daemon user can read the file, also an agent on the machine. Revisit with a key that cannot leave the hardware (Secure Enclave on macOS, TPM on Linux), or when agents run as their own users.
- **K-1703** `kitshn join` makes the key pair before it sends the join code, and sends the public half with the code to `/join/exchange`. kitshn stores the public half in the same step that deletes the code (K-602). kitshn refuses a join without a public half.
- **K-1704** Each connection (K-604) starts with a challenge. After Access lets the socket in, kitshn sends 32 random bytes, new for each socket, and the fingerprint of the key that it expects (none for a machine without a key; that daemon does not answer, K-1708). It keeps them only in the socket attachment, so a challenge writes no row. The daemon signs four lines: `kitshn-connect-v1`, the kitshn host, its machine id, and the challenge. The host is the hostname without a port: the daemon takes it from the server address in its own `machine.json`, and kitshn from its `KITSHN_HOST`, never from the challenge. kitshn checks the signature with the stored public half. Until the check passes, kitshn reads no message from the socket and sends it no job, state or grant. Another message first, also one that is not JSON, closes the socket. When the check passes, kitshn sends "accepted", and only then does the socket replace an older socket of the machine (4001), so the token alone cannot push the real daemon off. Without a valid answer in 10 seconds, kitshn closes the socket with 4003 and the reason. A replay fails: a recorded answer signs the challenge of an older socket, and each socket accepts one answer only. An answer for another kitshn host names that host, so it fails here too.
- **K-1705** "Rotate key" in the machine panel and `kitshn rotate-key` on the machine do the same thing over the live connection. The daemon makes a new pair and keeps it in `machine.key.next`. It signs five lines with the old private half: `kitshn-rotate-v1`, the kitshn host, its machine id, the challenge of this connection, and the new public half. It sends the new public half and the signature. A daemon that connects in the middle of a rotation signs with the file whose fingerprint the challenge names (K-1704). `kitshn rotate-key` sends `rotate-key` on the local socket (K-702) and waits up to 30 seconds for the new fingerprint. A daemon without a signed connection refuses the request with the reason. kitshn stores the new key, writes a History revision, and closes the connection with 4004 "key rotated". The daemon connects again at once with the new key. From that moment, kitshn refuses every answer that the old key signs. In the panel, only a member with control on the admin card (K-104) rotates.
- **K-1706** "Reset key" in the machine panel is for a key that someone may have stolen, or for an offline machine. For a machine without a key, the same button is "Make key code" and gives only the code (K-1708). kitshn deletes the public half and closes the connection at once with 4005; the daemon then tries again only once an hour. It then shows the command `kitshn rekey <code>`, with the code rules of K-602: one use, 10 minutes, about 99 bits and no attempt limit. The command makes a new pair and keeps it in `machine.key.rekey`, which a rotation or a reconnect never touches. It sends its public half and its machine id with the code to `/join/rekey`; kitshn refuses a code of another machine and keeps that code. After kitshn takes the key, the command moves it to `machine.key` and sends `reconnect` on the local socket (K-702), so the running daemon connects again with the new key. When the daemon does not run, the command says so, and the daemon signs with the new key when it starts. Only that connection changes; the tunnel and the apps keep serving (K-603). Until then the machine cannot connect, so its jobs wait (K-613).
- **K-1707** "Remove machine" (K-615) deletes the public half and closes the connection at once. A rotation, a reset or a removal also ends every ask in flight of the machine, denies its open proposals and revokes its GitHub tokens (K-1716). A pass for an outside service that kitshn gave before stays valid until it expires (K-1774).
- **K-1708** A machine gets its first key only with a key code: from the join (K-1703), or from `kitshn rekey <code>` (K-1706). kitshn never takes a first key from a connection, so nothing runs unsigned. A machine that joined before PR 1 has no key. It connects with its Access service token alone, but only for status: kitshn reads its status and samples, and ignores every other message. It gets no job, also no "Update daemon", and its card shows "needs a key" with "Make key code" in the panel. When the key arrives, kitshn closes the connections of the token alone, and the daemon connects again and signs. Known limits until `kitshn rekey` on a machine without a key: kitshn sends it no job, so deploys and commands wait (K-613), and its apps and its tunnel keep serving. kitshn also ignores its `sites`, `volumes` and `jobResult` messages, so no unsigned message changes routing: offline detection of live sites, `kitshn expose` and late job results wait for the key. Whoever holds the token of such a machine can push its daemon offline (4001) until the rekey. The two joined machines (the Oracle VPS, then the VPS) get the new daemon by hand, because "Update daemon" is a job.
- **K-1709** The machine keeps its Access service token, and `/connect` keeps both locks: Access checks the service token, and kitshn then checks the key signature (K-1704). Access also needs the token on `/connect/deploys/` (K-812), and it stays the Access identity of the machine in circles (K-107, K-1609). The owner chose this on 2026-10-28, on one condition: joining stays one code. kitshn makes the service token and the daemon stores it with the join (K-602); nobody makes or copies a token by hand. With the token, Access drops a socket without a valid service token of the account before it costs a Worker request. The count of service tokens (K-1301) stays one per machine.

### 17.2 Asks from agents

Planned.

- **K-1710** An agent asks its daemon with `ask` on the local socket (K-701): one action (K-1711), one target, an optional reason of at most 500 characters, and optional labels (K-1750). `kitshn agent <action> <target> [--reason <text>] [--label <key>=<value>]` asks and prints the answer. The daemon gives an ask only to an allowed local user, with the peer check of K-701. It adds the attested labels (K-1752) and sends the ask over its signed connection (K-1704). kitshn answers with the result, with "waiting" and a proposal id (K-1722), or with a refusal and its reason (K-006). kitshn makes no token for its own actions: no JWT, no pass, and no stored pass id.
- **K-1711** The actions match the paths of K-718: `state` reads the cards and rights of the machine; `apply` moves one card, also into or out of Everyone by the publish rules of K-718; `publish` is the short form of `apply` for that move; `organize` runs Organize (K-532) on the cards that the machine manages, under the right of `apply`; `allow` allows one waiting repo (K-819); `deploy` redeploys or builds one card; `job` runs one command on one machine (K-612); `job-read` reads the state and output of one job that the machine sent; `github-token` gets a repo token (K-1762); `audience-add` adds a pass audience (`kitshn agent audience add`, K-1773); `pass` gets a pass for an outside service (K-1774); `approve` and `deny` answer a proposal (K-1726); `history` searches the ask events of the machine (K-1756); `backup` backs up a Compose card that the machine manages now (K-1819), under "deploys"; `restore` writes one of its backup runs back (K-1820), under "restores". `state`, `job-read` and `history` need no right. `approve` and `deny` need membership of the approver circle (K-1723). Each other action needs one right of K-1730.
- **K-1712** kitshn runs an ask only when all of these hold at that moment: the machine exists and its connection passed the challenge (K-1704); the machine has the right through its circles (K-1730); every condition of the right holds on attested labels (K-1754); K-718 and K-819 allow the action on that target; and kitshn is not paused (K-1504). It checks them again when an approval runs the ask (K-1723).
- **K-1713** Known limit: every process of an allowed local user can ask, and labels without an attester are claims (K-1750). The unit of trust is the machine, plus the thread where an attester vouches for it (17.5). Revisit when agents run as their own users.
- **K-1714** The asks of agent keys keep their HTTP paths: `kitshn.<zone>/agent/<path>` with the key's service token (K-718). A machine asks the actions of K-1711 only over `/connect`. The commands `publish`, `address`, `redirect`, `logs` and `repo` of `kitshn` on a machine send their `/agent` call to the daemon as a `forward` request. The daemon builds the URL first and sends only a path that stays on the kitshn server and, after normalizing, below `/agent/`, with no encoded slash, backslash, dot or percent. It sends it with the machine token, the attested labels (K-1752) and a signature of the machine key over the method, that normalized path with its query, the time, a random nonce and the SHA-256 of the labels. It drops the caller's own copies of these headers, runs at most 4 forwards at once, and stops reading an answer at the limit below. kitshn takes a machine token on `/agent` only for a path of its forward list that passes the same path check, with a valid signature from the last minute and a nonce that it has not seen in that minute. It keeps the nonces in storage for that minute, so a restart does not let a copied call run again. Then it runs the pause check, the right of the path with its mode and conditions, and K-718, and writes one ask event (`forward`). Rights: "adds pages" for pages, files, folder sites, addresses and redirects; a new folder site also needs "adds apps" (K-1123); a page or a site that goes into Everyone also needs the conditions of "publishes", checked at `plan` and again at `finish`; "adds apps" for `repo`; logs and page content need only a managed card. A forwarded call carries a body that a proposal does not keep, so "ask <circle>" refuses it: the owner sets the right to automatic. The body is not signed; TLS covers it. `kitshn version --json` prints `{"product":"kitshn","generation":2,"version":<version>}` and exits 0, so a tool can tell kitshn 2 from a KitSHn 1 `kitshn`, which has no such command; fields are only added. Known limit: a forwarded body is at most 12 MiB each way; a bigger file needs an agent key. Revisit when an agent needs one. Known alternative (decided on 2026-10-29 to keep HTTP): the same calls as asks over `/connect`, so one connection proves the machine and no machine token goes over HTTP. It costs about the same code, and upload bodies would wait in R2 for an approval, because a row holds at most 2 MB. Revisit when the owner wants forwarded uploads to wait for an approval instead of refusing.
- **K-1715** An ask of a machine reads no Durable Object rows beyond a wake (K-1302) and the reads of the agent path that it runs (K-718): the rights, circles, audiences and attester lists are in memory. A refused ask reads only what its event write reads. A `github-token` or `pass` ask can also read its open approval window, the approved proposals of its machine through the `proposals_machine` index (K-1723, K-1776). A new proposal reads what the alarm schedule, its notification (K-1722) and the alarm schedule of its Web Push (K-1907) read, about 40 rows. It writes one ask event (K-1717) and one index row for each label (K-1756). `test/asks.test.ts` bounds the reads.
- **K-1716** "Rotate key", "Reset key" and "Remove machine" (K-1705 to K-1707) close the connection, so an ask in flight gets no result. They also deny every open proposal of that machine, and revoke every GitHub token of that machine that kitshn still holds (K-1762). The pause (K-1504) does the same for every machine and agent key, and refuses new asks. Setting a right to off revokes the GitHub tokens that it gave.
- **K-1717** Asks are events, not revisions, as in K-1610: History shows them with no Undo, and kitshn keeps them 30 days, at most 5,000. An event names the machine, the action, the target, the reason, the labels with their attester (K-1752) and the outcome. A decision writes one revision: an approve or a deny names the approver and the circle, and a change of a mode names the owner. The thread title is the snapshot that the attester gave at the time of the ask, so a later rename does not change History.

A right that no agent circle sets is "default" and asks the Owner (K-1776); only "off" refuses. The owner sets the mode on the machine chip in the agent circle and picks the approver circle. In a circle that needs a passkey, a machine answers only while the circle's setting "machines may approve" is on. It is off by default, and only the circle editor shows it, for a passkey circle that holds a machine.

For 1 hour after the approval, the same ask of that machine (same action, target and right) runs at once without a new proposal, while the right still asks the circle that approved it.
- **K-1724** A deny, and an expiry after 24 hours (K-1607), reach the agent in the same way: "denied" or "expired", with the proposal id.

If the owner sets the right to "off" while the ask waits, the approval refuses and says so. For a token it opens the hour of that ask. ### 17.5 Labels and thread attestation

Planned.

- **K-1750** An ask carries at most 10 labels. A key has a prefix and a name, at most 64 characters of `a-z`, `0-9`, `.` and `-` (for example `t3.thread.id`). A value has at most 256 characters. kitshn refuses an ask with a bad label and names it. Labels without an attester are claims of the requester: History stores them and shows them as "claimed".
- **K-1751** The daemon config lists attesters. Each has a label prefix, an address and the name of the environment variable that holds the caller's token. The address must be `http:` or `https:` on loopback (`127.0.0.1`, `::1` or `localhost`), and the daemon refuses another one at start. The daemon never takes an attester address from the caller of an ask. The service behind an attester registers itself with the local request `attester-set` (`kitshn attester set --prefix <p.> --url <loopback url> --token-env <NAME>`), which only the daemon user and root may send (K-701), because an attester vouches for every thread. The daemon writes the entry into `machine.json` with the uid of the registering user, and replaces an older entry of the same prefix; it never rewrites a `machine.json` that it cannot read. It takes the entry only while that user listens on the port, and before each check it compares the listener's uid again (Linux: `/proc/net/tcp`; macOS: `lsof`, which sees only the daemon user's processes unless it runs as root, so another user's listener counts as a stranger). So a stale port that another user took never gets a thread's token. Known limit: a hand-written entry has no uid, so its port is not checked. The T3 server sends it on each start with its real port, so kitshn fixes no port. Example: prefix `t3.`, address `http://127.0.0.1:3773/api/thread-identity`, variable `T3_ACP_MCP_AUTHORIZATION`. The daemon reports its attester list to kitshn, and the machine panel shows it. Known limit: another local user can listen on the loopback port while the attester is down, and the daemon user can edit the list. This is the same trust as `t3 machine exec` (MM-1920). Revisit with a Unix socket and the peer check of K-701.
- **K-1752** `kitshn agent` and `kitshn git-credential` read the variable of each attester and send its value with the ask. The daemon calls the attester address with `Authorization: <value>`, follows no redirect, and waits at most 2 seconds. An active answer becomes labels with the attester prefix, marked "verified by <attester>". kitshn stores the mark with the ask event and the proposal, from the attesters that the machine reported at ask time. A command always sends `T3_ACP_MCP_AUTHORIZATION` when it has it, also when `status` fails; with no `t3.` attester registered, the call refuses with "this T3 thread is not checked: the T3 server has not registered with kitshn". A call that carries a token fails closed: an error or a timeout refuses it with "could not check the T3 thread; try again", and an inactive answer (a revoked or idle token, or an archived or deleted thread) refuses it with "the T3 thread of this call is not active". Such a call never goes on as the bare machine. These refusals are refusals of the ask, so `git-credential` stops git with `quit=1`, as for any refusal of a kitshn owner (K-1763); a daemon error, such as no daemon or no connection, still prints nothing, so git tries its next helper. A call without any token goes as the bare machine, with its claimed labels only, and a right with a condition refuses it (K-1754). The daemon keeps the caller's token only for that call.
- **K-1753** The daemon drops every label of the caller that has the prefix of an attester, also when the attester does not answer. Only the attester sets those labels. The prefix `t3.` stays reserved also before a machine lists the T3 attester.
- **K-1754** A right can have conditions on attested labels: a key equals a value, or a key is one of a list (for example `t3.subagent` = `false`, or `t3.project.name` in `kitshn`, `riffle`). kitshn refuses a condition on a prefix that no attester of the machine reports (K-1751). An ask that fails a condition gets a refusal that names the condition.
- **K-1755** The T3 attester gives these labels: `t3.thread.id`, `t3.thread.title` (the title at that moment), `t3.project.id`, `t3.project.name`, `t3.environment.id`, `t3.provider`, `t3.runtime`, `t3.interaction`, `t3.subagent`, `t3.thread.parent` and `t3.thread.parent.environment` (empty for the same environment; a child that a linked environment delegated has `t3.subagent` = `true`). The T3 fork serves the route ([Yarden-zamir/t3code#398](https://github.com/Yarden-zamir/t3code/pull/398), merged as 55799ea274). The token is its only lock, as for `/mcp`; the daemon calls the loopback address of its own config (K-1751). Known limits: agents and the T3 server run as one OS user, so an agent that steals the token of another thread acts as that thread. A subagent that a provider runs in the same process (for example a Claude Code `Task`) uses the token of its parent, so it has `t3.subagent` = `false`. Revisit when agents run as their own users.
- **K-1756** History is searchable by label: the History view filters ask events by `key=value`, and `kitshn agent history --label <key>=<value>` lists the ask events of the machine with that label, newest first, at most 50. kitshn stores one index row for each label of an ask event, with an index on (key, value, time), and deletes the rows with the event. A search reads at most 50 events and their index rows.

### 17.6 GitHub tokens

Planned. It needs the GitHub App (K-908) with the permissions Contents (read and write) and Pull requests (read and write), which the owner adds.

- **K-1760** The GitHub way of an owner (a user or an org) is a setting of its owner repo group (K-1733): "kitshn App token" or "not kitshn". Settings has the default for owners without a group, "not kitshn" when kitshn starts. Employer orgs stay "not kitshn". Only kitshn answers "not kitshn"; the daemon keeps no copy of the ways (owner decision of 2026-10-29). Known limit: kitshn sees the repo name of each ask, also for a "not kitshn" owner, and writes it in the ask event.
- **K-1761** "reads code" gives Contents read and Metadata read. "writes code" gives Contents write and Pull requests write, and includes "reads code". "writes code" never deploys (K-1767). No right gives Workflows, Secrets, Administration or Issues. A future right for one of them is its own high-risk right (K-1725).
- **K-1762** `github-token` asks for one repo and "read" or "write". kitshn checks the right on that repo (K-1733) and the GitHub way of its owner (K-1760). It makes an installation token for that repo only, named by `repository_ids` when kitshn knows the repo id (K-819), else by `repositories`, with the permissions of K-1761, and gives it to the daemon. GitHub fixes its life at 1 hour. Each grant writes an ask event (K-1717).
  - kitshn keeps each live token in the table `github_tokens`: its machine, repo, right and expiry, and the token sealed with AES-GCM under a key that HKDF derives from the App private key. `DELETE /installation/token` needs the token itself, so the sealed copy is the one way to revoke it on the events of K-1716 after a sleep. The table is in `SECRET_ROWS` (K-1831). The 30-day point-in-time recovery of K-1821 holds the sealed copy, never the key, and each token ends after its hour.
  - The daemon keeps a token in memory, never on disk, until 5 minutes before it expires. It gives a kept token only to an ask for the same repo from the same attested `t3.thread.id`, and a read token only to a read ask. An ask without an attested thread always goes to kitshn. The daemon drops every kept token on a new connection and on a rotation of the machine key or of the pass key. It drops the tokens of one repo when kitshn revokes them (K-1716) and on `git credential erase`, which git sends after GitHub refuses a token.
  - kitshn keeps the installation id of each owner in one row. A token costs one GitHub API call and one ask event.
- **K-1763** `kitshn git-credential` is a git credential helper. `kitshn setup-git` writes it to the user's git config before other helpers, with `useHttpPath` for `https://github.com`, so git sends the repo path. For `get`, it asks for "write" when the machine has "writes code" on the repo, else "read", and it sends `password_expiry_utc` with the token. For an owner with "not kitshn", it prints nothing and exits 0, so git tries the next helper (the machine's own login). For an owner with "kitshn App token", a refusal or "waiting" prints `quit=1` and the reason, so git stops and never falls back to the machine's own login. It ignores `store` and `erase`.
- **K-1764** `kitshn gh <args>` gets a token for the repo of `--repo` or of the git remote of the current folder, and runs `gh <args>` with `GH_TOKEN`. It adds nothing else to `gh`.
- **K-1765** Work with these tokens shows as `kitshn[bot]` on GitHub, so the owner can review and approve agent pull requests. Commits keep the author of the machine's git config, so they count for that person.
- **K-1766** An owner that has not installed the App gets "the kitshn App is not installed on <owner>" and no token.
- **K-1767** A push or a pull request of the kitshn App (the OIDC `actor` of K-811 is its bot) never deploys by itself. While kitshn has the App but cannot read its bot name, every push or pull request whose actor ends with `[bot]` waits (409). A push waits for a deploy ask: a machine with "deploys" on the card starts a build with `kitshn agent deploy <card>`, which runs by `workflow_dispatch`. A pull request waits for the owner: kitshn records the run with its pull request and the commit of the run, and the map panel lists it under "Agent pull requests" with "Deploy". Deploy approves that commit only and runs the workflow run again, so the preview deploys; a new push waits again (owner decision of 2026-10-29).

### 17.7 Passes for outside services

Planned. kitshn's own actions never use passes (K-1710). Passes stay off until the host move of K-1209 is done: "Passes" in Settings is off, and the owner turns it on after the move. While it is off, `pass` refuses with that reason, and the `/.well-known` paths answer "not found".

- **K-1770** kitshn is an OpenID issuer with the issuer `https://kitshn.<zone>`. The Worker serves exactly `/.well-known/openid-configuration` and `/.well-known/jwks.json` on the kitshn host with no login (K-1204), with `Cache-Control: public, max-age=300`. Every other path below `/.well-known/` answers "not found", never the map. The discovery document names the issuer, `jwks_uri`, `id_token_signing_alg_values_supported` `["ES256"]`, `response_types_supported` `["id_token"]`, `subject_types_supported` `["public"]` and `claims_supported` (K-1772). It has no authorization endpoint, because kitshn gives passes only to machines.
- **K-1771** The pass key is an ES256 (P-256) key. AWS (since 2024-11-20) and Google Cloud accept ES256. The Durable Object makes it with `crypto.subtle` when it has none, and keeps it in its storage, never in a Worker secret. No read path, export, backup, snapshot or History entry includes the private half; a test checks the snapshot and the export. "Rotate pass key" in Settings makes a new key with a new `kid`. The JWKS lists an old key for 6 minutes after it retired (5 minutes of pass life and 1 minute of leeway), and at most 5 keys. kitshn's own restore to a point in time (section 18) rotates the pass key as its last step, through the same rule as "Rotate pass key". After a restore outside kitshn, the owner rotates the pass key at once. Revisit with an RS256 key for an audience whose verifier refuses ES256.
- **K-1772** A pass is a JWT with `alg` `ES256` and these claims: `iss`; `aud`, one allowed audience (K-1773); `sub` `machine:<machine id>`; `iat`; `exp`, 5 minutes after `iat`; `jti`, 128 random bits. Only when the audience allows labels (K-1773): `act` `{"sub": "t3:<thread id>"}` from an attested `t3.thread.id`, and `kitshn_labels` with the attested labels. `sub` holds ids only, never names. The claims are a public contract in [docs/passes.md](docs/passes.md): kitshn only adds claims and never renames or removes one.
- **K-1773** Audiences are a list in Settings. Each has its exact address and "labels in passes", off by default. An agent with "adds audiences" adds one with `kitshn agent audience add <address> --reason <text>`, and removes one that it added with `kitshn agent audience remove <address>`, which applies at once because it lowers access (K-715). An audience grants nothing by itself: the outside service must also trust kitshn. A member with control on the admin card removes any audience.
- **K-1774** `kitshn agent pass --audience <address>` asks for a pass (`--aud` is an alias). It needs "gets passes" and an audience in the list. During a pause (K-1504), "Passes" in Settings can be turned off but not on. The pass goes to the agent. kitshn stores no `jti`: only the outside service checks the pass, and it checks `exp`. Known limit: a pass is a bearer token for 5 minutes, which kitshn cannot revoke. Revisit with a proof of the machine key on each call ([DPoP, RFC 9449](https://www.rfc-editor.org/rfc/rfc9449)).
- **K-1775** A pass costs one ask event and reads no row beyond a wake. Discovery and JWKS answers read no row: the public keys are in memory.

## 18. Logs, backups and export

### 18.1 Logs

- **K-1801** "Logs" opens the logs of a Compose card or a Worker card from its card panel, its card menu and the command palette. The view has two tabs, "App" and "Deploy runs", a search box and a time range: the last 15 minutes, hour or day, or a custom start and end. Search is plain text and ignores case; it is no regex. The view shows at most the newest 500 lines that match, oldest first, and says when more lines matched. "Live" follows new lines of the app as they come. This replaces dozzle, the log viewer of KitSHn 1.
- **K-1802** Only the admin (K-104) reads logs, in the map. A later read by another member needs a share at a new level `use` on `site.compose` and `site.worker`. A circle with "everyone" never gives logs, at any level, because logs can hold data that the page does not show. A static site, a page and a file have no logs, because no code of theirs runs. A live site (K-1104) has no logs, because kitshn does not run its process.
- **K-1803** A Compose app keeps its logs on its machine, in Docker. On each deploy, redeploy and rollback, the daemon sets `logging: {driver: local, options: {max-size: 10m, max-file: 3}}` on each service, so a container keeps at most 30 MB of logs. This replaces a `json-file` or `local` setting of the app. A service with another driver that the owner allows (K-818) keeps it, and its logs do not show in kitshn. A running container gets the setting on its next deploy only; kitshn does not restart an app for it. The first deploy after the daemon update recreates every service of the app once, also a service whose image did not change, because the setting changes its Compose config. No log line goes into the Durable Object or R2.
- **K-1804** A Compose search goes to the daemon of the card's machine. The daemon runs `docker compose -p <card> logs --timestamps` with the time range, keeps the lines that match and sends the newest 500 and the count. The daemon stops a search after 15 seconds; Compose writes each container oldest first, so the answer then says that it was cut, and the view says "Search stopped at 15 s; narrow the time range". The daemon reads only the logs of a project that has an app folder below its `apps` folder, so a request never reads a project that kitshn did not deploy. A machine that is offline, or a daemon that does not answer in 20 seconds, gets an error that says so. A search writes no row.
- **K-1805** "Live" on a Compose card starts `docker compose logs --follow --tail 100` on the daemon. The daemon sends new lines at most once a second, at most 500 in one batch, and names the count of lines that it skipped. It stops when the view closes, when the map's connection or the daemon's connection drops, and after 30 minutes. An hour of Live costs about 3,600 daemon messages, so about 180 Durable Object requests (K-1302). A wake reads 9 rows plus each row of the small tables (circles, cards, places, share settings, stacks, machines, live sites, presence), about 330 rows for the reference setup (K-1301); measured on 2026-10-28 with the rows-read test. A quiet app would wake the object for each batch, up to 360 times an hour, so about 120,000 rows. So while a map holds a Compose tail, a timer keeps the Durable Object in memory, and Live causes no wake after its start; the timer stops with the last tail. The cost is Durable Object duration only, about 450 GB-s per hour of Live.
- **K-1806** A Worker app logs to Workers Logs, which each deploy turns on (`observability.enabled`). The bootstrap turns it on for the kitshn Worker itself. Cloudflare keeps the events: on the free plan, 200,000 events a day for 3 days, and from 2026-12-01 0.5 GB a day for 7 days ([Workers Logs pricing](https://developers.cloudflare.com/workers/observability/logs/workers-logs/#pricing)). kitshn stores none of them. Search uses the query API (`POST /accounts/<id>/workers/observability/telemetry/query`) for the events of the card's script. That API needs the token permission "Workers Observability: Edit". Without it, the search box says so and names the steps to add it, and Live still works. The bootstrap reports a token without it as a warning, not a stop, and its token link asks for it. VERIFY: the short key `workers_observability` of the token link; a user token link drops an unknown key without a word.
- **K-1807** "Live" on a Worker card starts a tail with `POST /accounts/<id>/workers/scripts/<script>/tails`, which "Workers Scripts: Edit" covers. The map connects to the tail address itself with the `trace-v1` protocol, so tail events cost no Worker request and no Durable Object request. kitshn deletes the tail when the view closes or the map's connection drops.
- **K-1808** "Deploy runs" lists the newest 20 deploys of the card, newest first, with the time, the commit, the state, the reason of a failure and the link to the workflow run. A Compose deploy shows the output of its job (K-813), so a search there filters the lines of each output. The output of a static or Worker deploy stays in GitHub Actions, behind the run link. Known limit: only finished output shows, because the daemon sends it at the end of the job (K-813). Revisit with K-813 when builds get long enough to need live output.
- **K-1809** `kitshn logs <card> [text] [--since 15m|1h|1d|<n>m|<n>h|<n>d | --from <time> [--to <time>]] [--deploys] [--json] [-- <text>]` searches the logs of a card with an agent key, through `POST kit.<zone>/agent/logs` with the body of K-1801 and the card. The search, the 500 lines, the cut of K-1804 and the Worker permission of K-1806 work as in the map. It prints one line per log line (time, source, text), and a cut or a capped answer adds a note on stderr. `--deploys` prints each deploy run of K-1808 with its matching lines, and `--json` prints one JSON object on stdout: the answer as it came, or `{"error"}`, as the other agent commands do. The default range is the last hour. `--` ends the flags, so a search text can start with `--`. It exits 0 when the search worked, also with no line, 1 on an error, an error answer or a refusal (also with `--json`), and 2 on bad arguments. Known limit: no live follow, because Live needs the map's WebSocket (K-1805); revisit when agents need to watch a deploy come up. Section 17 moves the route to `kit.<zone>/agent/key/logs` with the other key routes (K-718).
- **K-1810** An agent key reads the logs of a card only while it controls the card (K-718), by the same check as a redeploy by a key. A circle at `view` and the later `use` level of K-1802 do not give a key logs in v1. A key that does not control the card gets 403. A key searches at most 30 times a minute; then kitshn answers 429 with `Retry-After`, so a loop of an agent cannot keep a daemon busy with `docker compose logs`. The count lives in the memory of the Durable Object, so a wake starts it empty.

### 18.2 Backups

- **K-1811** Each Compose card is backed up once a day: each named volume of its Compose project (by the project label) and its data folder (`apps/<card>/data`). A pull request preview (`pr-<n>`) is not backed up, because it is temporary. Each card has one restic repository in R2 at `backups/<card>/`, so a backup is deduplicated, compressed and encrypted, and only the changes of a day take new space. On 2026-10-28 the VPS held about 2.7 GB of such data, 2.3 GB of it riffle, so daily full copies (about 19 GB for 7 days) would not fit the 10 GB of free R2.
- **K-1812** The daemon runs restic 0.19.1 from the image `restic/restic:0.19.1`, pinned by digest, as a container without a network. Each volume and the data folder is a folder `/data/<name>` in that container. restic so reads files that a container of the app owns, which can have user ids that the daemon user cannot read in rootless Docker, and a later run skips a file whose size and times did not change. The password reaches the container in its environment, never on a command line. One backup run is one snapshot with the tag `run-<id>`.
- **K-1813** restic talks to a proxy that the daemon serves on a Unix socket only while a backup or restore job runs (`rest:http+unix://`). The socket is in a folder that only the daemon user reads, and the proxy answers only requests below a random secret path of that job. It adds the machine's Access headers and sends each request to `kit.<zone>/connect/backups/<card>/<restic path>`. The Worker serves the restic REST protocol from the R2 binding and streams each body to R2 without holding it in memory. restic writes packs of at most 32 MiB, under the 100 MB request body limit. Checked on 2026-10-28 with a probe Worker: a 32 MB PUT from the VPS took 2 to 3 seconds and 1 to 2 ms of CPU time (the free plan allows 10 ms). Checked the same day with restic 0.19.1 against this REST server: init, backup, forget, prune, check, dump and restore of a sub-folder.
- **K-1814** The Worker lets a machine reach `backups/<card>/` only while that machine runs a backup or restore job of the card that kitshn sent to it, as for deploy files (K-812). A job that a dropped daemon socket marked failed (the offline note of K-613) keeps this access until the job expires, so a short drop does not break a running backup. The check reads the current machine of the card on each request, so a move (K-611) gives the new machine access and takes it from the old one with no other step. A restore keeps this access until its job ends, also after its point of no return: the swap whose app started (K-1820). After that point kitshn never puts the old files back; a failed clean-up is a note on a job that is "done", and the next daemon start does it.
- **K-1815** The repository password of a card is HMAC-SHA-256 of the card id under the Worker secret `KITSHN_BACKUP_KEY`. The bootstrap makes this secret once and prints it once, to keep outside Cloudflare, but only when run with `KITSHN_BACKUP_KEY_NOW=1` and with its output on a terminal, so the key never lands in a log file; a bootstrap without it prints that backups stay off, and the daily backup step then backs up nothing and logs one line a day. Each Compose card then says "Backups are off: run the bootstrap with KITSHN_BACKUP_KEY_NOW=1" instead of when the first backup runs. The daemon gets the password from `/connect/backups/<card>/key` under the rule of K-1814; the password is never in a job row. Without `KITSHN_BACKUP_KEY` nobody, kitshn included, can read the backups, so a lost key loses them. Known limit: the passwords come from the key, so a new key locks every repository unless each one first gets the new password with `restic key add`; kitshn has no rotation of this key. Revisit when the key must rotate.
- **K-1816** A backup first runs restic while the app runs, which copies the bulk. Then the daemon writes a marker file, runs `docker compose pause`, runs restic again, and unpauses every service of the app; a failure at any of these steps also unpauses. A failed unpause keeps the marker, and each daemon start unpauses each app that has a marker, so a crash or an update in the middle of a backup does not leave an app paused. The paused snapshot is a copy as after a power loss, which SQLite, DuckDB and Postgres recover from; requests wait during the pause instead of failing. kitshn keeps only the paused run, and forgets the live run also when the paused pass fails. The paused pass has a hard limit of 3 times the pause of the card's last run, at least 30 and at most 90 seconds: 90 s stays under the 100 s that Cloudflare waits for an answer, so a request that waits on the pause still gets one. At the limit the daemon stops restic, unpauses, and the job fails. Each run records its pause length, which "Backups…" shows and the Usage view can show later. A file that changed since the first pass is read whole again. Measured on 2026-10-28 on the VPS: riffle keeps its data in one DuckDB file of 2.4 GB that changes all the time, and a second pass over it took 48 to 60 seconds, so riffle pauses for about one minute each night, at 03:00 UTC (K-1817). Known limit: every card works this way, with no choice per card, and an app whose pause grows past 90 s fails its backup each night. Revisit then with a dump hook per app: the recipe names a command that writes a consistent copy while the app runs, and the backup reads that copy without a pause.
- **K-1817** At 03:00 UTC, a quiet hour, the alarm queues one backup job for each Compose card that has a finished deploy, with an expiry of 24 hours (K-613); the same run writes the export of K-1821 and measures the bucket (K-1818). kitshn queues no job for an online daemon that does not report the capability `backup-restore`. After each backup the daemon runs `restic forget --group-by host --keep-daily 7 --keep-weekly 4 --keep-monthly 3 --keep-tag before-restore`, then lists the runs with the tag `before-restore` and forgets each one whose own time is older than 7 days (restic's `--keep-within` counts from the newest run, not from now), and on Sundays (UTC) also runs `prune`. It reports the runs that the repository still holds, and kitshn deletes the rows of the others. Two runs on one day keep only the newer one. "Back up now" in the card panel queues the same job at once.
- **K-1818** Before it queues backups, the 03:00 run lists the `kitshn` bucket and adds up the sizes of all objects: pages, files, deploy files and backups. At 8 GB or more it queues no new backup, and each Compose card says "Backups wait: the R2 bucket holds <n> GB of the 10 GB of the free plan". A restore passes this guard, because it is the step that the owner needs most. The Usage view (K-1303) shows this size as "R2 bucket kitshn", from the snapshot field `r2Bucket`.
- **K-1819** The card panel of a Compose card shows its newest backup (time, size, state) and "Back up now". "Backups…" lists the backup runs of the card, newest first, from the `backups` table, one row per finished job; it reads no R2. The map reads that table at the first snapshot after a wake, not at the wake. The daily run deletes rows older than 100 days and failed rows older than 14 days. A failed backup shows a "backup failed" sticker with the reason until the next backup works. The 03:00 run notes when it first sees that a card with backups is gone (the table `backup_gone`), and 7 days after that it deletes the repository in R2 and the rows, so a new card with the same id starts empty. An Undo that brings the card back before then keeps its backups; an Undo after that brings the card back without them (K-1502).
- **K-1820** "Restore" on a backup run asks for a confirm that names the time of the run. The daemon then:
  1. checks that each volume and folder of the run exists, before it changes anything;
  2. takes a paused backup with the tag `before-restore`, the way back;
  3. writes the run into a new folder `.kitshn-restore` in each volume and the data folder, while the app runs;
  4. stops the app, moves the files of now into `.kitshn-before`, and moves the restored files in, writing the name of each one to `.kitshn-moved-in` before it moves;
  5. starts the app, and deletes `.kitshn-before` and `.kitshn-moved-in`.
     Each move in step 4 stops the swap when it fails (`set -e`). A failure in steps 1 to 3 leaves the data as it is. A failure in step 4, or a start in step 5 that fails, stops what started, removes only the entries that moved in, moves the files of now back, and starts the app on them. The point of no return is a swap whose app started: after it, a failed clean-up is only a note, and the next daemon start does it. A marker file names the phase of a restore (writing, swapping, cleaning), so a daemon that stops in the middle finishes it at its next start: it deletes the new copy, takes the swap back, or cleans up. A run of step 2 stays "done" also when the restore fails, so the way back always works. History records the restore with the run that it wrote and the run that holds the state from before. Undo cannot run a restore; the way back is "Restore" on that earlier run. Known limits: step 3 needs free disk space for a second copy of the data of the run, and the app sees `.kitshn-restore` in its own folder while step 3 runs. kitshn writes it there because a rename inside one volume is the swap; a folder outside the volume would need a copy across file systems in step 4, while the app is stopped.
- **K-1821** The Durable Object data has two copies. Point-in-time recovery of the Durable Object keeps 30 days without a cost in rows or R2. Checked on 2026-10-28 with a probe namespace on this account: a restore to a time between two writes brought back the older value. And the 03:00 run (K-1817) writes the state export of K-1831 to R2 as `state/<date>.json.gz`; it keeps 30 of them. It holds no secret (K-1831), and the restic repositories need `KITSHN_BACKUP_KEY` (K-1815). The daily export reads each row of the Durable Object once, about 15,000 rows.
- **K-1822** "Restore kitshn to a time…" in the Safety panel needs a fresh passkey (K-1504) and a confirm that names the time and what goes out of step: a machine that joined later loses its card, a removed machine comes back, and deploy files that R2 already deleted stay gone. It rewinds everything in the Durable Object to that time: cards, circles, shares, History, rollbacks, jobs and repos. It does not rewind Cloudflare (Access, DNS, Workers, R2); the next alarm makes Cloudflare match the restored state again (K-408). Writes after the restore point are lost, so the restore keeps its finish in R2 (`state/restore-pending.json`): the undo bookmark, the time label that the Durable Object makes, and the highest job id so far. After the restart, the Worker's poll runs the finish; when the poll times out, the next alarm runs it from R2. Only one of the two runs it. The finish sets the job ids to go on after the old highest one, so a late result of a daemon finds no other job; records the restore in History with the bookmark from before, and a second restore to that bookmark undoes it; and as its last step rotates the pass key of section 17 (K-1771), because the restored storage can hold a key that was retired after that time. Until section 17 lands, that step is an empty hook.

### 18.3 State export

- **K-1831** The state export is one JSON file: `{"format": "kitshn-state", "version": 1, "account": <Cloudflare account id>, "schemaVersion": <n>, "exportedAt": <ms>, "tables": {<table>: [<row>, ...]}}`. It holds every table of the Durable Object except the one-time codes (`join_codes`, `rekey_codes`, `device_invites`), the jobs, and each secret that the constant `SECRET_ROWS` (`packages/edge/src/worker/backups.ts`) names: the pass key of section 17 (the table `pass_keys` and each `meta` key that starts with `pass_key`, K-1771), the sealed GitHub tokens (the table `github_tokens`, K-1762) and Web Push (K-1907): its VAPID private key (the `meta` key `push_vapid_jwk`) and the table `push_subscriptions`, whose endpoints and auth secrets let anyone push to a device. So an import has no subscription, and each browser subscribes again when its Notifications view opens. A new secret is one line there, and a test checks each line. A BLOB value is `{"base64": <text>}`. The exported tables hold no secret: tokens stay on the machines and in Cloudflare (K-602). The daily copy of K-1821 uses this format, and so does the import of a later step.
- **K-1832** "Download state export" in the Safety panel, next to "Restore kitshn to a time…", saves the export of K-1831 as `kitshn-state-<date>.json` from `GET /api/state/export`. Only the admin (K-104) reaches it. It reads each row once, about 15,000 rows for the reference setup (K-1301), and holds no secret.
- **K-1833** `KITSHN_IMPORT=<file>` makes the bootstrap (K-1201) rebuild the state of kitshn from an export, a `.json` file of K-1832 or a `.json.gz` copy of K-1821. The bootstrap uploads the file to R2 as `import/state.json.gz` and sets the Worker variable `KITSHN_IMPORT_AT` to the time of the run. When the Durable Object starts and sees a new `KITSHN_IMPORT_AT`, it imports the file once, before the other start steps (the first-start setup, the admin address, presence and rollbacks), so they run on the imported state. The bootstrap waits up to 2 minutes for the answer of the public `GET kit.<zone>/join/import-status` and prints it. The answer holds only `pending`, `done`, or `refused` with one code of `no_file`, `bad_file`, `other_account`, `newer_schema`, `unknown_table`, `not_empty` and `failed`; the details, which can name an account, a card or a table, go only to the server log. The import refuses:
  1. an install that is not empty: it has a machine, a deploy, a library item, a repo, a revision, or a card other than the admin card;
  2. an export of another Cloudflare account (`account`), or one without an account;
  3. an export of a newer schema than this kitshn (`schemaVersion`), or a table that this kitshn does not know.
     Then, in one transaction, it drops every table, runs the migrations up to the schema of the export, writes each row (a `{"base64"}` value back as a BLOB), runs the later migrations, records the import in History, and stores the status `done`, so a later error or a restart never reports a done import as refused. After the transaction, kitshn deletes the file and rotates the pass key (K-1834); a failure there goes to the server log, and the next start tries again. A refused import also deletes the file at once, because it holds the whole state; a failure there goes to the server log. `KITSHN_IMPORT_AT` stays set until the next bootstrap without `KITSHN_IMPORT` drops it; that is harmless, because the Durable Object keeps the `import_at` of the last import and never reads the same one twice. A done import whose last steps failed still finishes at a later start without the variable. A table that the export does not hold (the jobs, the one-time codes and each secret of `SECRET_ROWS`) starts empty. An import writes each row once, about 15,000 rows, under the 100,000 rows a day.
- **K-1834** After an import, kitshn makes what the export does not hold: the next alarm compares Access with the shares and writes what Cloudflare lacks (K-408), each daemon connects again with its own machine token, and the export holds no pass key of section 17, so the import ends with the pass key rotation of K-1771. Known limits of v1: an import works only into the same Cloudflare account, so the tunnels, service tokens, Workers, DNS records and R2 objects that the rows name still exist; and the import rebuilds no R2 object, so pages, files and backups are there only when the bucket still holds them. Revisit with a move to another account, which needs a new join of each machine, a new deploy of each Worker and a copy of R2.

## 19. Notifications

- **K-1901** One notification system for every source. A notification has a source (for example `uptime`, `deploy` or `kitshn.ask`), a key that is unique within its source, an optional card, its recipients, a level (info, warn or error), a priority (normal or high), a title of at most 100 characters, a text of at most 500, its actions and its state. A source opens a notification, changes it and closes it through the same source and key, so a later state replaces the earlier one and a key that is still open makes no second notification. A notification is open or closed (closed, dismissed, or a final state of its source). Known limit: a state other than "open" closes the notification, so a source state that must stay open, such as "asked, waiting" for `kitshn.ask`, needs a separate field; PR (c) of notifications adds it. kitshn keeps notifications for 30 days, at most 500, and deletes older ones in the daily run.
- **K-1902** Recipients. In the first version the owner (a member of the Owner circle, K-101) gets every notification except `kitshn.ask`. A `kitshn.ask` notification goes only to the people of the approver circle of its proposal (section 17); an owner outside that circle reads the ask in History (K-1717). The live asks of the map snapshot (`/api/state` and the socket), which feed the Inbox and its counts, follow the same rule: a person, a device or a machine gets only the asks that it may answer, with the answer check of K-1723 and K-1727. Other members get no app, uptime or deploy notification. Known limit: the notification routes sit behind the admin check (K-104) and take the Owner circle only, so a member of an approver circle cannot reach them yet; `kitshn.ask` needs its own route for them. Later rule: a circle can turn on the notifications of a card for its members, per card, off by default, and never through a circle with "everyone" (K-201), so a member never learns about a card that the member cannot see in detail.
- **K-1903** The service of the Durable Object has three calls for every source: open or change a notification (source, key, recipients, level, priority, title, text, actions, card), set its state (an answer closes it for all recipients), and register an action handler per source. An action is "run" or "link". "Run" calls the handler of its source at once, after kitshn checks that the caller is a recipient; "link" opens a path of the map, which runs its own checks there. A source writes a row only when its notification changes (K-1302).
- **K-1904** Sources of the first version: a deploy whose newest run failed or did not run (K-820) opens a `deploy` notification for its card, which closes when a later deploy of the card ends well; a card that goes down (K-1125) opens an `uptime` notification, which closes when it is up again. kitshn derives both from the state that it keeps anyway, after each change, so no deploy step needs a call of its own. Further sources: app events (K-1908), limits and machines that stay offline (K-1910), `kitshn.ask` (K-1909), and later the health alerts of K-1604.
- **K-1905** The Notifications view (K-519) lists the notifications of the last 30 days, newest first, with the source, the card, the open and close times and the actions. The toolbar shows a bell with the number of open notifications that are not muted or snoozed; the alarm runs at the next end of a mute or a snooze, so the count follows it. Ways out: "Dismiss" closes an open notification; the same source and card open a new one only for a new episode (a later failed deploy, or a card that goes down again after it was up). "Snooze 1 h" hides one notification for one hour, and "Unsnooze" shows it again. "Mute" hides the notifications of one card and source for 1 hour, 1 day or until unmute; a mute names a card that exists and a known source. The view lists the mutes, each with its end or "until you unmute", and "Unmute". Mute, snooze and dismiss never answer a notification of a source with answers (K-1909). Only the Owner circle uses these routes in this version (K-1902), and each device of the owner sees the same mutes.
- **K-1906** Rows per day for the reference setup (K-1301): a `deploy` notification writes 1 row when it opens and 1 when it closes, about 2 a day; an `uptime` notification 2 rows per down time, a few a day; a mute or a snooze 1 row. The reconcile after each change reads the open notifications only, from memory after the first read (K-1302). The view reads at most 500 rows, only while it is open.
- **K-1907** Web Push of notifications. The Durable Object makes the VAPID key (P-256, Web Crypto) on first use and keeps the private half in `meta` under `push_vapid_jwk`; no read path, export, backup, snapshot or History entry includes it, and a test checks the snapshot. Like the pass key of K-1771, it is plain Durable Object storage, which Cloudflare encrypts at rest; kitshn adds no encryption of its own, because it has no store key (K-809). "Rotate push key" (owner) makes a new key and deletes every subscription, because a subscription belongs to one key; each browser subscribes again when its Notifications view opens. A subscription belongs to one browser of one person and keeps its endpoint, keys, a label, the levels it gets (default warn and error), quiet hours in its time zone and the time of its last delivered push. A push goes to the subscriptions of the recipients of a notification (K-1902), checked again at send time, when the notification opens, and for priority high when its state changes; never on close, dismiss or snooze, and never for a muted card and source, also not a state change of priority high. During quiet hours only "error" and priority high get through. The payload is encrypted end to end (RFC 8291): the title, the source and the card name, the notification id and the map path; never an address, a reason text or a secret. A push lives 24 hours (`TTL`); "error" and priority high are urgent; a `Topic` from the source and key lets a newer push replace one that waits. Ways out: "Turn off" on the device, "Remove" on any device in the list, which shows when each one last got a push; an answer 404 or 410 of the push service deletes the subscription; "Sign out everywhere" (K-110) deletes every subscription. "Send a test" is for the owner, at most once a minute. Each push is one subrequest per subscribed browser. Only the alarm sends pushes, once at its end after its own reconcile, at most 5 in one run, so an alarm run with its 40 calls stays at 45 of the 50 subrequests (K-406); a change elsewhere queues its pushes and sets the alarm within a second. The rest wait in memory for the next alarm, and a send that fails gets one more try there. Known limit: a wake drops the pushes that wait; revisit if pushes get lost. An answer 401 or 403 of the push service keeps the subscription and logs a warning: the service refuses kitshn's key, for example after a VAPID bug or a clock skew, and "Rotate push key" is the way out. kitshn takes the push endpoint that the owner's browser gives, any https address; only the owner adds one. Revisit with a list of push service hosts if other people can add devices.
- **K-1908** App events. Each deploy, redeploy and rollback of an app card gives the app a new notify token and the address `KITSHN_NOTIFY_URL` (`https://<KITSHN_HOST>/notify`): a Worker app gets both as secret bindings `KITSHN_NOTIFY_TOKEN` and `KITSHN_NOTIFY_URL`, a Compose app in the environment of each of its services, with no change to its Compose file: the daemon adds both to the checked config that it runs (K-812), and a value that the app sets itself wins. The token goes into that config without a value, and each other place where Compose interpolated it (another key, a command, a label, a build arg) becomes `${KITSHN_NOTIFY_TOKEN}` again, so Compose takes it from its own environment at `up`; it is in no file, log or job row, and the checked config, which stays with the last good build (mode 600), holds only the address. kitshn keeps only the SHA-256 of each token. A token works at once, so an app that starts before its deploy reports back can send; it stays only when its deploy, redeploy or rollback succeeds, and a failure drops it. kitshn keeps the newest 6 tokens of successful runs per card, so a rollback (K-821) brings back a build whose token still works, and failed runs never push that token out; Remove app deletes them. The app sends `POST /notify` with `Authorization: Bearer <token>` and `{title, text, level, key?, resolved?}`, at most 4 KB (else 413): a title of at most 100 characters, a text of at most 500, a level of info, warn or error. The path has an Access Bypass application like `/deploy` (K-1204), and the Worker checks the token itself; a token opens only the card that it was made for. The source is `app` and the key is `key`, or the title; `resolved: true` closes the open notification of that key, and kitshn tells the maps only when one closed. Limits: 10 calls per card per hour, a resolve included, and 30 notifications per hour for all cards together, so one app cannot starve the others; a refused call gets 429 with `Retry-After`. Known limits: the counts live in memory, so a wake starts them again; a call with a wrong token gets 401 with no count, which costs one Durable Object request and one indexed row read, as the other Bypass paths do. Revisit either if an app or a stranger floods. The owner gets every app notification (K-1902), and its push says only "<card> has news" with the source, never the app's title or text (K-1907); the map shows them.
- **K-1910** kitshn's own sources. Limits: once an hour, and never in the daily run, the alarm reads the use of the account (K-1303, K-1305); a value at 80% or more of its limit opens a `limits` notification with the value's label as its key, and it closes when the value is under 80% again; an unknown value opens nothing. Machines: a machine that is offline for 15 minutes opens a `machine` notification, which closes when the machine is online again; the alarm runs at that time. Rows per day for the reference setup (K-1301): the hourly check writes one `meta` row an hour; each notification writes 1 row when it opens and 1 when it closes.

## 20. Game servers

- **K-2001** A game card (kind `game`, level `view`) gates 1 to 4 ports (1024 to 65535, TCP or UDP) of one machine. Its name is one DNS label of 1 to 63 characters (`join` and `login` are kept), and the game address is `<name>.<zone>`. It has a door time from 1 hour to 7 days (12 hours by default) and an optional SRV service such as `minecraft`. The card does not run the game: any process on the machine that listens on the ports is the game, for example a Compose app with the `ports` allowance of K-818. The owner (`POST /api/games`), the CLI (`kitshn game add`) and agents (`POST /agent/games`) make it, in the tray. Its address must be free (K-817), and its machine must report the capability `doors` (K-2002). A game port may not be a port that kitshn's neighbours use (Tailscale `41641/udp`, T3 Code `3773/tcp`), that a kitshn site of the door machine serves, or that another service of the door machine listens on, from the running servers report (K-619). The game itself may listen already, so another service is one that answers HTTP or a process that is never a game (`sshd`, `cloudflared`, `kitshn`, `tailscaled`). Known limit: that report lists TCP only, so a UDP port of another service is not seen; revisit when the report lists UDP.
- **K-2002** A machine reports the capability `doors` only on Linux with nftables (Windows: K-2009), with the door helper, its sudoers line (the daemon user may run only `doors apply`) and its boot unit installed (`kitshn doors install --user <daemon user>`, as root, once), and with a public address on an interface. Otherwise its status names the reason, a game card on it is refused, and a Linux daemon checks again every minute, because a start problem can pass (the network was not up yet). The status also carries the public IPv4 and IPv6 addresses of the machine; kitshn keeps them per game card, so its records stay while the machine is offline.
- **K-2003** The join page `pages.<zone>/join/<name>` is Worker-checked like a page (K-1004), with no new Access application or record. It needs a person login, because a door belongs to a person, except for a game open to all (K-2004): its page needs no login and says "Open to everyone: join <game address>". A logged-in person whose circles share the card sees the game address with a copy button, the addresses that the doors open before the click, "Open for <door time>", and their own open doors with one "End now". A home network can leave through another public IPv4 address per destination, so the page asks `ipv4.icanhazip.com`, `api.ipify.org` and `ipv6.icanhazip.com` from the browser, each with a 3 second timeout. It opens the address that kitshn sees and each other address that the browser found; when a family does not answer, it says so. Known limit: a network whose route to the door machine uses yet another address still fails; revisit with a check from the door machine itself. The game address is `<name>.<zone>` with an SRV service, else `<name>.<zone>:<first port>`.
- **K-2004** While a game card has an active share in Everyone (an "any" circle with everyone), its ports are open to every address, with no door and no login, and its map card shows an "open to all" sticker. An Everyone game is a public server. After the unshare the ports are gated again at the next plan, and the doors of circle members work as before. Otherwise a door opens the game ports of one card for one address until its end: an IPv4 address, or the `/64` of an IPv6 address, because one home gets one `/64` and its devices change their address in it. A private, shared, loopback or link-local address is refused. A person has at most 4 IPv4 doors and 2 IPv6 doors on a card. A new address adds a door, and an address that is open already gets a new end; past the limit, the oldest door of that family closes. The address that kitshn sees is always a door, the browser adds the other addresses of K-2003, kitshn leaves out one that it refuses or that the share check with that address does not allow (so an address condition of a circle holds), and nothing opens when kitshn refuses the address that it sees. "End now" closes all doors of the person on the card. A person opens or closes a door of a card at most once in 10 seconds; kitshn keeps that time in memory, so a restart of the Durable Object only resets the wait. Only a person opens a door; an agent or a device cannot. Each open and close is a History line with the person, the card and the address.
- **K-2005** The machine holds the doors in the nftables table `inet kitshn_doors`, which only its root helper writes. The game ports drop every packet that comes from no open door, in the input, output and forward hooks, so "End now" also ends running connections, and a port that system Docker publishes is gated too (the forward chain tests the `dnat` flag of the connection; `test/doors-netns.sh` sends real traffic through it in CI). Each door has its end as a kernel timeout, so it closes on time also while the daemon is down. The ports of a game open to all leave the gated set of the plan, and its doors leave the plan; a port that a gated game of the machine also names stays gated. kitshn sends the full plan of a machine as a job after each change, also when a share in Everyone of a game starts or ends (after a restart of the Durable Object, only to a machine whose last plan has other game ports), and again each time a daemon that reports `doors` connects, also an empty plan, so a card that went while the machine was offline releases its ports; the daemon keeps the last plan, writes it again after a restart and every minute, because a `flush ruleset` (such as `nftables.service` or a reload) can delete the table, and ignores a kept plan of another shape with a log line. After a reboot the table is gone, so the boot unit `kitshn-doors.service` loads the last game ports with no door after `nftables.service` and before the network and Docker start, from a root-owned copy at a fixed path that each `apply` writes; the ports start closed, and a damaged line of that copy is skipped while the good ports still load. A door closes at once when its person loses the share of the card (after each commit and in the alarm, checked with the address that opened the door), when its card goes, when its machine is removed, and with "End now". Known limit: an Everyone game stays open while its daemon has lost kitshn, also through an unshare or a pause, until the daemon reconnects; revisit if that window matters, for example with a daemon-side end for open-to-all ports.
- **K-2006** The owner reads each game card with its doors, records, listening ports and problem (`GET /api/games`), closes any door (`DELETE /api/games/<card>/doors/<address>`) and removes the card (`DELETE /api/games/<card>`). An agent whose circle controls the door machine does the same for that machine's games (`GET /agent/cards/<card>/doors`, `DELETE /agent/cards/<card>/doors/<address>`, `kitshn game doors|close`), and with "adds apps" removes the card (`DELETE /agent/cards/<card>`, `kitshn game remove`). The daemon reports which game ports listen.
- **K-2007** kitshn makes the DNS-only records of each game card: A and AAAA to the public addresses of the door machine, and with an SRV service `_<service>._tcp.<name>.<zone>` to the first TCP port. Before it makes a record it checks that no record of that type and name exists, so it never adds to a record that it did not make. The alarm spends at most 4 calls a run on them (K-406), and a new public address moves them.
- **K-2008** A game on a machine without a public address (a Mac, a machine behind NAT) goes through a relay machine that has one, TCP only. The game has one TCP port, and its second address `<name>-relay.<zone>` is ingress of the game machine's tunnel to `tcp://localhost:<port>`, with its own proxied record and an Access application that lets in only the service token of the relay machine (none during the pause). The relay machine runs `cloudflared access tcp` on that port with its own service token, so its door table gates the relay like a local game. The game address then has an A record to the relay machine only. UDP games behind NAT need another way, such as WireGuard; revisit when one is needed.
- **K-2009** Game doors on Windows, IPv4 only. A PC behind a home router uses the router's UPnP port mapping: the daemon forwards each game port to the PC (forwards named `kitshn <port>/<proto>`; it removes its own forwards that the plan no longer has and refuses a port that another device holds) and reports the public address that the internet sees. It reports `doors` only when the helper is installed, the router offers UPnP, the address is not shared (carrier NAT) and the router's outside address is that address (no double NAT). Windows Firewall applies block rules before allow rules, so each game port gets one block rule for IPv4 and one for IPv6, for every remote address except the open doors and the private, loopback, link-local and shared networks; so existing allow rules (Java, for example) cannot open it, and the home network keeps it. The rules need administrator rights, so `kitshn doors install`, in an administrator PowerShell once (one UAC prompt), copies kitshn to `C:\Program Files\kitshn\kitshn-doors.exe`, which the user cannot change, makes `C:\ProgramData\kitshn\doors`, where the user may write only the plan, and registers the SYSTEM task `\kitshn\doors` at start-up. That helper reads the plan file every 2 seconds and again every 30 seconds, skips a bad line (the good ports still close), drops ended doors, and writes only the rules of the group `kitshn doors`, new rules before it removes old ones. Windows keeps the rules over a reboot, so the ports stay closed until the helper runs. Known limit: the helper copy does not update with the daemon; revisit when the plan format changes.
