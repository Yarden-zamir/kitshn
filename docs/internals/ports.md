# Ports

A port card shares the ports of a service on one machine, such as a game server. Each route is a way for a player to reach the ports. A door opens the ports for one address of a person. This file holds those rules (K-20xx).

- **K-2001** A port card (kind `port`, level `view`) shares 1 to 4 ports (1024 to 65535, `tcp` or `udp`) of one port machine. Its address is `<name>.<zone>` (`connect` and `login` are kept names), with a door time from 1 hour to 7 days (12 hours by default) and an optional SRV service. The card does not run the service: any process that listens on the ports is the service, for example a Compose app with the `ports` allowance of K-818. The owner, the CLI (`kitshn port add`) and agents make it, in the tray. An agent needs control of the port machine, and of the relay machine for a relayed card. A port may not be a port of kitshn's neighbours (Tailscale `41641/udp`, T3 Code `3773/tcp`), of a kitshn site on the port machine or the relay machine, or of another service of either machine from the server report (K-619). Known limit: that report lists TCP only. Revisit when it lists UDP. Known limit: the ports have no DDoS shield, so a flood can fill the line of the whole machine, its tunnel sites too.
- **K-2002** A port card has one or more routes, which the owner picks when the card is made:
  - **direct**: players connect to the public address of the port machine, which needs `doors` (K-2003);
  - **relay**: players connect to a relay machine that has `doors` (K-2009); the port machine does not need it;
  - **private**: comes later, with the Cloudflare One Client; K-2011 to K-2013 are kept for it.

  A card has at most one of direct and relay, because both use `<name>.<zone>`. A relayed card has one TCP port and no UDP port. So a port machine of a card without the direct route can run any platform, also Windows and macOS, without admin rights. Known limit: the route is fixed when the card is made. To change it, the owner removes the card and adds it again, which loses its shares. Revisit with the private route, or when an owner needs to move a card with many shares.
- **K-2003** A machine reports the capability `doors` only on Linux with nftables, with the door helper, its sudoers line and its boot unit installed (`kitshn doors install`, as root, once), and with a public address. Otherwise its status names the reason, and the daemon checks again every minute, because a start problem can pass. Rules:
  - A public address is an address on an interface, or a declared one (`kitshn doors install --public-address <IPv4>`) for a cloud machine whose provider translates the address. The daemon drops a declared address only when `ipv4.icanhazip.com` gives a different one. No answer or a 5xx changes nothing, so an outage of that service never takes the doors and the records away.
  - The install reads the INPUT rules of the host firewall and names each rule that rejects or drops before the ports could pass, for example the default `REJECT` of an Oracle image. The status says so. kitshn does not change other firewalls. A helper from before this check saves no rules, so the status says that the firewall was not checked.
  - Known limit: kitshn cannot see a cloud firewall (an Oracle security list, an AWS security group), so the card panel says that it must allow the ports. Revisit with a reach test from outside.
  - kitshn keeps the public addresses per port card, so its records stay while the machine is offline.
  - The tools run by their full path, so a root shell without `/usr/sbin` on its PATH works.
- **K-2004** The connect page `pages.<zone>/connect/<name>` is Worker-checked like a page (K-1004), with no new Access application. It needs a person login, because a door belongs to a person. A home network can leave through another public IPv4 address per destination, so the page also asks address services from the browser and opens each address that it found. A relayed card listens on IPv4 only, so the page opens nothing for it when no IPv4 address answered. Known limit: a network whose route to the port machine uses yet another address still fails. Revisit with a check from the port machine.
- **K-2005** While a port card has an active share in Everyone, its ports are open to every address, with no door: such a card is a public server. Otherwise a door opens the ports for one address until its end: an IPv4 address, or the `/64` of an IPv6 address, because a home gets one `/64` and its devices change address in it. kitshn refuses private, loopback and link-local addresses, and an address that the share check does not allow, so an address condition of a circle holds. A door opens an address, so everyone behind the same NAT (a café, mobile CGNAT) reaches the ports while it is open, and the service's own login stays the second wall. A person has at most 4 IPv4 and 2 IPv6 doors per card, and the oldest closes past the limit. Only a person opens a door, never an agent or a device. Each open and close is a History line.
- **K-2006** A machine with `doors` holds the doors in the nftables table `inet kitshn_doors`, which only its root helper writes. The gated ports drop every packet from no open door in the input, output and forward hooks, so "End now" also ends running connections, and a port that Docker publishes is gated too. Rootless Docker with pasta binds host sockets, so the input hook sees the real client address. `test/doors-netns.sh` sends real traffic through it in CI. On a relay machine, the gated port is the relay listener (K-2009). Rules:
  - Each door has its end as a kernel timeout, so it closes on time also while the daemon is down.
  - kitshn sends the full plan of a machine after each change and on each connect, also an empty plan, so a card that went while the machine was offline releases its ports.
  - A `flush ruleset` can delete the table, so the daemon writes the last plan again every minute.
  - After a reboot, the boot unit `kitshn-doors.service` loads the last ports with no door, before the network and Docker start, so the ports start closed.
  - A door closes at once when its person loses the share, when its card, port machine or relay machine goes, and with "End now".
  - Known limit: a card open to all stays open while its daemon has lost kitshn, also through an unshare or a pause. Revisit if that window matters.
- **K-2007** The owner reads each port card with its doors and problems (`GET /api/ports`), closes any door, and removes the card. An agent whose circle controls the port machine does the same for that machine's cards, and needs "destroys" to remove a card. Only a direct card reports which ports listen, because the relay's own listener always answers.
- **K-2008** kitshn makes DNS-only A and AAAA records of each port card to the public addresses of the machine that players reach (the port machine, or the relay machine), and an SRV record for the first TCP port. A relayed card gets an A record only, because its relay listens on IPv4 only. kitshn never adds to a record that it did not make. The alarm spends at most 4 calls a run on them (K-406).
- **K-2009** A relayed card goes through a relay machine with `doors`, TCP only. The port machine's tunnel serves `<name>-relay.<zone>` to `tcp://localhost:<port>`, behind an Access application that lets in only the relay machine's service token. The relay runs `cloudflared access tcp` on that port, so its door table gates the listener like a direct port. Rules:
  - kitshn refuses a port that another card holds on the same door machine when either card is relayed, because two listeners cannot share a port and a door of one card would open the other.
  - A new relayed card shows the progress sticker of K-538 until the relay has held its port for 10 seconds, so the owner sees when players can connect.
  - The owner picks a relay machine near the players and near the data centers of the port machine's tunnel (K-632), because each byte takes that path.
  - Known limit: UDP behind NAT needs another way, such as WireGuard from the relay machine to the port machine. Revisit when a UDP service needs it.
- **K-2010** The card panel of a port card shows each route that is on, and the problem of each machine on it, such as no `doors`, a host firewall that rejects, or a tunnel without a connection. It names each share that the route cannot check: a door opens for a person or an address, so the devices and machines of a circle do not get in.
