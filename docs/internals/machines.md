# Machines and the daemon

Each machine runs one `kitshn` daemon. This file holds the rules for machines, jobs, updates and health checks (K-6xx).

## Daemon and tunnel

- **K-601** Each machine runs one `kitshn` daemon as a service of the user who joined it: a systemd user service on Linux (with lingering, it starts without a login), a launchd agent on macOS, a Task Scheduler task at logon on Windows (K-622). The tunnel runs as a second user service of the same user, which the daemon installs (K-603). The daemon is one binary per platform, so a machine needs no Node.js.
- **K-602** "Add machine" creates a service token and a remotely managed tunnel, and shows a one-time join command with a code that expires after 10 minutes. `kitshn join` saves both tokens in a file that only the daemon user can read, and sends the public half of the machine key pair (K-1703). kitshn stores the tokens only encrypted with a key from the code, and deletes them when the code is used. The code has 20 random characters (about 99 bits), so kitshn sets no attempt limit. Revisit if codes get shorter.
- **K-603** The daemon runs `cloudflared` as its own user service, with the tunnel token in a file (`--token-file`), not on the command line. A restart or an update of the daemon never stops the tunnel, so apps keep serving. The daemon restarts the tunnel only when `cloudflared`, its token or its service file changes, or on the job of K-634. The service file carries the edge pin of K-632, when there is one. kitshn owns the tunnel ingress through the API, and the daemon never edits it. Each ingress rule whose address has a kitshn Access application sets `originRequest.access` with `required: true`, so `cloudflared` drops a request without a valid Access JWT. This guards the address when a DNS record or a removal step goes wrong. Traps:
  - A rule whose application has a Bypass policy (K-403) gets no check, because Access issues no JWT for Bypass. kitshn decides from the application that Cloudflare last accepted, not from the shares, so the check never comes on before Access stops the Bypass.
  - While kitshn does not know the audience tag of an application, the rule goes without the check, and kitshn logs the address. A site never leaves the tunnel for a missing tag.
  - A Service Auth policy with only an IP range gets a JWT, so the check stays on for network members. An Allow policy with only an IP range sends the visitor to the login, so kitshn does not compile networks to Allow (K-402).
  - Known limit: "running" means that the tunnel service runs, not that `cloudflared` has a connection. Revisit with the readiness endpoint of `cloudflared` when a false "running" misleads.
- **K-604** The daemon keeps one WebSocket to the Durable Object at `/connect`, with backoff after a failure. Each connection starts with the challenge of K-1704. Liveness uses `ping` and `pong` with the Durable Object auto response, so a ping wakes nothing.
- **K-605** The daemon sends its status on connection and on each change, at most once every 5 seconds, and a resource sample (CPU, memory, disk) once a minute. The local request `samples` (K-702) answers from the daemon's disk, with no message to kitshn.
- **K-606** The Durable Object keeps only the latest sample of each machine, in memory. The daemon keeps 30 days of history on its disk. This keeps the daily writes low (K-1302).
- **K-607** Local sites use Unix sockets: a Compose service listens on `<name>.sock` in `$KITSHN_SOCKET_DIR`, which is `<daemon data>/s/<first 16 hex of SHA-256 of the card id>`. The hash keeps the path length the same for every card, inside the socket path limit (107 bytes on Linux, 103 on macOS) while the daemon data folder has at most 71 bytes. A deploy whose socket path passes the limit fails before the old app stops. Services publish no host ports, and no Caddy is needed.
- **K-608** Planned: for an app that cannot listen on a socket, the recipe names a port inside its Compose network, and the daemon adds a small socket proxy. The machine still publishes no host port.
- **K-632** The daemon pins its tunnel to the near edge region. This serves every card of the machine, web routes too: a visitor from Israel takes the same Haifa data center. Rules:
  - At start and every 6 hours, it measures the TCP connect time to two addresses of each tunnel edge region (`region1.v2.argotunnel.com`, `region2.v2.argotunnel.com`, port 7844).
  - A pin changes only when two measures in a row agree that one region is at least 20 ms faster. The tunnel service then gets `--edge` with those addresses and `--protocol http2`. A region that stays the pin keeps its addresses, although DNS rotates them, so the tunnel restarts only when the pin changes (K-603). A measure with no answer changes nothing.
  - Every 30 seconds the daemon reads `/ready` of cloudflared. A pinned tunnel that is not ready for 60 seconds in a row loses the pin until the next measure. A read with no answer and a clock jump, such as a wake from sleep, start the 60 seconds again. Only `/ready` says whether a connection is up, because `cloudflared_tunnel_server_locations` keeps its value after a cut.
  - The metrics port is a free port that the daemon picks once and keeps. It moves only when the tunnel service does not run and another program holds the port, because cloudflared exits on a busy metrics port.
  - Known limits: all connections are in one data center, so an outage there stops the tunnel until the 60-second fallback. A network outage of more than 60 seconds also drops the pin, for at most 6 hours. `--edge` is not documented, and a pin with QUIC timed out in the test, so a pin uses HTTP/2. Revisit if cloudflared drops `--edge`, or when QUIC works with a pin.

## Jobs and placement

- **K-609** Each machine has labels, for example `docker`, `server`, `arm`, `laptop`. The owner sets one order of all machines.
- **K-610** A job names the labels that it needs. kitshn gives it to the first online machine in the order that has all of them, or it waits until its expiry (K-613). The placement of a Compose app can ask for more machines (K-823). A deploy runs only on a machine with the label `deploy`, so the apps of repos never land on a machine that the owner did not offer. So an agent never sets labels without a person: it asks the Owner (K-1777).
- **K-635** kitshn also gives each machine fact labels from the live daemon status (K-605): `os:linux`, `os:darwin` or `os:windows`, `arch:x64` or `arch:arm64`, and `unix` on Linux and macOS. They count for job labels and `runsOn` like the labels of K-609, and change with each status. An offline machine has none, so they cost no row writes (K-1302). Nobody sets or removes them, so the owner labels refuse `unix` and the prefixes `os:` and `arch:`. They never include `deploy`, so consent stays with the owner (K-610).
- **K-611** A running app stays on its machine. kitshn never moves it by itself. "Move to <machine>" deploys it on the other machine, then removes the old copy. The placement of a Compose app adds and drops its other instances by the rules of K-825.
- **K-612** Commands are jobs too: restart the daemon, restart the tunnel, update the daemon, collect diagnostics, run a shell command. A provider adds its own commands (K-707). kitshn also queues "update the daemon" (K-627) and "restart the tunnel" (K-634) by itself.
- **K-613** A job for an offline machine waits. It has a delivery rule ("when online" or "when online and idle", `whenIdle`, K-1608) and an expiry: 24 hours by default, 1 hour for a job that a person approved for an agent (K-1776). A job that only the gate of K-1777 let run keeps 24 hours, because its delivery checks K-718 again.
- **K-614** "Run a shell command" needs `control` on the machine, unless a person in the Owner circle approved it for an agent (K-718), or the gate of K-1777 let the agent run it. History names the member that sent it. A job that kitshn makes itself, such as a deploy (K-812), needs no member: the `deploy` label is the owner's consent (K-610).
- **K-615** "Remove machine" runs at once, without a confirm, and History records it. It deletes the service token, the public key (K-1702), the tunnel, the DNS records and the queue, and closes the connection. Its apps show as stopped. A connected daemon removes its tunnel service, and that service stays gone until a new join, also after a restart of the daemon. An offline one keeps it until `kitshn service uninstall`.
- **K-616** A whole machine can belong to another person, for example a VPS in the circle "Her" with `use`. Its provider shows everything on it to every member with `use`, including the owner's threads there. The owner accepts this.

## Releases and the skill

- **K-617** kitshn names one release: the version of its Worker. The join, "Update daemon" and the deploy workflow download the daemon and the CLI only from that release, `edge-<version>`, and check each file against `SHA256SUMS`. No update path takes a version from the sender. The rolling `edge` release only serves the bootstrap of a new account. The release workflow never deletes an `edge-<version>` release: an old one is the way back, and a pinned machine keeps working. Every `edge` release is a pre-release, so none shows as "Latest".
- **K-618** The daemon and the App CLI carry the kitshn agent skill of their release. `kitshn skill install` writes it to `~/.local/share/kitshn/skills/kitshn` and links `~/.claude/skills/kitshn` to it. It replaces that path only when it is free or already a kitshn link, so a folder or a link of the user stays. `kitshn skill install --repo` writes the repo copy. `kitshn skill check` exits 1 when a copy is missing or from another release. The daemon rewrites the global copy at its start when it is from another release. The deploy workflow warns, and deploys anyway, when the repo copy is old.
- **K-619** Each daemon reports the TCP ports that listen on its machine, for the site wizard (K-1131), with the process name and the status and `<title>` of one `GET /`. It reports only the listeners of its own user, so it never probes a server of another user. kitshn keeps the list on the machine's socket attachment, so it costs no row writes. Trap: workerd keeps at most 16,384 bytes there, so all socket data shares one budget of 15,000 bytes, and the servers go first when it is over.

## Windows

- **K-620** Windows has one console binary, `kitshn-windows-x64.exe`, and no arm64 build yet. Windows cannot replace a running program but can rename it, so an update renames the running `.exe` to `kitshn.old-<time>.exe` and puts the new one in place. When that fails, the old one goes back, so the task always finds a binary.
- **K-621** On Windows the local socket of K-701 is the named pipe `\\.\pipe\kitshn-<user>`. Its default security descriptor gives write only to its owner, SYSTEM and Administrators. Traps:
  - The name is first come. So each client checks the account SID of the pipe's server process before it sends anything.
  - Bun's pipe server does not refuse remote clients, so only that access list guards the pipe from SMB. Known limit: with SMB open, a remote session of the owner or an Administrator reaches the pipe. Revisit when a machine has a user other than the owner.
- **K-622** On Windows `kitshn service install` registers two user tasks in `\kitshn\`: `daemon` and `tunnel`. They start at logon and through a repeating time trigger, because the repetition of a logon trigger starts only at the next logon. They run through `conhost --headless`, so no window opens. The daemon runs only while the user is logged on. Traps:
  - The tunnel task runs the daemon's own `kitshn-cloudflared.exe` with its own config and a metrics port that it keeps (K-632), so it never clashes with another cloudflared.
  - A process that the daemon spawns belongs to the task run, and `IgnoreNew` ignores a start while it runs. So a restart goes through a waiter that WMI creates. A daemon that does this reports `task-restart`.
  - `schtasks /End` does not stop the program inside `conhost`, so a stop also ends the process, found by its full path, never by its name.
  - The install refuses an elevated window, because its tasks carry an access list that the user's normal token cannot use.
  - The task output goes nowhere, so the daemon also writes `daemon.log` in its data folder.
- **K-623** On Windows the config, the key, the tokens and cloudflared live in `%LOCALAPPDATA%\kitshn`. The join gives that folder access only to the user and SYSTEM, because Windows ignores the file modes of K-602.
- **K-624** Windows does not have Compose apps, their logs and backups, doors (a Windows machine serves ports through a relay machine, K-2002), the server list of K-619, or local users other than the user who joined. The daemon does not report those capabilities, so the map and the deploy refuse them with a reason. Shell jobs run in Windows PowerShell.
- **K-625** "Add machine" also prints the join for Windows PowerShell. Its script sits below the public Access path `/join`, so the bootstrap needs no new application. It stops in an elevated window before it changes anything (K-622).

## Updates

- **K-626** Each machine has the setting "Update daemon automatically", on by default. It needs control on the kitshn admin, as the labels do. An agent needs the right "maintains" (K-1777). Each change is a revision with Undo. Turning it off ends that machine's step and failure in the rollout, so a machine that sleeps or broke never holds the others.
- **K-627** kitshn queues "update the daemon" by itself, one machine at a time. Hibernating daemon sockets can survive a Worker deploy without a reconnect, so once per release a wake of the Durable Object also checks the saved statuses of signed sockets. It picks the first machine in the owner's order that is online with a key, has the setting on, reports the `update` capability and runs another release than the Worker's. kitshn keeps one rollout in `meta`. The step ends well only when its job is `done` and the machine is online on the new release. A failure stops the rest of that release. "Update daemon" by hand on the machine that holds or stopped the rollout becomes its step. Rules:
  - A Windows daemon without `task-restart` (K-622) updates only by hand.
  - A machine whose provider reports `busy` (K-1608) holds nothing: kitshn goes on to the next machine and comes back when it is idle. After 2 hours of `busy`, it updates anyway. So `whenIdle` stays a preference and never a block.
  - kitshn delivers no automatic update while it is paused (K-1504).
  - An `update` by an agent does not end a stopped rollout. Only a person does.
- **K-628** The card shows the update state and the steps of the update job (K-538). The end of each update job adds a History entry. A failed update opens a notification (source `update`, K-1904), which closes when the failure ends.
- **K-629** An update keeps the way back. The daemon runs the new binary with `version` before the swap, keeps the previous binary (`kitshn.old`, or the renamed `.exe` of K-620), and writes `update.json` with a deadline 5 minutes after the swap. A small entry module reads `update.json` before any other daemon module loads. A start after the deadline, or after 3 starts without an accepted connection, puts the previous binary back. The new connection must stay up for 3 minutes before the daemon sends `done`, so a release that crashes just after kitshn accepts it never counts. A daemon never installs the release that it runs, so `kitshn.old` stays the way back. The service managers restart a daemon that ends. Known limits: a crash inside the entry module has no way back. A daemon that cannot reach kitshn for 5 minutes for another reason, such as a network outage, also rolls back.

## Health and connect steps

- **K-630** Every 10 minutes, each daemon checks what it can reach and sends the result to kitshn as `health`. A provider passes while a connection holds it. A link passes when one `GET /` through the link proxy (K-1609) reaches the card of a provider on the other machine. Any answer passes, except 401, 403, 5xx and a redirect to the Access login. So the check is one round trip per pair, and kitshn knows nothing of the provider. Failure counts live in memory. `kitshn health` shows the last report. Known limit: a provider that hangs behind a live bridge passes, but the link checks of other machines find it. Revisit when providers answer a ping.
- **K-631** kitshn keeps the last `health` report on the socket attachment (K-1708), so it costs no row reads or writes. The Machines view shows a grid: one row and one column per machine, with the providers on the diagonal. A report older than 25 minutes is unknown. A link that failed 2 times in a row opens a `health` notification. A link to an offline machine opens none, because the `machine` notification says that (K-1910). "Check now" (`POST /api/health/check`) asks each online machine that the caller controls.
- **K-633** The panel of a machine has "Connect this machine": live steps from what kitshn knows now (daemon connected, T3 registered, T3 address has its Access rule, member of a circle). The address step names what kitshn knows, not that the address answers. For 7 days after the join, the card shows the open steps. Known limit: a link test is no step yet, because kitshn stores no result of one. Revisit with `linkTest`.
- **K-634** A tunnel can stay connected in `cloudflared` while no request reaches it, so `/ready` (K-632) stays true. The link checks of other machines find it: a link with no answer at all, 2 times in a row, makes kitshn queue `tunnel-restart` on the target machine. The daemon then runs the restart steps of its tunnel service. Rules:
  - Only an online machine whose daemon reports `tunnel-restart` gets the job, at most once in 30 minutes, and once per failure streak. So a link that stays dead for another reason, such as a missing DNS record, does not restart the tunnel again and again.
  - History records it, with no Undo. The `health` notification of the link says that kitshn restarted the tunnel.
  - "Restart tunnel" on the machine card and in its panel queues the same job. Agents send it as a closed command with the rights of "Restart daemon" (K-718).
  - Known limit: one machine that reports is enough, so a reporter with a bad network can restart a good tunnel. Revisit with 3 or more machines, then ask for 2 reporters.
