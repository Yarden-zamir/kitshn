# Machine identity and agent rights

An agent on a joined machine acts in kitshn as its machine (K-1612). kitshn is the authority, not the tool layer: it decides who may do what, with which approval, and records it. Agents keep their own tools (`git`, `gh`, `wrangler`, cloud CLIs, MCP servers). kitshn gives them identity and short credentials, and never wraps those tools. This file holds those rules (K-17xx).

kitshn reaches an outside service in one of four ways, in this order of preference:

1. Federation: the service trusts kitshn passes. kitshn has no code for that service.
2. Token minting: kitshn makes a short, narrow token of the service (GitHub).
3. Action relay: kitshn makes the call with a credential that stays in kitshn. Only for a short, named list of actions, each with its own design check. None exists yet.
4. Not kitshn: the machine uses its own credentials.

Agent parity: every action of the owner has an agent path (K-1777). A call runs, waits for a person, or refuses because the rule also refuses the owner. What stays different: a person proves things with a passkey. An ask of "shares" or "secrets" needs that proof (K-1723). Check this in every new feature.

Each operation has exactly one effect (K-1730). Circles decide where an actor acts; effects decide what kind of action it takes, the same for a person, a token, a machine and an agent. A new operation takes one of the effects, so it gives no new kind of access by itself.

## Machine key pairs

- **K-1701** A machine proves itself to kitshn with its own Ed25519 key pair. Workers `crypto.subtle` and Bun both support Ed25519, so kitshn does not need P-256 here.
- **K-1702** The daemon keeps the private half in `machine.key` next to `machine.json`, mode 0600 in a 0700 folder. kitshn stores only the public half, its fingerprint and the time that it became valid. Known limit: root and every process of the daemon user can read the file, also an agent on the machine. Revisit with a hardware key (Secure Enclave, TPM), or when agents run as their own users.
- **K-1703** `kitshn join` makes the key pair before it sends the join code, and sends the public half with the code. kitshn stores it in the same step that deletes the code, and refuses a join without one.
- **K-1704** Each connection starts with a challenge: 32 random bytes per socket, kept only in the socket attachment, so a challenge writes no row. The daemon signs `kitshn-connect-v1`, the kitshn host, its machine id and the challenge. Each side takes the host from its own config, never from the challenge. Until the check passes, kitshn reads no message and sends no job, state or grant. Only an accepted socket replaces an older socket of the machine, so the token alone cannot push the real daemon off. Each socket accepts one answer, so a replay fails.
- **K-1705** "Rotate key" (panel or `kitshn rotate-key`) runs over the live connection. The daemon signs the new public half with the old key and the current challenge. kitshn stores the new key, writes a revision, and closes the connection, and the daemon connects again with the new key. From then on, kitshn refuses the old key. Only a member with control on the admin card rotates.
- **K-1706** "Reset key" is for a key that someone may have stolen, or for an offline machine. kitshn deletes the public half and closes the connection at once. Then `kitshn rekey <code>`, with the code rules of K-602, makes a new pair. The tunnel and the apps keep serving meanwhile (K-603), and jobs wait (K-613).
- **K-1708** A machine gets its first key only with a key code, from the join or from `kitshn rekey`. kitshn never takes a first key from a connection, so nothing runs unsigned. A machine without a key connects with its Access token for status and samples only. It gets no job, and kitshn ignores its other messages, so no unsigned message changes routing. Known limit: whoever holds the token of such a machine can push its daemon offline until the rekey.
- **K-1709** The machine keeps its Access service token, so `/connect` has two locks: Access checks the token, then kitshn checks the key signature. With the token, Access drops a socket without a valid service token before it costs a Worker request, and the token stays the machine's Access identity in circles (K-107). The owner chose this on the condition that joining stays one code: kitshn makes the token, and nobody copies one by hand.

## Asks

- **K-1710** An agent asks its daemon with `ask` on the local socket: one action, one target, an optional reason and optional labels. `kitshn agent <action> <target>` asks and prints the answer. The daemon accepts an ask only from an allowed local user (K-701), adds the attested labels (K-1752), and sends it over its signed connection. kitshn answers with the result, with "waiting" and a proposal id, or with a refusal and its reason. kitshn makes no token for its own actions: no JWT, no pass, no stored pass id.
- **K-1711** Owner actions are operations (K-1777). The asks match the agent paths of K-718: `state`, `apply`, `publish`, `organize`, `allow`, `deploy`, `job`, `job-read`, `github-token`, `audience-add`, `pass`, `approve`, `deny`, `history`, `backup` and `restore`. `state`, `job-read` and `history` need no effect. `approve` and `deny` need membership of the approver circle (K-1723). Each other action has one effect of K-1730.
- **K-1712** kitshn runs an ask only when all of these hold at that moment: the connection passed the challenge, the effect of the action is automatic for the actors of the call (K-1730) or an approval covers it, K-819 and K-718 allow the action (or an Owner approval covers it, K-1776), and kitshn is not paused. It checks them again when an approval runs the ask.
- **K-1713** Known limit: every process of an allowed local user can ask, and labels that no provider vouched for are claims. The unit of trust is the machine, plus the thread that its provider vouches for. Revisit when agents run as their own users.
- **K-1714** Agent keys keep their HTTP paths `/agent/<path>`. A machine asks the actions of K-1711 only over `/connect`. The CLI commands `publish`, `address`, `redirect`, `logs` and `repo` send their `/agent` call through the daemon as a `forward` request. Rules:
  - The daemon sends only a normalized path below `/agent/` or `/op/` (K-1777), signed with the machine key over the method, the path, the time, a nonce and the hash of the labels. kitshn takes a machine token on `/agent` only for a forward path with a valid signature from the last minute and an unseen nonce. It keeps the nonces in storage, so a restart does not let a copied call run again. The body is not signed; TLS covers it.
  - A forwarded call whose effect asks a circle, also by its default, waits like an ask: kitshn answers 409 with a proposal, and the CLI sends the same call again after the approval. With `--json`, the CLI also prints `{"outcome":"waiting","proposalId","circle","expiresAt"}` as one line on stdout while it waits, before the result line. The same call of the same machine and thread runs once within 1 hour after the approval.
  - `kitshn version --json` prints `{"product":"kitshn","generation":2,...}`, so a tool can tell kitshn 2 from a KitSHn 1 `kitshn`.
  - Known limit: a forwarded body is at most 12 MiB each way. Revisit when an agent needs more.
  - The owner chose HTTP over asks on `/connect` for these calls, because the asks would hold upload bodies in R2 for an approval. Revisit when an agent must not send its call a second time after the approval.
- **K-1715** An ask reads no Durable Object rows beyond a wake and the reads of the path that it runs: rights, circles, audiences and provider lists are in memory. It writes one ask event and one index row per label. `test/asks.test.ts` bounds the reads.
- **K-1716** "Rotate key", "Reset key" and "Remove machine" close the connection, deny every open proposal of the machine, and revoke every GitHub token of the machine that kitshn still holds. The pause does the same for every machine and agent key, and refuses new asks. Setting "reads" or "changes" to off revokes the GitHub tokens that it gave.
- **K-1717** Asks are events, not revisions: no Undo, kept 30 days, at most 5,000. An event names the machine, the action, the target, the reason, the labels with their vouching provider, and the outcome. A decision writes one revision. The thread title is the snapshot at ask time.

## Modes and approvals

- **K-1720** Each effect of an actor chip has one of four modes: "default", "off", "automatic" and "ask <circle>". "Default" takes the default of the effect (K-1730). Only "off", also as a default, refuses. Only a member with control on the admin card sets a mode, and each change is a revision. All configurations are allowed, and some get a warning (K-1725).
- **K-1721** With "automatic", kitshn runs the ask at once (K-1712).
- **K-1722** With "ask <circle>", kitshn makes a proposal (K-1607) that names the actor that asked, the action, the target, the reason and the labels, and answers "waiting". A proposal belongs to the credential that asked (K-1778), and each credential has at most 20 open proposals; a machine key counts once for all its actors. `kitshn agent` waits for the local socket event of the result, so nothing polls. The same call gets the open proposal while it waits, so nobody answers it twice: the same credential, the same vouched thread, the same stored body and the same labels. A call with no vouched thread never joins, because two agents of one machine key could send it. The circle's people get it in the Inbox and as a Web Push at once (K-1907). Deny works in both. The push carries ids only: the service worker reads the text with the browser's admin login and shows it. Notification and push texts leave out the request headers of a forwarded call, because a header can hold a token. The push offers "Approve" only when its body shows the whole shown text: one line of at most 100 printable ASCII characters, with no run of spaces (`approvesOnPush`). Else a tap opens the ask in the map. "Approve" sends the hash of that text to the approve path of its kind (K-1723) with the browser's own approve login. Without one, for example a passkey check older than 10 minutes, Access redirects, and "Approve" opens the check in a window. "Deny" runs with the admin login. The notification closes with the state of the proposal (approved, denied or expired), and its push tells every device. Mute and snooze hide an ask, but never answer it.
- **K-1723** One member of the approver circle answers, with its own proof at that moment. Rules:
  - A person approves through one of two Access applications compiled from the approver circles. An Access token does not say which policy or login method let a person in, so the application decides it: `/api/approve/passkey` holds the passkey circles, and each circle that a chip asks for "shares" or "secrets", and takes a login of at most 10 minutes. `/api/approve/login` holds the other approver circles. VERIFY: a person of a passkey circle reaches `/api/approve/passkey/start` only after a passkey prompt.
  - While any machine is joined, the Owner circle is an approver circle, because an unset effect can ask the Owner.
  - An approve shows the full text of the ask first (the Inbox row, a push that fits it in full as K-1722 says, or the confirm after the check), and approves only with the hash of that text. A link alone never approves.
  - "Resume" stays with the owner emails on `/api/fresh`. An approver policy never opens it.
  - A machine approves with the `approve` action over its signed connection. In a passkey circle, it approves only while "approves without passkey" is on (off by default), because it has no passkey (K-1778). A machine never approves a job or deploy outside the K-718 limit of the asker. Known limit: no route lets a token of an actor approve. Revisit with step (c) of K-1778.
  - An ask of "shares" or "secrets" needs a passkey proof: only a person through `/api/approve/passkey` approves it, also in a circle with "approves without passkey" on (K-1778). The asker never approves its own ask (K-1727).
  - A service token that no actor holds never approves. "Deny" needs no fresh proof, because it lowers access.
  - A proposal gets one answer, through one conditional write.
  - No proposal row holds a token. An approved `github-token` or `pass` sends "approved", and the daemon asks again. The same ask of that machine runs at once for 1 hour after the approval.
- **K-1724** A deny and an expiry after 24 hours reach the agent as "denied" or "expired", with the proposal id.
- **K-1725** The map warns, and does not refuse, when:
  - the approver circle holds only the actor that asks, which never approves its own ask (K-1727);
  - a passkey approver circle has "approves without passkey" on;
  - a high-risk effect ("creates", "changes", "runs", "destroys", "shares", "secrets") asks a circle with no person;
  - "shares", "secrets", "runs" or "destroys" is "automatic"; its chip on the map carries a warning;
  - an approver circle with a machine member reads requester text, which an agent can write to fool another agent;
  - "changes" is "automatic" on a machine actor with no conditions (K-1754).
- **K-1726** An agent that answers for a circle uses `kitshn agent approve` or `kitshn agent deny` with a reason. It never approves an ask of its own credential (K-1727). It sees in `state` the proposals of its circles, in a passkey circle only while "approves without passkey" is on.
- **K-1727** The credential that asked never approves its own ask, also when its actor is in the approver circle (K-1778). So no thread on a machine approves an ask of that machine. It may deny it, because that lowers access.
- **K-1776** A call whose effect asks the Owner, by its mode or by its default, waits for the Owner, and the approval runs that one call. A target that fails the scope of its operation (K-1777) waits for the Owner the same way, whatever "shares" says (K-1778). Rules:
  - An effect set to "off" refuses with one line that names the effect. "Off" counts only for its own effect.
  - A `job` or `deploy` outside the limit of K-718 asks the Owner also when its effect is "automatic" or "ask <circle>".
  - A job that no approval can run, a command that does not parse, and a backup or restore of a card that the machine does not manage refuse at once, with no proposal. A volume removal follows "destroys", on `/connect` as on `/op`.
  - A `kitshn gh` token ask with `auto` asks for write, because gh cannot say whether it writes.

## Operations

- **K-1777** One table, `OPERATIONS` in `packages/kitshn/src/operations.ts`, names each owner action once, with its owner route and its gate. Every caller uses the same path and the same gate: a person in the map or the CLI, an agent through MCP or the CLI, a script through the CLI. Only the proof differs. Rules:
  - `POST /op/<operation>` takes `{ target, body, reason }` and answers `done` with the result, `waiting` with the proposal, or `refused` with the reason. `GET /op/state` is the read: the row `state` (effect "reads") through the same gate, and its answer always through `AGENT_READ`. A row of an owner GET sends the text fields of its body as the query, for example `ask-events` with `label`.
  - Each row has exactly one effect (K-1730) and a gate: a scope, or "only a person" with its reason. Scopes: any, a card that the caller controls, a card that it added, a machine of K-718, the edit rule of K-715 and K-718, a job that the caller queued or that runs on a machine card that it controls, the port machines of K-2007, the caller's own machine, and "owner". The scope "owner" never holds, so each call asks the Owner: it covers settings of the whole kitshn and actions with no target that a caller controls. The desired state of one machine and the shared desired state are two rows, so the scope checks the part that the call writes. A target that does not exist refuses with "no such" and the kind, because no approval could run the call. A target that exists and fails the scope reaches beyond the caller's circles, so it asks the Owner, whatever "shares" says. An edit beyond the rule that only moves cards that the caller manages, not the admin card, follows "shares": into any circle or Everyone. Any other edit beyond the rule, such as a circle, a member, a level or the effects of a chip, is out of scope, so an actor never changes its own effects without the Owner. An edit that does not resolve does not pass the rule. A row that answers with a secret has the effect "secrets"; a row that can raise access (K-715) has "shares".
  - The gate: a person gate refuses. The admin runs, as from the map, so only the Owner circle passes the owner checks of the handlers. The pause refuses. An effect "off", set or by its default, refuses, also after an approval. A failed scope or an edit beyond the rule with "shares" off refuses, also after an approval. An approval of exactly this call runs. A failed scope asks the Owner, so a call out of scope never runs more easily than in scope. An edit beyond the rule on cards that the caller manages follows the caller's "shares". Else the mode of the row's effect decides, and "default" takes the default of the effect (K-1730).
  - "maintains" covers machine care, and the closing of invites and asks: restart, update, diagnostics, tunnel restart, order, automatic update, job cancel, the rotation of its own key, the health check, the cancel of a device invite and the deny of an ask. None of them opens a shell or raises access, so its default runs at once. The rotation of another machine's key fails the scope "self", so it asks the Owner, because it ends the approved jobs of that machine (K-1776). Labels have "shares", because the label `deploy` is the owner's consent (K-610). "reads" gives `kitshn state` the owner snapshot through `AGENT_READ`, which hides History text, jobs, queued jobs and icons, because they can quote what a person typed. The rows `jobs` and `state-export` give those, so they have "secrets". Known limit: `app-logs` stays "reads", but the logs of an app can hold a secret. Revisit when kitshn reads logs that it does not filter.
  - A call that runs goes through the owner code of its route, with the machine as the caller, so History names the machine. The rules that also bind the owner (K-105, K-1504) stay in the handlers. A job of the call carries the gate's approval with the verified labels of the call. Its delivery checks that the machine that asked, its key and the effect stay, as K-1776, and the labels let its agent actors count again. When no person approved the call, the delivery also checks K-718 again for a command that is not closed, and the job keeps the expiry of K-613. When only the gate let the call in, with no approval, the effect that let it in must still be "automatic" at delivery. The pause ends it (K-1504).
  - An approval runs nothing. The same call of the same machine and thread runs once within 1 hour, as K-1714. So a secret answer (a join code, a key code, an invite link, a device secret) never sits in a proposal row. The proposal names what the answer gives, for example a key code that can act as a machine.
  - The admin application lets in the owner logins and every token of kitshn: each machine token and each token credential of an actor, so `/op` has one Access application. It never admits any valid service token of the account, which would let in tokens of other apps. A machine proves its key on each call (K-1714), and its token alone never reaches an owner route: a machine acts only through `/op` or `/connect`, signed. A proof that no actor holds is refused.
  - `kitshn ops` prints the table, `kitshn state` the read, and `kitshn <operation> [target] --body <json> --reason <text>` one call. The machine binary calls through the daemon; the npm CLI calls with `KITSHN_TOKEN=<client id>:<secret>` and `--server` or `KITSHN_SERVER`. The table is in `packages/kitshn/src/operations.ts`, so both CLIs and the Worker read the same rows. A script on a joined machine uses the daemon and acts as the machine.
  - `src/core/operations.test.ts` fails when an owner route or a call of the map has no row, when a row has no effect of `EFFECTS`, and when a row with every effect unset refuses for a reason other than a person gate or the default "off" of "secrets". `test/operations.test.ts` sends each row, with an Owner approval, to the owner route as a machine call, and fails when the call fails where the owner's call does not, or when its job does not go out. It does not check the scopes. A row whose fixture target does not reach its handler checks fails for both callers, so the test does not see it; the test names these rows. A guard sends each row that had the scope "never" before effects, except `desired` (now scope "any"), as a machine with every effect automatic except "shares", once with "shares" at ask and once at automatic, and fails when one of them does not wait.

## Actors

- **K-1778** An actor is a name in the map that can act: a person, a script, a machine, or an agent on a machine. Every caller uses the same operation path and the same gate (K-1777): a person in the map or the CLI, an agent through MCP or the CLI, a script through the CLI. Only the proof differs. Rules:
  - A credential proves a call: a login, a token (K-106), or a machine key (K-107). A login and a token belong to exactly one actor. A phone or desktop token is a credential of its person, so a circle of that person also opens to the phone.
  - A circle holds actors and rules (K-202). Effects sit on the chip of an actor in a circle (K-1720, K-1730), for every actor, persons too, and count in every circle that holds the proof now. A call is every actor of its credential whose conditions hold, and the modes of their chips add up: "automatic" wins, then the first "ask"; "off" refuses only when no chip opens the effect.
  - An agent actor is a machine key plus conditions on attested labels (K-1754), not one actor per thread. It narrows the machine: it matches only calls with those verified labels. Only an actor with exactly one machine credential has conditions. It never enters Access or a grant table, because Access sees only the machine token.
  - The passkey line: a circle that needs a passkey holds only a login, because only a person at a device proves a passkey (K-103). kitshn checks this in the Worker and in the Access compile, so no token, machine or network holds such a circle, also a token of the owner. So no token holds the admin card (K-104) through a passkey circle. A token that held the admin through the Owner circle keeps it through its circle "<actor>'s devices", which needs no passkey (migration 44), and acts as the owner only with "shares" and "secrets" automatic (K-1730).
  - A script on a joined machine may use the daemon and then acts as the machine actor. A token of its own is optional: only for its own name, its own rights or its own revoke, or where no daemon runs.
  - "shares" alone shares what the actor manages: its cards into a circle or Everyone, audiences and passes (K-715). Out of scope, every call asks the Owner, whatever "shares" says. "shares" and "secrets" together act as the owner: a token or a machine with control of the admin card (K-104) holds the admin only with both automatic, and then runs past the gate. On `/op` a login runs past the gate only when it holds the admin through circles that all need a passkey, so it has every effect automatic. Every other caller goes through `decide`. Known limit: the map path `/api` keeps the admin check alone until step (c) moves the map to `/op`. An approval of an ask of "shares" or "secrets" needs a passkey proof (K-1723), and only such an approval runs a later ask of the same call for that effect.
  - The credential that asked never approves its own ask (K-1727).
  - Migration 44 made one actor per email, each joined machine, each agent key (K-1732) and each set of conditions of a machine right ("<machine> <rights>"). The machine chip asks the Owner for each right that moved to an agent actor. A device with the token of a joined machine became that machine (K-107). Another device in no passkey circle became a token of the one person that every circle of the device also holds, else an actor of its own. One circle widened: the token of a person opens the person's other circles. A device in a passkey circle stayed an actor of its own and got nothing in that circle, so its actor went into a new circle "<actor>'s devices" with the same place, level and share settings. No login gets these cards without a passkey. A token or a machine that held the admin through a circle kept it, in its devices circle or where it was, with "raises access" automatic on its chip, which migration 46 made "shares" and "secrets" automatic, so it still acts as the owner (K-1730). A History note names each one. Any other devices circle got no share of the admin. A circle of devices and machines only stayed an agent circle: each machine chip there got "maintains" and "reads the map" (now "reads") as "automatic" where no mode was set, because their default ran at once there before (K-1777). The migration keeps the circle bodies of before in `circles_before_actors`, and it rolls back when the moved map breaks a rule. An Undo never reaches a revision from before it.
  - Known limits: "Delete actor" removes the actor and its chips, but revokes no Cloudflare token. Revisit with the token revoke of step (c). A machine that leaves keeps its actors; "Delete actor" removes them. A person chip meets a scope only on rows of scope "any", because the other scopes read agent circles, so effects on persons are weaker than on agents. Plan person scopes for step (c).

## Rights on machines

- **K-1730** Each operation has exactly one effect (`EFFECTS` in `packages/kitshn/src/operations.ts`), and the modes of the effects sit on the chips of actors (K-1778). Circles decide where; effects decide what kind of action, the same for every actor. Rules:
  - The effects, with their defaults: "reads" (the map, logs, History, the output of its own jobs, repo read tokens, desired state; automatic), "maintains" (closed machine care, closing invites and asks; automatic), "creates" (new cards, which land only in the creator's own circles, so creating never shares; automatic), "changes" (existing cards in scope: deploys, settings, desired state, repo push tokens, backups; asks the Owner), "runs" (shell and exec on machines in scope; asks the Owner), "destroys" (anything without Undo; asks the Owner), "shares" (shares what the actor manages: its cards into a circle or Everyone, audiences and passes; asks the Owner) and "secrets" (invite codes, key codes, tokens, the last jobs with their output, the state export; off). "shares" alone shares what the actor manages; "shares" and "secrets" together act as the owner (K-1778). Every row of "secrets" has the scope "owner", so "secrets" alone hands out nothing without the Owner. A circle, a member, a level, deploy labels and every other setting of the whole kitshn ask the Owner, whatever "shares" says. A provider never puts a secret in desired state (K-709), so desired state stays "reads", with the scope "any".
  - A default of "automatic" counts per proof: for a caller whose proof is in at least one agent circle, in every circle where it acts. An agent circle holds only actors that are not people, has no rule, names the actor with at least one effect set, has not ended and does not need a passkey. A caller in no agent circle gets "ask the Owner" for an automatic default. K-718 holds for a machine in its agent circles, with the machine in place of the key.
  - Migration 46 moved the rights to effects: "reads code" and "reads the map" to "reads", "maintains" to "maintains", "adds apps" and "adds pages" to "creates", "deploys" and "writes code" to "changes", "runs commands" to "runs", "restores" to "destroys", and "publishes", "adds audiences", "gets passes" and "raises access" to "shares". The rights of one effect took the narrowest mode (off, then ask, then automatic), with the mode that an unset right had then, so the merge widened no chip; a History note names each merge of different modes. The new defaults and the new effects of some rows widen some calls, for example "creates" where "adds apps" and "adds pages" were unset. "reads code" and "writes code" counted only in a circle that holds a repo or a repo group. A chip with "raises access" automatic got "shares" and "secrets" automatic. A chip of an actor that is not a person, in a circle with people or rules, kept only "off", because its rights counted only in agent circles before.
- **K-1731** A machine actor in an agent circle is also an Access member of that circle (K-107), so its service token opens the sites of the circle. An agent actor with conditions is not: Access sees only the machine token.
- **K-1732** Migration 44 made each agent key a token actor: its flags became "automatic", "raises access" stayed at default, and its other rights became "off", so a key kept exactly its rights. Migration 46 then took the narrowest mode of each effect, so a key with "adds apps" and not "adds pages" has "creates" off (K-1730). A new token actor has every effect at default.
- **K-1733** A repo group is a card of the kind `repo.group`. It matches repos by owner or by a name pattern with one `*`. A right on a repo group covers every repo that it matches, also one that kitshn has not seen yet. Known limit: a pattern matches by name, while the gate of K-819 matches by id, so a repo that someone renames into a pattern gets the rights of the group.
- **K-1734** A click on a repo group card highlights the repo cards that it matches. The panel lists them.

## Labels and attestation

- **K-1750** An ask carries at most 10 labels, each a prefixed key (for example `t3.thread.id`) and a value. kitshn refuses a bad label and names it. Labels that no provider vouched for are claims, and History shows them as "claimed".
- **K-1751** A provider vouches for its own agents over its own connection (K-704), so no config lists attesters. An agent carries `KITSHN_ATTEST=<provider>:<token>`, and every agent command sends it. The daemon sends `attest` with the token only to that provider's connection. Known limit: the agents of a provider run as the provider's user, so an agent can register the provider again and vouch for labels of its prefix. Revisit when agents run as their own user, and before any grant depends on such a label.
- **K-1752** The provider answers `attest` within 2 seconds with `active` and at most 16 bare labels. The daemon adds the provider's prefix and marks them "verified by <provider>". A call that carries a token fails closed: no provider connection, a late answer or `active: false` refuses it. It never goes on as the bare machine. A call without a token goes as the bare machine, so it matches no agent actor (K-1778).
- **K-1753** The daemon and kitshn drop every caller label with the prefix of a provider of the machine. Only that provider sets those labels. The prefix `t3.` stays reserved also on a machine without T3.
- **K-1754** An agent actor has conditions on attested labels: a key equals a value, or is one of a list (K-1778). A condition counts only on the prefix of a provider of the machine, so a claimed label never meets one. A call that fails a condition is not that actor: it gets the modes of the other actors that it is, at least the machine actor.
- **K-1755** T3 vouches with `thread.id`, `thread.title`, `project.id`, `project.name`, `environment.id`, `provider`, `runtime`, `interaction`, `subagent`, `thread.parent` and `thread.parent.environment`. Known limits: agents and the T3 server run as one OS user, so an agent that steals the token of another thread acts as that thread. An in-process subagent uses its parent's token, so it has `t3.subagent` = `false`. Revisit when agents run as their own users.
- **K-1756** History is searchable by label: `key=value` in the History view, and `kitshn agent history --label`, at most 50 events. kitshn stores one index row per label, on (key, value, time).

## GitHub tokens

The GitHub App (K-908) needs Contents and Pull requests (read and write) for these rules.

- **K-1760** The GitHub way of an owner is a setting of its owner repo group: "kitshn App token" or "not kitshn". Settings holds the default, "not kitshn" at first. Only kitshn answers "not kitshn", and the daemon keeps no copy. Known limit: kitshn sees the repo name of each ask, also for a "not kitshn" owner.
- **K-1761** "reads" gives Contents read and Metadata read on a repo that a card in its circle covers (K-1733); unset, it takes its default there. "changes" gives Contents write and Pull requests write, and includes "reads". A push token never deploys (K-1767). No effect gives Workflows, Secrets, Administration or Issues. A future token for one of them needs its own decision on its effect (K-1725).
- **K-1762** `github-token` asks for one repo and "read" or "write". kitshn makes an installation token for that repo only, with the permissions of K-1761. GitHub fixes its life at 1 hour. Rules:
  - kitshn keeps each live token in `github_tokens`, sealed with AES-GCM under a key that HKDF derives from the App private key. `DELETE /installation/token` needs the token itself, so the sealed copy is the one way to revoke it after a sleep. The table is in `SECRET_ROWS` (K-1831).
  - The daemon keeps a token in memory only, until 5 minutes before it expires. It reuses a kept token only for the same repo and the same attested `t3.thread.id`. It drops every kept token on a new connection and on a key rotation.
- **K-1763** `kitshn git-credential` is a git credential helper, which `kitshn setup-git` writes before other helpers. Git never tells a helper push from fetch, so `setup-git` also sets `pushInsteadOf`, and a push carries the user name `kitshn-push`. The helper asks for "write" on a marked push and "read" otherwise. For a "not kitshn" owner, or with no daemon, it prints nothing, so git tries the next helper. For a "kitshn App token" owner, a refusal prints `quit=1`, so git never falls back to the machine's own login. Known limits: a helper that looks up the user name does not answer a marked push, so `setup-git` warns about each one. A remote with its own `pushurl` is not marked.
- **K-1764** `kitshn gh <args>` gets a token for the repo of `--repo` or of the git remote, and runs `gh` with `GH_TOKEN`. It adds nothing else.
- **K-1765** Work with these tokens shows as `kitshn[bot]` on GitHub, so the owner can review agent pull requests. Commits keep the author of the machine's git config.
- **K-1766** An owner without the App gets "the kitshn App is not installed on <owner>" and no token.
- **K-1767** A push or a pull request of the kitshn App bot never deploys by itself. A push waits for a deploy ask (`kitshn agent deploy`), which runs by `workflow_dispatch`. A pull request waits for the owner's "Deploy" in the map panel, which approves that commit only. While kitshn cannot read its bot name, every actor that ends with `[bot]` waits.

## Passes for outside services

kitshn's own actions never use passes (K-1710). Passes stay off until the host move of K-1209 is done. While they are off, `pass` refuses, and the `/.well-known` paths answer "not found". The claims are a public contract in [passes.md](../user/passes.md).

- **K-1770** kitshn is an OpenID issuer, `https://kitshn.<zone>`. The Worker serves exactly `/.well-known/openid-configuration` and `/.well-known/jwks.json` with no login and `max-age=300`. Every other path below `/.well-known/` answers "not found". There is no authorization endpoint, because kitshn gives passes only to machines.
- **K-1771** The pass key is ES256 (P-256), which AWS and Google Cloud accept. The Durable Object makes it and keeps it in its storage, never in a Worker secret. No read path, export, backup, snapshot or History entry includes the private half, and a test checks that. The JWKS lists a retired key for 6 minutes (pass life plus leeway), at most 5 keys. kitshn's own restore to a time rotates the pass key as its last step. After a restore outside kitshn, the owner rotates it at once. Revisit with RS256 for a verifier that refuses ES256.
- **K-1772** A pass is a JWT with `iss`, `aud` (one allowed audience), `sub` `machine:<machine id>`, `iat`, `exp` 5 minutes later, and `jti`. Only when the audience allows labels: `act` from an attested `t3.thread.id`, and `kitshn_labels`. `sub` holds ids only, never names. kitshn only adds claims and never renames or removes one.
- **K-1773** Audiences are a list in Settings, each with its exact address and "labels in passes" (off by default). An agent with "shares" adds one, and removes one that it added at once, because that lowers access. An audience grants nothing by itself: the outside service must also trust kitshn.
- **K-1774** `kitshn agent pass --audience <address>` asks for a pass. It needs "shares" and an audience in the list. kitshn stores no `jti`: only the outside service checks the pass. Known limit: a pass is a bearer token for 5 minutes that kitshn cannot revoke. Revisit with DPoP (RFC 9449).
- **K-1775** A pass costs one ask event and reads no row beyond a wake. Discovery and JWKS read no row: the public keys are in memory.
