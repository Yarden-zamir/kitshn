# Logs, backups and the state export

This file holds the rules for logs (K-180x), backups of Compose apps (K-181x and K-182x), and the export and import of kitshn's own state (K-183x).

## Logs

- **K-1801** "Logs" opens the logs of a Compose card or a Worker card, with the tabs "App" and "Deploy runs", a plain-text search that ignores case, and a time range. The view shows at most the newest 500 matching lines. "Live" follows new lines. This replaces dozzle, the log viewer of KitSHn 1.
- **K-1802** Only the admin (K-104) reads logs. A later read by another member needs a new level `use` on `site.compose` and `site.worker`. An "everyone" circle never gives logs, because logs can hold data that the page does not show. Static sites, pages, files and live sites have no logs, because kitshn runs no code of theirs.
- **K-1803** A Compose app keeps its logs on its machine, in Docker. Each deploy sets `logging: {driver: local, options: {max-size: 10m, max-file: 3}}` on each service, so a container keeps at most 30 MB of logs. A service with another allowed driver (K-818) keeps it, and its logs do not show in kitshn. No log line goes into the Durable Object or R2.
- **K-1804** A Compose search goes to the daemon of the card's machine, which runs `docker compose logs --timestamps` and sends the newest 500 matches and the count. The daemon stops a search after 15 seconds and says that it was cut. It reads only projects with an app folder below its `apps` folder, so a request never reads a project that kitshn did not deploy. A search writes no row.
- **K-1805** "Live" on a Compose card follows the daemon's `docker compose logs --follow`, in batches of at most one a second. It stops when the view or a connection closes, and after 30 minutes. A quiet app would wake the Durable Object for each batch, about 330 rows read per wake. So while a map holds a tail, a timer keeps the Durable Object in memory, and Live costs only duration.
- **K-1806** A Worker app logs to Workers Logs, which each deploy turns on. Cloudflare keeps the events, and kitshn stores none. Search uses the telemetry query API, which needs "Account > Workers Observability > Edit". Without it, the search box names the steps to add it, and Live still works.
- **K-1807** "Live" on a Worker card starts a tail through the API, and the map connects to the tail address itself, so tail events cost no Worker or Durable Object request. kitshn deletes the tail when the view closes.
- **K-1808** "Deploy runs" lists the newest 20 deploys of the card with their state, reason and run link. A Compose deploy shows its job output (K-813). The output of a static or Worker deploy stays in GitHub Actions.
- **K-1809** `kitshn logs <card> [text]` searches the logs of a card through `POST /agent/logs`, with the same search and limits as the map. `--json` prints one JSON object. It exits 0 when the search worked, also with no line, 1 on an error or refusal, and 2 on bad arguments. Known limit: no live follow, because Live needs the map's WebSocket. Revisit when agents need to watch a deploy come up.
- **K-1810** An agent key reads the logs of a card only while it controls the card (K-718). A key searches at most 30 times a minute, then gets 429, so an agent loop cannot keep a daemon busy. The count lives in memory.

## Backups

- **K-1811** Each Compose card is backed up once a day: each named volume of its project and its data folder. A preview is not backed up, because it is temporary. Each card has one restic repository in R2 at `backups/<card>/`, so a backup is deduplicated, compressed and encrypted. Daily full copies would not fit the 10 GB of free R2. Known limit: kitshn backs up no storage of Worker apps (KV, Durable Objects), because it cannot read a Durable Object from outside. Revisit when a Worker app holds data that matters.
- **K-1812** The daemon runs a pinned restic image as a container without a network, with each volume and the data folder mounted under `/data/<name>`. So restic reads files with user ids that the daemon user cannot read in rootless Docker. The password reaches the container in its environment, never on a command line. One backup run is one snapshot with the tag `run-<id>`.
- **K-1813** restic talks to a proxy that the daemon serves on a Unix socket only while a backup or restore job runs, below a random secret path of that job. The proxy adds the machine's Access headers and sends each request to `/connect/backups/<card>/<restic path>`. The Worker serves the restic REST protocol from the R2 binding and streams each body to R2. restic writes packs of at most 32 MiB, under the 100 MB request body limit, inside the 10 ms of CPU.
- **K-1814** The Worker lets a machine reach `backups/<card>/` only while it runs a backup or restore job of that card, as for deploy files (K-812). The check reads the current machine of the card on each request, so a move (K-611) needs no other step. A short socket drop does not break a running backup.
- **K-1815** The repository password of a card is HMAC-SHA-256 of the card id under the Worker secret `KITSHN_BACKUP_KEY`. The bootstrap makes and prints this secret once, only with `KITSHN_BACKUP_KEY_NOW=1` and its output on a terminal, so the key never lands in a log file. Without the key, backups stay off and each Compose card says how to turn them on. Without the key nobody, kitshn included, reads the backups, so a lost key loses them. Known limit: kitshn has no rotation of this key. Revisit when the key must rotate.
- **K-1816** A backup first runs restic while the app runs, which copies the bulk. Then the daemon pauses the app (`docker compose pause`), runs restic again, and unpauses. A marker file makes each daemon start unpause an app that a crash left paused. The paused snapshot is a copy as after a power loss, which SQLite, DuckDB and Postgres recover from. Requests wait during the pause instead of failing. The pause has a hard limit of 3 times the last pause, between 30 and 90 seconds, because Cloudflare waits 100 s for an answer. Known limit: every card works this way, and an app whose pause grows past 90 s fails its backup each night. Revisit then with a dump hook per app.
- **K-1817** At 03:00 UTC, the alarm queues one backup job for each Compose card with a finished deploy, on daemons with the capability `backup-restore`. After each backup the daemon runs `restic forget` with 7 daily, 4 weekly and 3 monthly runs, and forgets `before-restore` runs after 7 days. It prunes on Sundays. "Back up now" queues the same job at once.
- **K-1818** Before it queues backups, the 03:00 run adds up the sizes of the whole `kitshn` bucket. At 8 GB or more it queues no new backup, and each Compose card says why. A restore passes this guard, because it is the step that the owner needs most.
- **K-1819** The card panel shows the newest backup and "Backups…", which reads the `backups` table, never R2. A failed backup shows a sticker until the next backup works. When a card with backups is gone for 7 days, the 03:00 run deletes its repository and rows, so a new card with the same id starts empty. An Undo within those 7 days keeps the backups.
- **K-1820** "Restore" on a backup run asks for a confirm that names its time. The daemon then:
  1. checks that each volume and folder of the run exists;
  2. takes a paused backup with the tag `before-restore`, the way back;
  3. writes the run into `.kitshn-restore` in each volume and the data folder, while the app runs;
  4. stops the app and swaps the folders, and writes the name of each moved entry before it moves;
  5. starts the app and deletes the old files.

  A failure before the swap leaves the data as it is. A failure in the swap or at the start puts the old files back and starts the app on them. The point of no return is a swap whose app started. A marker file names the phase, so a daemon that stops in the middle finishes it at its next start. Undo cannot run a restore: the way back is "Restore" on the `before-restore` run. Known limit: step 3 needs free disk for a second copy, and the app sees `.kitshn-restore` in its folder. kitshn writes it there because a rename inside one volume is the swap.
- **K-1821** The Durable Object data has two copies: point-in-time recovery of 30 days, at no cost in rows or R2, and the daily state export (K-1831) in R2 as `state/<date>.json.gz`, 30 kept. The export holds no secret, and the restic repositories need `KITSHN_BACKUP_KEY`.
- **K-1822** "Restore kitshn to a time…" needs a fresh passkey (K-1504) and a confirm that names what goes out of step. It rewinds everything in the Durable Object, but not Cloudflare. The next alarm makes Cloudflare match the restored state (K-408). The restart loses writes after the restore point, so the restore keeps its finish in R2 (`state/restore-pending.json`). The finish sets the job ids past the old highest one, so a late daemon result finds no other job. It records the restore with an undo bookmark and rotates the pass key (K-1771) as its last step, because the restored storage can hold a retired key.

## State export and import

- **K-1831** The state export is one JSON file of every Durable Object table, with the account id and the schema version. It leaves out the one-time codes, the jobs, and each secret that `SECRET_ROWS` (`packages/edge/src/worker/backups.ts`) names: the pass key, the sealed GitHub tokens, the VAPID key and the push subscriptions. A new secret is one line there, and a test checks each line.
- **K-1832** "Download state export" in the Safety panel saves the export from `GET /api/state/export`. Only the admin reaches it.
- **K-1833** `KITSHN_IMPORT=<file>` makes the bootstrap rebuild kitshn from an export. The bootstrap uploads the file to R2 and sets `KITSHN_IMPORT_AT`. The Durable Object imports it once, before its other start steps. The public `GET /join/import-status` answers only a status and a code, and the details go only to the server log, because they can name an account or a card. The import refuses an install that is not empty, an export of another account, and an export of a newer schema or an unknown table. Then one transaction drops every table, migrates to the export's schema, writes the rows, and runs the later migrations. kitshn then deletes the file, because it holds the whole state.
- **K-1834** After an import, the next alarm writes what Cloudflare lacks (K-408), each daemon connects again with its own token, and the pass key rotates (K-1771). Known limits: an import works only into the same Cloudflare account, and it rebuilds no R2 object. Revisit with a move to another account, which needs a new join of each machine, a new deploy of each Worker and a copy of R2.
